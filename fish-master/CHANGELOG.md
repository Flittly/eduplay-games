## v0.1.0

**这一版修掉了两处会影响学生认知的真实缺陷，并接入了地球真实影像底图。**

### 底图：手绘简化多边形 → 地球真实影像图

- 旧底图是 7 个手绘多边形（北美/南美/欧非/亚洲/澳洲/格陵兰/南极），
  注释里就写着"极度简化，不追求地图精度"。
- **问题（实测）**：那张图**没有一致的经纬网** —— 各大陆的经纬尺度互相对不上。
  按同一套等距圆柱反算，澳洲被压在 −60°~−31°（应 −39°~−10°，整体南移约 20°）、
  亚洲经度上限只到 141°E（应到 180°）、非洲南端到 −48°。学生无法从它建立
  "这条洋流在真实地球的哪里"的空间认知。
- **现在**：底图换成**地球真实卫星影像**（天地图，合规图源），并叠一层
  **真实海岸线**（Natural Earth 110m，公有领域）让大陆形状在影像上仍清楚。
- 影像需要一份天地图密钥，由老师在**大厅「底图」区填一次**，只存本机浏览器。
  **没填或没网时自动回退到内置海岸线底图，玩法完全不受影响。**
- 底图来源按合规要求标注在图上。

### 洋流位置：手写归一化坐标 → 真实经纬度

- 旧坐标是手工摆在手绘底图上的 0~1 值，**与真实地理毫无对应**。
- **问题（实测偏差，全部为真错）**：

  | 洋流 | 旧位置换算后 | 真实位置 | 偏差 |
  |---|---|---|---|
  | 加利福尼亚寒流 | 41°E, 31°N（大西洋东岸） | 128°W, 35°N | **169°** |
  | 阿拉斯加暖流 | 36°E, 63°N（欧洲北部） | 145°W, 55°N | **181°** |
  | 南赤道暖流 | 90°E, 6°S（印度洋） | 125°W, 8°S | **215°** |
  | 北赤道暖流 | 90°E, 11°N（印度洋） | 160°E, 12°N | 70° |
  | 北太平洋暖流 | 79°E, 46°N | 155°E, 40°N | 76° |
  | 赤道逆流 | 79°E, 2°N | 155°E, 5°N | 76° |
  | 西风漂流 | 43°E, 62°S | 0°, 50°S | 45° |
  | 东澳大利亚暖流 | 113°E, 28°S | 155°E, 32°S | 42° |
  | 墨西哥湾暖流 | 31°W, 27°N | 70°W, 35°N | 40° |
  | 拉布拉多寒流 | 14°W, 42°N | 52°W, 55°N | 40° |

  即：**整个太平洋的洋流全部横向错位**，北赤道暖流与南赤道暖流被画到了印度洋。
- **现在**：24 条洋流全部改存**真实经纬度**，画布位置由 `src/proj.ts`
  按等距圆柱投影现算。经纬度成为唯一真相源，位置可复核（查一个经纬度就能验）。

### 新增的技术设施

- `src/proj.ts` —— 经纬度 ⇄ 画布 投影层；含跨 ±180° 日界线的拆段算法
  （北太平洋暖流、南北赤道暖流、赤道逆流这 4 条会跨，不拆会在画布上横穿全图）。
- `src/basemap.ts` —— 天地图影像接入。按画布分辨率自动选 z=2（源分辨率≈画布需求，
  16 块源瓦片；每块沿纬度切 8 条以贴合等距圆柱，共 128 个子块，肉眼无缝）。
- `src/imageryKey.ts` —— 密钥的本地存取（只进 localStorage，不上传、不随包分发）。
- `scripts/prepare_world.py` —— 生成真实海岸线数据（可重跑）。
- 大厅新增「底图」设置区与**底图预览**，老师开局前就能看到底图长什么样。

### UI 与项目基调对齐（基础层统一）

审计了 13 个游戏的 `:root` 变量后，发现项目里已有一套公认基调，
而本作在**每一条**上都不同：

| 项 | 项目里 7 个游戏的取值 | 本作原取值 |
|---|---|---|
| 页面底色 | `#f2e8d5` 米黄纸 | `#ffffff` 纯白 |
| 主文字 | `#1a1a1a` | `#1d2b36`（偏蓝） |
| 强调红 | `#cc0000` | `#e0483a` |
| 圆角 | `0`（直角基调，9/11 个游戏） | 12px / 8px |

现在**基础层对齐**（纸色、墨色、强调红、圆角、阴影），本作在商城列表里
与其它游戏属于同一族。

**同时有意保留两处例外，并写明理由：**

- **`--warm` / `--cold`（暖流红 `#e0483a` / 寒流蓝 `#2f6fb5`）不参与统一。**
  它们是**知识点本身的编码**，要跟教材图 4-24 的箭头颜色一致 ——
  学生看到红色要想到"暖流"。改成项目通用的 `#cc0000` 会让学生对不上课本。
- **错误/失败态的红色改用 `--red`（`#cc0000`）。**
  原先错误态也画成暖流红，导致"答错了"的那层红与图上暖流箭头同色 ——
  而本游戏的核心恰恰是让学生分清暖/寒，两种红必须分开。
  现在语义清晰：`var(--warm)` 只剩 4 处（全是暖流语义）、`var(--red)` 7 处（全是错误态）。

### 字号体系：32 个散值 → 6 档

原先本文件有 **32 种** `font-size` 取值，其中
`12.5 / 12.6 / 12.8 / 13 / 13.2 / 13.4 / 13.5 / 13.6 / 13.8 / 14 / 14.2 / 14.3 / 14.4 / 14.5 / 15 / 15.5`
—— **3px 波段里挤了 16 个值**。那是历年微调累积出来的，不是设计系统：
单个差异肉眼看不见，但导致"没有两块面板共用同一节奏"。

现收敛为 6 档：`--fs-xs 13 / --fs-sm 14 / --fs-md 15 / --fs-lg 17 / --fs-xl 20 / --fs-2xl 24`
（取值参考 `china-relief` / `mountain-zones` 已有的 `--fs-*` 档位）。
共替换 87 处，产物里不再有任何裸 `px` 字号。

**另外单列一套 SVG 专用档位 `--fs-map-label / -note / -badge`**：
SVG 里的 `font-size` 是 **viewBox 用户单位**，不是屏幕像素，差一个约 0.8 的缩放比。
混用会引出"看着小而调大 → 屏幕上又跟正文一样大"的来回改。两套单位分开命名即解决。

### UI 与项目基调对齐（第二批：组件层 —— 真正让观感归队）

> 第一批（下方"基础层统一"）只改了 `:root` 的取值。上架后学生一上手就反馈
> **"UI 风格并没有保持一致"** —— 因为"看着像一套"并不来自颜色，而来自
> **五个共同结构**。这一批把这五项全部补齐：

| 结构 | 项目 7 个游戏的写法 | 本作（第一批后） | 现在 |
|---|---|---|---|
| 字体栈 | `Arial Black / Franklin Gothic Heavy` + 全站 800 字重 | `Noto Sans SC` + 400/600 | **已对齐** |
| 边框 | `3px solid var(--ink)` 墨色硬边 | `1px solid var(--line)` 浅棕细线 | **已对齐** |
| 阴影 | `Npx Npx 0 var(--ink)` 零模糊硬投影 | `0 1px 3px rgba(...)` 软阴影 | **已对齐** |
| 圆角 | `border-radius: 0 !important` | 2px，另有 6 处 20px 胶囊 | **已对齐** |
| 交互 | hover `translate(2px,2px)` + 阴影同步缩短 | 只改 `border-color`/`brightness` | **已对齐** |

具体落到这些地方：

- **全局 `button` 改为项目"纸墨按钮"三件套**：3px 墨边 + 纸色底 + 4px 硬投影；
  hover 整体右下平移 2px、投影缩到 2px；active 再平移 2px、投影归零。
  `border-radius: 0 !important` 同时压掉浏览器默认圆角。
- **对局页顶栏 `.hud`：白底细线 → 项目标配的"墨色横条"**（墨底 + 纸色字 +
  4px 墨线下边 + 右上角红色旋转斜条），与 6 个游戏逐字节同款。
  顶栏内的读数格改用纸底方块（压在墨底上才读得清）。
- **所有卡片统一成"4px 墨边 + 8px 硬投影"**：地图框、提问卡、结算卡、图鉴卡、
  大厅各卡。软阴影全部清掉（它是"浮在玻璃上"的语言，与硬边框打架）。
- **大厅/图鉴/战绩页主标题**：加 6px 墨色下划线 + 尾部一枚红色方块（项目标配）。
- **侧标式强调卡**：解释卡、三层说明、易混清单改用"白底 + 墨边 + 一道加粗彩色左边"，
  不再用整块浅色底 —— 投影仪上浅底会让墨字发灰、后排读不清。

**本轮真机抓到的回归（连带修掉）**：给大厅预览框加 3px 边框后，
`aspect-ratio: 1000/560` 的**内边盒**比例掉到 **1.8015**（正解 1.786）——
因为子层 `.current-map-wrap` 用 `inset:0` 贴在内边盒上，边框会从内容里占走 3px。
影像瓦片层与 SVG 都按百分比定位，比例一偏就**两层错位 + 两极横向条纹**。
改用 `outline`（不占布局空间）后回到 **1.7860**。

这条也补了**两道判据**：源码层 `assert_preview_border_is_outline()`（打包时就拦）
＋ 真机「大厅预览比例 = viewBox 比例」（两道都反证过会红）。

### 上架前修掉的一个"看不见的 bug"：影像层其实没显示

首次构建完成后做真机截图复核，发现**影像底图在屏幕上完全看不到** ——
而所有机器判据当时**全是绿的**：128 块瓦片加载成功（`naturalWidth=256`）、
位置尺寸全部正确、`display/visibility/opacity` 正常、来源标注也出来了。

根因：SVG 里有一层**铺满整张画布的不透明海面矩形** `<rect fill="url(#sea)">`，
它的本意是"没影像时当底图"，但它的 **z-index（1）高于影像瓦片层（0）**，
且**无条件渲染** ⇒ 影像瓦片即使 100% 加载成功也被它整块盖住。
画布区域实测平均亮度 **232.5**，恰好是 `#dce9f6`（那层海面渐变的底色）的亮度。

**修法两处：**

1. 海面矩形改为**只在没有影像时渲染**（`{!imagery && <rect …/>}`）。
2. `.map-tile` 的 `object-fit` 由 `cover` 改为 `fill` ——
   一块 256×256 的瓦片在画布上被切成 8 条很扁的横条（宽高比 ≈12.5:1），
   `cover` 会等比放大后裁掉约 92% 的图像、只留中间一条，
   128 条都取"同一中心线"⇒ 整张画布退化成均匀色。

**并且补了一条"看得见"的判据**：影像模式下画布区域的**像素标准差**必须 > 26。
实测：被盖住时 **17.2**、真影像铺满时 **40.2**（阈值取在中间）。
这条判据用同一缺陷注入验证过**确实会红**（17.22），是目前唯一能守住这个 bug 的检查 ——
因为压缩后局部变量会被改名，静态字符串指纹守不住这个 JSX 条件。

> 为什么仍叫 v0.1.0：这一版**尚未有学生玩过**，影像不可见属于"交付前自己发现的缺陷"，
> 不是对已发布行为的变更，因此并入同一版本号，不另占一个版本。
