## v1.4.6 改了什么（2026-09-25 上架）

一线反馈回来的两条，看着是两个不相干的毛病，**根因是同一处**：

> 1、左上角月相小窗中的月相图超过了小窗本身
> 2、主窗口中的月球没有在屏幕的最中间

### 一、根因：canvas 的**显示尺寸**不该由 devicePixelRatio 决定

`renderer.setSize(w, h, false)` 的第三个参数是 `updateStyle`，传 `false` 就是
"**别**写 canvas 的内联样式"。而 canvas 是**替换元素**：CSS 不给它尺寸时，
它的**显示尺寸就退化成属性尺寸**（`canvas.width/height`）。而代码里属性尺寸是
`w × devicePixelRatio` ⇒ **DPR>1 的机器上画布被整体放大 dpr 倍**。

```
DPR = 1.50（Windows 150% 缩放）实测：
  月相小窗   缓冲 225×225 显示成 225px → 塞进 146px 的内容框，溢出 77px；
             月盘直径 188px > 卡片内容宽 146px ⇒ 把"上弦月 / 50.0%"整行盖掉   ← 反馈 ①
  主视图     缓冲 2520×1198 显示成 2520×1198，而 .moon-stage{overflow:hidden} 只有 1680×799
             ⇒ 只露出渲染画面的左上角；月球画在渲染画面正中 ⇒ 屏幕上落在 (1260, 599)，
               偏离可视中心 465px、掉到右下角                                 ← 反馈 ②
```

**修法是让 CSS 决定显示尺寸**，属性尺寸照旧是 `w × DPR` —— 那本来就是**渲染分辨率**，
DPR>1 时更清晰，与布局无关。四处改动：

| 位置 | 改法 | 为什么 |
|---|---|---|
| `.moon-canvas canvas` | `width:100%; height:100%` | 容器 `inset:0` ⇒ 内容盒 = 舞台尺寸，与 `setSize` 的入参同一个数 |
| `.phase-canvas` | 显式 `box-sizing: content-box` | 全局是 `border-box` ⇒ 150px 的**外框**只剩 146px 内容宽，画布会盖住右侧与下侧的墨框（DPR=1 时也能量到 4px 溢出） |
| `.phase-canvas canvas` | `width:100%; height:100%` | 挂在那个 150px 的内容盒上 |
| `PHASE_WINDOW_W` | 178 → 182 | 画布外框 154px + 内边距 16 + 卡片墨框 6 = 176，两边各留 3px |

修复后实测（DPR=1.5）：月相画布显示 **150×150**（缓冲仍 225×225）、月盘占容器半宽
**84%**（修复前 129%）；主画布显示尺寸 **= 舞台尺寸**，月盘相对可视中心偏移
**0.0px**（修复前 465px）。

### 二、为什么这版能一路全绿、却让两个毛病跑到用户手里

**因为回归只在 DPR=1 下跑过。** 而 DPR=1 时"属性尺寸 = 显示尺寸"恰好成立 ⇒
B6/B10 那几条判据全绿。这一版把这条补上：

- 回归脚本新增 **`MOON_DPR`** 环境变量：`MOON_DPR=1.25 sh run.sh shot.js`。
  它用 `--force-device-scale-factor` 只改 devicePixelRatio、**不动 CSS 视口**
  （实测 CSS 视口仍是 1120×740）⇒ 全套判据原样复用，不必为高 DPI 另写一套。
- 新增四条**尺寸口径**判据（与 DPR 无关）：B6b/B6c（主画布显示尺寸 = 舞台、
  属性尺寸 = 显示 × DPR）、B10b/B10c（月相画布同款，且不溢出墨框）。
- 顺手修掉三处**判据自己的错**（它们在 DPR≠1 下会假红，会把人引去查产品）：
  - `mainLimbPx` 曾乘 `devicePixelRatio`。它比较的是 `diskOnScreen().radius`（CSS 口径），
    乘 dpr 之所以"对得上"，纯粹因为当时 `clientHeight` 恰好等于属性尺寸 ——
    **两个错互相抵消 ⇒ 判据全绿而屏幕是坏的**。
  - B7「左边缘落在整数像素」在 125% 缩放下不成立：Chromium 把栏内内容吸附到
    **物理像素的半点**（实测 x=32.4 ⇒ 物理 40.5），那是整栏一致的**全局偏移**、
    眼睛看不出来 ⇒ 改成与 DPR 无关的"两栏各自只有一个 x 值（栏内严格对齐）"。
  - I29g 的**新月重心**不再参与断言：受照比例趋近 0 时重心**分母接近 0、由噪声主导**
    （DPR=1 时落进容差是运气）⇒ 改成"两边都确实亮不起来（< 0.02）"。

### 三、比上版改了什么（一眼版）

- 主视图：画布显示尺寸恒等于舞台 ⇒ **月球回到画面正中**（任意系统缩放比下）。
- 回归：新增 **DPR=1.25 高 DPI 复跑**（同一套判据，两遍都必须全绿）+ 4 条尺寸口径判据。
- 判据侧修掉三处 DPR 敏感的旧口径（`mainLimbPx` 的 dpr 因子、B7 的整数像素、I29g 的新月重心）。

## v1.4.5 改了什么（2026-09-24 上架）

两条要求：①「追月特写应该是从地球看月球的这个特写，方向就是从地球看向月球」；
②「模拟太阳光线的那个箭头可以不要了，看起来很奇怪」。

### 一、追月特写＝**从地球看月球**（相机钉在地球表面，永远看向月心）

这个功能前后改了三版，三版的口径差别正好是一部"逐步逼近教学意图"的过程：

| 版本 | 机位怎么定 | 结果 |
|---|---|---|
| `v1.1.0` | 按一下＝**一次性把镜头搬到月球**（`focusFeature` 那一路） | 到位那一帧确实对着月球，之后月球继续公转、相机不动 ⇒ 月球立刻跑掉 |
| `v1.3.0` | 每帧按**月球位移增量平移**相机 | 月球钉住了，但**机位方向取的是当时的视线方向** ⇒ 从默认斜视档按下去，等于"顺着看太阳的方向飞到月球旁边"，看到的月相与地球观测者无关 |
| `v1.4.5` | 每帧按**绝对位置重摆**：`ê = normalize(月心 − 地心)`，机位 = `地心 + ê × (R⊕ × 1.05)`，`controls.target = 月心` | 主视图的月相 = **地球观测者看到的月相** |

**为什么 v1.3.0 的"增量平移"在这里根本用不了**：那条机位向量是"地心→月心"的方向，
而地球在绕太阳、月球在绕地球 ⇒ **它每帧都在转**。平移补得了位移，补不了旋转 ——
所以必须每帧重算绝对位置（`position` 与 `target` 一起给），而不是在旧位置上加一个量。

两个几何事实值得写下来，它们解释了"为什么画面看起来这么干净"：

- **地球一个像素都不会出现**：机位在地表**外侧** 1.05 R⊕ = 3.850，而地心到地表的任一点沿视线的
  分量最大也只有 3.667 < 3.850 ⇒ 整个地球都在视平面之后。不用做任何遮挡处理。
- **不会退化**：地月方向永远落在黄道面内，与相机的 `up=(0,1,0)` 不平行，
  所以"看向月心"这一步不会出现相机与视线共线那种奇异姿态。

**交互上做了两处取舍**：

- **旋转、平移全关** —— 这个模式的承诺就是"机位在地球上"，拖走就不成立了（拖动实测
  `ΔdevDeg = 0.00e+0`、`Δ地心距 = 0.00e+0`，跟随也不被打断）。
- **滚轮改吃视场角**（`FOLLOW_FOV = 22°`，范围 `10°~55°`），＝**换镜头／望远镜变焦**，
  而不是 OrbitControls 那种"沿视线推拉相机"（那样相机会离开地球表面）。
  实测：向上滚到 10° 夹住、向下滚到 55° 夹住，月盘屏幕半径 113px → 299px，
  而**机位漂移 1.78e-15**（纯浮点噪声）。退出模式后 fov 恢复 42°。

### 二、站在地球上时必须**把太阳藏起来**（本版最容易误判成 bug 的一条）

太阳的**世界**半径 13.5 是"给 214 远的相机"定的夸张值（真实比例下太阳该是地球的 109 倍，
屏幕上是 4.1 倍）。相机一挪到地球表面（离太阳只剩 42），几何立刻翻脸：

```
太阳角半径   asin(13.5 / 42)  ≈ 18.7°
辉光外缘     atan(48.6 / 42)  ≈ 49°
而 fov 22° 的**半**视场角只有 11°
```

⇒ 整幅画面会被阳光与辉光糊满（新月最惨：月盘本来就只剩一道细弧）。
这是**几何必然，不是渲染缺陷**，所以解法是"在这个模式里把太阳与两条轨道虚线、地月连线一起收起来"，
退出即原样恢复（实测：进入隐藏 4/4 且太阳不可见；退出隐藏 0/4、太阳可见、fov 回 42°）。
右侧「太阳方向」标签也一并隐藏 —— 它指向一个屏幕上根本不存在的东西。

### 三、删掉阳光箭头（需求②）

删掉的是：「日心→地心」箭杆（`CylinderGeometry`）+ 锥头（`ConeGeometry`）那一组、
`setLayers` 里的显隐、每帧的姿态更新，以及那条只给它用的 `X_AXIS` 常量。

⚠ **`sunDirFromEarth` 必须留着**：它同时是月面着色器的平行光方向（白天/黑夜/晨昏线全靠它）。
删了箭头不等于删了这个方向 —— 顺手删掉整颗月亮会变成全黑月。

⚠ **`0xffd34d` 不能当"箭头已删"的指纹**：图层栏「昼夜明暗」那个小色块用的是同一个颜色，
两个版本都在。指纹只能用中文文案串（旧版"黄色的箭头指着阳光照过来的方向"）。

删除型改动**必须另立"禁表"**，因为任何"必须存在"的检查在删掉东西之后都不会红：

- 源码侧：打包指纹的 `GONE_JS` 收录旧文案，`--falsify` 定向破坏逐条验证它会红；
- 屏幕侧：I26 反过来验 —— **同一个探针位置、同一组采样点、同一个时刻**
  （v1.4.0 那里有 20/31 个满亮黄点），现在沿"日心→地心"连线扫 93 个采样点
  （含两侧各 18px）**一个黄点都找不出来**，最亮的一个像素是 `rgb(115,110,102)`（偏灰的暗星/雾）。
  两套判据（本色命中 / "偏黄"广义命中）都为 0，避免"换个颜色就漏过"。

### 四、顺手修掉两处**半截状态**

点站点卡片与点「去三维视图看看」都会把镜头搬到站点头上 ⇒ 引擎里会退出追月特写。
但 React 这份 `following` 状态原先只在切换视角档时才同步，这两条路径漏了。
以前它只影响按钮高亮（不容易瞧出来），v1.4.5 起它还**决定底部提示条与右侧说明的文案**
—— 不同步就是"提示说在追月、镜头其实已经飞到站点头上"。两处都补上了。

### 五、回归基线

| 层 | 判据数 | 结果 |
|---|---|---|
| 数据层（`scripts/moonPhase.test.cjs`） | 87 | 87/0 |
| 真机渲染回归（Electron + 真实产物） | **156** | **156/0** |
| 打包指纹注入式反证（`publish_moon.py --falsify`） | 336 | 336/336 |

真机这一版从 154 条涨到 156 条：新增 I29 系列六条（机位在地球上 / 连推 6 次仍钉住 /
拖动不改机位 / 滚轮换镜头 / 藏太阳与退出恢复 / 负对照 7387.5px 证明"不动"不是"没跑"）、

解析值 0.98 / 1.00 / 0.93 vs 近地面最大 −0.01）。

## v1.4.0 改了什么（2026-09-24 上架）

两条要求：①「旋转的时候会有异动，瞬间的卡动」；②「地球的自转有些奇怪，并不符合真实的
自转速度……地球自转速度很快也没有关系，但是一定要足够真实」。

两条其实是**同一个根因**：引擎里只有一个时间变量，而且它是个**循环量**。

### 一、"瞬间的卡动"：拿循环量当线性时间用

旧代码全程只有一个 `currentAge`（月龄，0..朔望月 29.53 天，到点回卷）。月相几何用它是对的
—— 月相本来就是循环的 —— 但**地球公转也吃它**：

| 量 | 旧实现（吃回卷的月龄） | v1.4.0（吃单调天数） |
|---|---|---|
| 地球公转角 | `π + 360°×月龄/365.25` ⇒ 回卷时**倒跳 29.1°** | `π + 360°×累计天数/365.25`，单调 |
| 那一帧地球的世界位移 | **23.03 单位**（正常帧 0.084，**279 倍**） | 0.2124（正常帧 0.068，3.1×） |
| 那一帧屏幕上的跳变 | 230px | ≤3px |

真机探针（逐帧采 `orbitState()`）在旧产物上抓到的就是这个：自动推进约 11 秒跨一次朔望月
边界，边界那一帧地球"瞬间"挪出去一大截。用户说的「旋转的时候有异动，瞬间的卡动」描述得非常准。

**修法：把时间基拆开。** 引擎里新增单调的 `currentDays`（可无限增长、也可为负）：

- 月相几何（月球位置/姿态、太阳直射点）吃 `normalizeAge(days)` —— 仍是 0..T 的循环量；
- 地球的**公转与自转只吃 `days`**，不再回卷。

月龄滑杆的语义也要迁移：用户拖到"上弦月"时落到**哪一天**？答案是**离当前时刻最近的**
那个上弦月（`nearestPhaseDays(monthAge, currentDays)`）—— 否则往回拖一年，地球会绕着太阳
倒转一圈，画面莫名其妙。

判据 **I30** 直接量这件事（改前红、改后绿）：自动推进跨边界那一段逐帧采样，最大位移
**23.02 / 249×** → **0.2124 / 3.1×**。3.1× 这个残量是**正常**的：`dt` 被 clamp 到 0.1s
⇒ 一帧最多走 2.5 倍于平均步长，加上采样抖动就到 3.1。

### 二、"自转不真实"：从"放慢 29.5 倍"改成恒星日

v1.2.0 为了让月相变化看得清，把地球自转**故意放慢**成"一个朔望月转一圈"（慢 29.5 倍），
界面文案也明写了。v1.4.0 按用户要求改成真实速度：

```
SIDEREAL_PER_DAY = 366.25 / 365.25 = 1.002738   // 一天自转几圈（恒星日）
earthSpinAngle(days) = 2π · days · SIDEREAL_PER_DAY
```

为什么是 366.25 而不是 365.25：地球一年里**相对恒星**转了 366.25 圈、**相对太阳**转了 365.25 圈
—— 多出来的那一圈正好抵消掉公转。所以相对"地球→太阳"这条线，一天**恰好一圈**，
这正是"一天 24 小时"的来历。界面文案把这件事说透了（"多出来的那一点，就是恒星日
23 时 56 分与太阳日 24 小时的差"）。

判据 **I9c** 正面核公式：`earthYaw 增量 − 初始偏置 = 2π×天数×1.002738`，**偏差 0.00e+0 rad**；
**I27** 再用像素证据独立复核"一天一圈"：拨 0.5 天，盘面平均亮度差 **27.7**（换了半张脸）；
拨 1.0 天，差 **2.9**（回到原面）。两个方向都要 —— 只写"变了"的话，把自转调快 10 倍也照样绿。

### 三、修好之后的连锁反应（四处，都不在原始需求里）

"地球真的开始公转"一旦成立，几处旧假设立刻不成立：

1. **取景必须与地球位置无关。** 旧 `orbitFitPoints()` 按"此刻的地月系"收紧 —— 那时地球不动
   所以没问题；现在地球要绕一整圈，收紧一次就会**出画**。换成**包络圈**
   `ORBIT_FIT_R = 46 + 15 + 1.15 = 62.15`（与地球走到哪儿无关），相机从约 60 退到 **214**。
   代价是三天体在屏幕上缩小到约 1/2.85 ⇒ 太阳世界半径 **5 → 13.5** 补回来
   （屏幕 47.6px，仍是地球的 4.1 倍）。`ORBIT_MAX_DIST` 跟着改成 `ORBIT_FIT_R × 4.5`。
2. **装饰尺寸要同步放大。** 箭杆粗细、虚线间隔这些"按世界单位写死"的量，退远后会掉到 1px
   以下。新增 `ORBIT_DECO = SUN_RADIUS / 5 = 2.7` 统一缩放它们（**不缩放天体半径** ——
   地球/月球的真实比例 3.667 是钉死的）。箭杆另外从 `0.1` 加粗到 `0.16 × ORBIT_DECO`：
   加粗前它只有 1.9px 宽，采样点半像素偏移就会踩在抗锯齿边缘上（判据读到本色的一半）。
3. **俯视图的朝向要每帧跟踪。** 旧口径靠"新月时地球恰好在 −X"这条约定凑出"太阳在地球左侧"，
   地球真走起来就不成立了。改成 `camera.up = (−sin ψ, 0, −cos ψ)`（ψ = 地球公转角）⇒
   屏幕右**永远**是"地球的外向方向"。`topViewLocked` + `syncTopView()` 每帧同步，
   学生一拖动就解锁（交回 OrbitControls）。
4. **判据必须自己摆到目标时刻。** 引擎变成"有状态"之后，"像素判据靠前一个用例碰巧停在那一帧"
   就不成立了：地球走到轨道近侧/远侧时，相机看到的是它的**黑夜面**（这是位相的真实几何，
   不是渲染 bug）—— I10/I12 因此读到"地球=4、背景=9"而假红。修法是给调试接口加
   `setDaysRaw(days)`，判据先把自己摆到"相机看到白天"的那一天再测。

## v1.3.0 改了什么（2026-09-24 上架）

两条要求：① 「视角」栏下面的按钮**大小不一致**；② 「日地月系统」里的**追月视角很奇怪**
—— 自动运动时"闪一下就走了"，不能把视角一直保持在月球上。

### 一、按钮不齐：根因是"边框长在容器上"

v1.2.0 统一过按钮尺寸（字号 12.5px、内边距 8px 0），但漏了一层：**边框长在谁身上**。

| 按钮 | v1.2.0 实测 | 差异来源 |
|---|---|---|
| 月球特写 / 日地月系统 | 83×**34**，字重 900 | 没有自己的上下边框（边框长在容器 `.mode-switch` 上） |
| 斜视全景 / 俯视黄道面 / 复位视角 / 追月特写 | 81×**38**，字重 800 | 自带 2px 边框 |

于是**选中态的深色块比旁边的按钮矮 4px、窄 2px**，字重也不一样 —— 并排看就是不齐。
v1.2.0 的判据当时把这 4px **"接受"掉了**：它比的是"档位**行**总高（38）vs 视角**按钮**高（38）"，
看着一样 ⇒ 自动判据全绿，而用户一眼就看了出来。

修法：**容器不再当外框**。`.mode-switch` 去掉 `border` 与 `background`
（留着 background 会让两个按钮之间的 8px 缺口露一条浅色底），
`.mode-switch button` 自己带上 `border:2px solid #2b2620` 与 `background:var(--paper-dim)`，
字重 900→**800**（与其他按钮一致）。六个按钮现在逐项相等的 **81×38**。

判据 **I28 随之收紧**：直接比**按钮自己**的 rect，六项宽高全部相等（不再比"容器 vs 按钮"）。
红绿对照：改前 I28 红（`月球特写 83×34 / 日地月系统 83×34 / 斜视全景 81×38 …`），
改后绿（六个全 `81×38`）。包指纹侧加了一条**双向**成对判据（档位按钮必须自带边框 ＋
容器不许再有 border/background），两个方向各注入一次反证，都如期变红。

### 二、追月特写 = 持续跟随，不是"飞过去一次"

旧实现是**一次性**把镜头搬到月球（复用 `focusFeature` 那条路）：到位那一帧确实对着月球，
但月球在公转（自动播放/拖滑杆时每帧都在动）、相机不动 ⇒ 下一帧月球就跑掉了。
用户描述得极准：「闪一下就走了」。

改成**持续跟随**，四条设计决定：

- **每帧平移**：在 `controls.update()` **之前**，把相机与 `controls.target` 一起平移
  "月球这一帧走过的位移"。用**增量**而不是"每帧重算偏移再赋值"——
  后者会把 OrbitControls 阻尼释放中的中间态一次次抹平，拖动的手感会变硬。
- **跟着当前视线飞过去**：机位方向取"按下按钮那一刻的视线方向"，不写死角度。学生一般是先看
  系统全貌、再按追月，顺着当前视角过去最不容易迷失方向；距离沿用 4.6（与"点站点定位"同一档）。
- **跟随中拖动不打断跟随**：那是"绕着月球换一个角度看"，偏移量下一帧被读走。
  这一点很关键 —— 跟随期间"拖不动"会让学生以为界面卡死了。
- **退出只有两条路**：再按一次「追月特写」（按钮变成带选中态的开关），
  或按别的视角按钮/切模式。退出统一放在引擎的 `setView` / `focusFeature` 里 ——
  任何"重新取景"的动作都会经过它们，React 侧只同步按钮态。

判据 **I29 写成两半方向相反**：

| 判据 | 口径 | 实测 |
|---|---|---|
| I29 | 跟随中连推 6 次月龄，月球投影每次都在画布中心 12px 内 | 最大偏移 **0.0px**（月球屏幕半径 135px） |
| I29b | 跟随中拖动后仍在中心、`following()` 仍为 true | 偏移 0.0px、following=true |
| I29c | **负对照**：关掉跟随后同样推进，月球必须明显跑掉 | 最大偏移 **10559px** |

只写 I29 是不够的：换成"月球本来就不动"的实现它照样绿；I29c 才是"这条判据真的在量跟随"
的证据。红绿对照：旧产物下 I29 红，最大偏移 224px，偏移序列 224/179/171/174/136/188 ——
月球在画面里"飘来飘去"，正是学生看到的现象。

## v1.2.0 改了什么（2026-09-24 上架）

五条要求：① 星空背景改成**贴图**，别用三维星点（拉远会露馅）；② 系统视角加上**地球自转和公转**，要符合科学；③ 太阳**再远一点、体积更大**；④ 太阳光别用一堆线段模拟，**有一个方向的体现即可**；⑤ 两个模式的**按钮大小保持一致**。

### 一、星空 = 一张贴图，不是 1400 颗星点

旧实现把 1400 颗星撒在**半径 60 的球面**上（`THREE.Points`）。v1.1.0 把相机上限放开到
156 之后这就成了定时炸弹：星点球壳比一些机位还近，拉远看星星会**缩成一团**、球壳边缘可见
—— 用户说的"拉的很远就会露馅"就是它。

修法：换成 `scene.background` 的**等距柱状贴图**（2048×1024 canvas，固定种子 LCG 生成），
挂 `EquirectangularReflectionMapping`。背景在 three 里是**无穷远**的，相机退到哪都不变形。
两个副作用都处理了：

- 贴图比纯色背景亮，`I10`（地球 vs 深空对比度）的地/背景读数从 37/11.6 变 37/13 ⇒
  贴图底色调暗、银河带减淡，阈值写明理由后放到 +20（默认月龄地球朝相机的是太平洋洋面，天然偏暗）；
- 星色**全部偏暖**（蓝分量 ≤ 红 +18）—— 真机回归 `H8` 的 `countBluish` 靠"场景里没有偏蓝元素"
  判经纬网，冷色星会把它污染成假红。

小窗也要干净：`renderBoth()` 渲染小窗前临时 `scene.background = null`，渲完还原
（`I25` 钉住"图层开关切的确实是这张贴图本身"）。

### 二、日心三球仪：地球公转 + 自转，一套物理推到底

这是 v1.2.0 最大的改动。v1.0.0/v1.1.0 的系统视角是**地心布局**（地球钉在原点、太阳固定在 +X）
—— 月球绕地球转是对的，但地球自己不动，不科学。v1.2.0 改成**日心布局**：

- **太阳在原点**；地球沿半径 46 的圆**公转**（`earthOrbitAngle = π + 360°×月龄/365.25`，
  一年一圈；约定新月时地球在 −X，默认月龄（上弦）地球正好在远侧、亮面朝相机）；
- **地球自转**：`earthSpinAngle = 360°×月龄/T`，一个朔望月转一圈 —— 放慢了 29.5 倍，
  界面文案明写（真实的一天一圈，播起来大陆会闪成一片）；
- **月球照旧绕地球**，但整个地月系统要跟着地球搬：地月**本地系**（地球在原点、太阳在 +X）
  的全部推导原样保留，只是整体旋转一个**搬运角 β = 公转角 + 180°**（让本地 +X 始终对准
  "地球→太阳"），月球世界位置 = 地球位置 + R_y(β)·本地轨道位置，世界姿态角 = β + 本地姿态角；
- **平行光口径统一**：地球着色器与月球着色器共用**同一个**世界系太阳方向
  `sunDirFromEarth`（= 地球→太阳单位向量，随公转缓慢转向，一天 0.07°）——
  与右栏"受照比例 = (1+cos 相位角)/2"的平行光公式严格一致，不再有"恒 +X"的特例。

数据层新增 8 条断言（轨道在黄道面/半径恒定/与月球同向/一朔望月 29.1°/β 定义/自转周期/
三球仪端到端：新月在日地之间、满月地球在日地之间），真机回归新增 `I9b`（地球公转位置逐点
对独立复算）、`I9c`（自转增量）、`I22`（太阳投影在画布正中）等。

**第一轮回归抓到的真 bug：阳光箭头指反了。** 箭头几何用的四元数写成
`setFromUnitVectors(X, sunDirFromEarth)` —— 那是**着色器口径**（地球→太阳，指向光源），
而箭头画的是**光的传播方向**（太阳→地球），两者正好差一个符号。截图上箭头背对地球，
一眼假；`negate()` 修正后由 `I26`（连线 34% 处的黄色像素 + 指向地球一侧）钉住。

### 三、太阳更远更大 + 一支箭头代替 9 条线束

每张有图注与署名）—— 抽样会漏掉"某一张 404 退回占位图"，而那正是最容易出的错。

### 二、比例：天体大小真实、距离压缩、太阳额外缩小

这三个量**不可能同时按真实比例画进一幅图**——真实地月距离是地球半径的 60 倍，
真按比例画，月球在屏幕上只剩两个像素。所以口径定为：

| 量 | 场景值 | 相对真实 |
|---|---|---|
| 地球半径 / 月球半径 | 3.667 | **严格真实**（6371 / 1737.4；v1.0.0 是 1.35） |
| 月球轨道半径 | 15（≈4.1 个地球半径） | 压缩 14.8 倍（真实 60.3 个地球半径） |
| 地日距离 | 36（=2.4×地月距离） | 压缩约 2390 倍 |
| 太阳半径 | 1.7 | 缩小约 236 倍（唯一不按真实比例的天体） |

数值全部住在 `moonPhase.ts` 的 `ORBIT_SCENE`（数据层真相源），界面文案从常量**算出来**
（"天体大小按真实比例 —— 地球直径是月球的 3.7 倍。但距离压缩了约 15 倍、太阳也画小了……"），
不手写；三个压缩倍数也直接显示在界面上 —— 比假装它是真的诚实。
判据 `I17` 量**世界半径比**（3.666974，与相机、月相都无关），`I17b` 再证屏幕比确实是
这个世界比按透视折算的（不是另写了一份尺寸）；期望值**从 NASA 真实数据自己算**
（6371/1737.4），不写死 3.667 —— 否则"独立复算"退化成抄源码。

### 三、机位是量出来的，不是随手给的

比例一拉大，"三个天体都看得见、地球是被照亮的、新月不贴着地球"三个要求开始打架：

- 太阳的横向偏移 ∝ `num`（相机方向与日地连线的偏离程度）—— `num` 小才能取景近、天体大；
- 但地球亮面比例 = `(1 + u.x)/2` —— `u.x` 必须明显为正，否则学生看到的是一颗黑球
  （实测 `u.x=−0.499` 时亮面只有 25%，判据 I10/I12 直接红）；
- `num` 太小，新月又会贴住地球。

当前 `(0.82, 0.43, −0.37)` 是三者的折中：亮面 91%、取景 1.93×地日距离、新月横向间距 ~81px。
几组候选的实测对比都写进了 `ORBIT_CAM_DIR` 的注释，防止后人"随手翻个方向"。

**取景上限必须由场景尺度算出来**（`ORBIT_MAX_DIST = 4.5×SUN_DIST`）：v1.0.0 写死 46，
尺度一拉大取景被它夹住、太阳直接出画 —— 而"轨道半径/姿态角/太阳方向"那些数学判据量的
都是世界量，照样全绿。识别信号：`camDist` 恰好等于上限，一个"太整"的数（`I21b` 钉住它）。

**"在画布里" ≠ "看得见"**：本版第一次跑就抓到太阳投影在 x=62、而左栏占到 226，
`onScreen` 照样绿。新增 `I3b`：三个天体的横向位置都必须落在左右两栏之间的可用竖带里。

### 一、两个视角不是两套代码，是同一套物理的两种说法

这是本版唯一需要"想清楚"的地方，也是后面所有功能的地基。

体固坐标系不变：**+Z 恒指向地球**（潮汐锁定）、+X 是月面东经、+Y 是北极。于是太阳在
**体固系**里的方向恒为 `(sin λ, 0, cos λ)`、`λ = 180° − 360°×月龄/T` —— 两个视角都一样，
因为"月面上现在哪儿是白天"本来就只取决于月龄。两个视角只是在**世界系**里换了个讲法：

| 视角 | 月球的世界位置 | 月球的世界姿态 | 世界太阳方向 |
|---|---|---|---|
| 月球特写 | `(0,0,0)` | 单位阵（体固系＝世界系） | `(sin λ, 0, cos λ)` |
| 日地月系统 | `r(cos φ, 0, −sin φ)` | `R_y(φ − 90°)` | 恒为 `(1, 0, 0)` |

其中 `φ = 360°×月龄/T` 是公转方位角（月龄 0 ＝ 新月 ＝ 月球跑到日地之间）。
`θ = φ − 90°` 不是拟合出来的，是**解**出来的：世界系里"月球→地球"是 `(−cos φ, 0, sin φ)`，
它必须等于体固系的 +Z；在"+Y 仍朝北"的前提下绕 Y 的旋转由这一条就定死了 ⇒ 唯一解。

**这条唯一解自检真的会红**：把 `θ` 写成 `−φ − 90°`（符号写反），渲染图上看不出任何异常
（月球一样绕地球转、一样有一面朝着地球），但月相会**整体反相**（新月变满月）。
实测注入：数据层单测 4 条断言同时红，真机回归 `I5`（姿态角偏 3.14 rad）、
`I6b`（三方互证偏 2.00）、`J4`（小窗亮面重心从 +0.294 翻成 −0.294）一起红。

**小窗相机挂成月球组的子节点**，是整个切换方案的关键一步：「从地球看月球」＝ 站在月球的
**局部 +Z** 看回来。挂成子节点后，相机的世界变换 = 月球的世界变换 × 局部变换，
**两个视角下小窗看到的是同一件事，一行跟随代码都不用写**。
前提是 `renderer.render(scene, camera)` 的相机必须 `parent !== null`，否则 three 会自己
`updateMatrixWorld` —— 所以这里**不能**写 `phaseCamera.lookAt(0,0,0)`。

### 二、屏幕朝向：让学生能把上面那张图直接抄到下面那张图

新月也在左侧、公转在屏幕上是**逆时针** —— 与右栏「月相成因」示意图逐项对上（`I15`/`I16`）。

而三维画面本身依然"看着正常"。

## v0.0.1 改了什么（2026-09-24 上架）

首版。四条要求：① 真实月球贴图的三维月球，可自由旋转缩放，能切换时间点看月面变化，

### 一、月相不是"贴图动画"，是从一个角度算出来的

全游戏的**唯一真相源**是 `src/moonPhase.ts`（纯函数，不依赖 three 与 React，Node 可直接跑）：

| 量 | 口径 |
|---|---|
| 朔望月 | `T = 29.53059` 天 |
| 太阳直射月面经度 | `λ(月龄) = 180° − 360°·月龄/T` |
| 太阳方向 | `(sin λ, 0, cos λ)`（体固系：**+Z 朝地球**、+X 为东经、+Y 为北极） |
| 相位角 | `\|λ\|` |
| 受照比例 | `k = (1 + cos 相位角) / 2` |

**潮汐锁定 ⇒ 近地面中心永远朝地球**，所以用"动太阳、不动月球"的地球中心模型：
`mesh.rotation.y = -π/2` 把贴图 u=0.5 从 +X 搬到 +Z，同时让东经落在屏幕右侧
（与天文照片"北在上、东在右"一致）。

### 二、两个只能靠实测定下来的口径

**① 小窗相机必须是正交，不能是透视。**
`k=(1+cos 相位角)/2` 是**正交投影**下的面积结果。第一版用透视相机，
真机逐像素数出来蛾眉月受照 **0.085**，公式是 **0.146** —— 差 6 个百分点。
根因是透视让月盘边缘的可见面积被多算。改成 `OrthographicCamera`（视景体半高 1.2，
月盘占半高 83.3%）后实测 **0.150**。物理上也本该正交：地月距离 38 万 km，视线几乎是平行光。

**② 判"亮面在左还是右"不能用"左右半边各自数比例"。**
盈凸月（k=0.85）左半边本来就有大量受光像素，左右相减最多到 0.7，判不出亮面在哪边。
改用**受光像素的横向重心**，与解析解 `x̄ = 4(1−cos λ)/(3π)` 比（6 个月龄覆盖
盈/亏 × 蛾眉/弦/凸，全在 ±0.05 内）。这个口径对所有相位都成立，且越细的月牙越贴近 ±1。

### 三、上架前真机抓到并修掉的缺陷：标注框装不住文字

**症状**：月面地名标注的框下边线**从字中间穿过**，字的下半截溢出到月面照片上。
肉眼一眼可见，但 55 项自动判据**全绿**。

**根因**：`layoutLabels()` 里写的是 `display = "block"`，而 `.moon-label` 的排版是靠
**flex** 把「色块 `<i>` + 文字 `<span>`」并排塞进 17px 高的框里。`block` 让色块独占一行、
文字被挤到第二行 ⇒ 10px 图标 + 14px 行高 = **24px 的内容塞进 14px 的框**。

**为什么自动判据没拦住**：`F2`（两两不相交）与 `F3`（落在画布内）量的都是
`getBoundingClientRect()`，即**框自己的 border-box** —— **溢出到框外的内容不算在内**。

**修法与新增判据**：`display="flex"`；并补一条 `F4b`，改量**三类冗余证据**：
① `scrollHeight/scrollWidth` 是否超出 client 盒；② 子元素矩形并集是否落在 padding 盒内；
③ 文字盒高度是否装得下 `line-height`。反证：缺陷版本下 `F4b` 是**唯一**的红
（8 个框全是 `[block]`、滚动溢出 7px、子元素越界 7px），F2/F3 照样绿 ——
这就是"只量框"拦不住的那一类。

### 六、已知局限

- 月相小窗的滚轮缩放在**回放脚本里**测不出：OrbitControls 的
  `onMouseWheel` 第一行是 `state !== NONE 就 return`，而 Electron 的
  `sendInputEvent` 合成鼠标事件时**指针捕获不生效** —— `pointerdown` 落在 canvas，
  `pointerup` 却落在光标位置的覆盖层元素上（实测 `target=SPAN`），于是 `state` 卡在
  `ROTATE`、滚轮整条哑掉。**这注入器的局限，不是产品缺陷**（真机 pointerup 一定投给
  捕获元素），所以滚轮判据排在任何拖动之前，并另立 `H3b` 把这一点单独钉住：
  拖动后滚轮哑了 → 补发那一下 pointerup → 缩放立刻复活。
- 触摸设备下 `pointercancel`（而非 `pointerup`）会让 `state` 卡住、缩放哑掉。
  本游戏跑在桌面 Electron 壳里，未做处理。
