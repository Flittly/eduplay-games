# 初高中生游戏设计与开发 · 项目方向选题指南

> **一句话结论**
> 让中学生做游戏，成败不取决于"想法多酷"，而取决于**能不能做完 + 30 秒内好不好玩**。
> 选方向的第一原则是：**先选一个"规则简单、内容量小、反馈即时"的机制，把「开始 → 玩 → 失败 → 重来 → 通关 → 分享」这条完整链路跑通**，再往上加系统。

---

## 0. 先建立判断标准：中学生项目为什么会烂尾

三个真实原因，按出现频率排序：

| 失败原因 | 典型表现 | 正确做法 |
|---|---|---|
| **内容量预估错**（占大多数） | 想做 20 关 / 50 种作物 / 8 个章节，做到第 3 关做不动了 | 先做 **3 关 / 5 个要素**，但每一个都打磨到位 |
| **美术资产做不完** | 一个人画不完 200 张素材，最后用占位图交差 | 几何图形 / 像素风 / 单色 + 粒子特效；靠**手感**取胜，不靠画面 |
| **用系统补救不好玩的核心** | 核心循环不好玩 → 加装备、加升级、加剧情 → 还是不好玩 → 项目死掉 | 核心 30 秒不好玩，就**换机制**，别加系统 |

**给学生的一句话**：*"做出一个能完整玩 5 分钟的游戏，胜过做出一个永远做不完的宏大游戏。"*

**给老师的一句话**：*把"砍功能"当成一项要教的能力。80% 的指导时间应该花在"帮学生砍掉一半想法"上。*

---

## 一档 · 入门（1～2 周出可玩原型）

规则一眼看懂、技术栈单一、无需美术积累。**第一次做游戏一定要从这里开始。**

### 1. 网格逻辑解谜

| 项 | 内容 |
|---|---|
| **核心玩法** | 在方格 / 网格上执行有限操作（推动、旋转、连接、涂色），用最少步数达成目标状态 |
| **代表形态** | 推箱子、数独变体、管道连接、华容道、一笔画、光线反射 |
| **认知匹配** | 初一至高一。11 岁起进入形式运算阶段，**"确定规则下的状态推演"正好是这阶段的强项**；失败成本极低、成就感即时，特别适合注意力容易被打击的学生 |
| **实现难度** | ★★☆☆☆（逻辑密度高，但技术极简） |
| **技术栈** | Canvas 2D 或纯 DOM + CSS Grid；无需引擎 |
| **单机/多人** | 单机为主；加"最少步数排行榜"即成轻度社交 |

**设计要点**
1. **先写规则引擎，再画界面。** 把"一个状态 + 一次操作 → 新状态"写成**纯函数** `step(state, move) => state`，可以脱离画面用脚本测试，这是解谜类最重要的一步架构。
2. **关卡用倒推法设计。** 从目标状态反向随机走 N 步，得到的就是"最少 N 步"的关卡。批量生成 100 个，再人工挑 10 个好的。
3. **必须有撤销。** 撤销键、步数回退、关卡内重开——解谜游戏的体验生死线，没有它玩家会立刻流失。
4. **做 10 关 + 一个关卡编辑器，胜过做 50 关。**

**最容易翻车**：规则用文字描述不清（"这个方块到底能不能推过拐角？"）→ 用**带图示的 20 秒教学关**代替说明文字。

### 2. 2D 平台跳跃 / 跑酷

| 项 | 内容 |
|---|---|
| **核心玩法** | 操作角色在关卡中跳跃、躲避、到达终点；难度来自时机与路线 |
| **代表形态** | 横版闯关、无尽跑酷、攀爬跳跃、躲避障碍 |
| **认知匹配** | 初一至高三通用。这个年龄是**反应速度的峰值期**，且空间推理能力已经成熟；成就感来自"我练会了" |
| **实现难度** | ★★☆☆☆ |
| **技术栈** | Canvas 2D + 手写 AABB 碰撞（推荐，一学就会）；或 Phaser / Godot |
| **单机/多人** | 单机；排行榜（最快通关 / 最少死亡） |

**设计要点**
1. **手感三件套比美术重要十倍：**
   - **土狼时间（coyote time）**：离开平台后约 0.1s 内仍可起跳
   - **跳跃缓冲（jump buffer）**：落地前约 0.1s 按下跳跃，落地瞬间自动触发
   - **可变跳跃高度**：松开按键立即减速上升，轻按=小跳，长按=高跳
2. **用固定时间步（fixed timestep）更新物理**，不要用帧率相关写法，否则不同电脑上跳得不一样远。
3. **难度曲线公式**：教学 → 变奏（换个方向）→ 组合（两个机制叠加）→ 考验（限时 / 追逐）。
4. **陷阱**：不要"一击必死 + 从关卡开头重来"，必须放检查点。

**最容易翻车**：一开始就追求"角色的动画帧"——先用一个圆或方块把物理调到舒服，美术最后再说。

### 3. 文字推理 / 交互叙事

| 项 | 内容 |
|---|---|
| **核心玩法** | 玩家阅读场景与对白，收集线索，做出判断，触发不同结局 |
| **代表形态** | 悬疑解谜（剧本杀单机版）、校园故事、历史情境模拟、科学伦理抉择 |
| **认知匹配** | 初二至高三。逻辑推理 + 共情 + 价值判断同步发展；**极适合语文学科跨学科项目**（把课文改成案件） |
| **实现难度** | ★☆☆☆☆（技术最简单，但写作最花功夫） |
| **技术栈** | JSON 数据驱动 + React / 纯 HTML；剧情写在数据里，不写在代码里 |
| **单机/多人** | 单机；可做**异步多人**——每人提交一份推理，互相评判 |

**设计要点**
1. **结构用"状态变量 + 条件显示"，不要写死分支树。**
   ```js
   // 好：线性增长
   { text: "你打开抽屉。", if: "has_key === false",
     options: [{ label: "拿走钥匙", set: { has_key: true } }] }
   // 坏：每个选择都分叉 → 3 层就爆炸成 27 条线
   ```
2. **错误选项也必须有反馈**，不能点了没反应——这是新手最容易忽略的体验断点。
3. **控量**：做 1 个场景 + 3 个结局，别想做 6 章。文字量永远比你以为的多三倍。

**最容易翻车**：把所有内容写死在代码里，改一句台词要动源码。

## 二档 · 进阶（3～6 周，需要状态管理与时间轴思维）

出现"实时系统"，需要理解帧循环、时间、状态机。

### 4. 节奏音乐游戏

| 项 | 内容 |
|---|---|
| **核心玩法** | 音符落在判定线上时按键，按准确度得分连击 |
| **代表形态** | 下落式音游、按键打击、跑动节奏关卡 |
| **认知匹配** | 初中至高中。节奏感知 + 专注力；音乐本身就是强动机，学生愿意主动做内容 |
| **实现难度** | ★★★☆☆ |
| **技术栈** | Web Audio API + Canvas |
| **单机/多人** | 单机；双人同屏交替或分数对比 |

**设计要点**
1. **判定基准必须是音频时间轴，不能用 `setTimeout`。** `setTimeout` 会累积误差，玩到后面"越打越不对"，这是音游最经典的新手坑。用 `audioContext.currentTime` 做唯一时间源。
2. **判定窗口建议**：Perfect ±50ms / Good ±100ms / Miss。
3. **谱面手写 JSON**（时间戳 + 轨道号），不要试图做自动生成。
4. **打击感三件套**：音效 + 粒子 + 屏幕微震。缺一个都会"软"。
5. **版权**：用免费授权音乐，或让会乐器的学生自己录。

### 5. 物理沙盒 / 弹射建造

| 项 | 内容 |
|---|---|
| **核心玩法** | 用有限零件搭建结构或发射物体，靠物理规律达成目标 |
| **代表形态** | 桥梁建造、过山车、弹球台、塔吊平衡、抛体打靶 |
| **认知匹配** | 初二至高三。直觉物理 + 空间想象；高中生可进一步延伸到向量、力矩、能量守恒——**天然的理科跨学科载体** |
| **实现难度** | ★★★☆☆ |
| **技术栈** | Matter.js / Planck.js（2D 物理引擎）；**不要自己写物理** |
| **单机/多人** | 单机；"我的解法分享码"（把搭建方案编码成字符串分享）是极省事的异步社交 |

**设计要点**
1. **用现成引擎。** 自己写物理会陷入调参地狱（穿模、抖动、能量爆炸）。
2. **给沙盒加目标。** 完全自由的物理玩具只能玩 2 分钟；必须给出"用最少零件让小车过河"这类约束，才有游戏性。
3. **允许反复试错**：随时"重置"、随时"撤销上一块零件"。
4. **物理类必加"慢放"**，方便学生观察和调试。

---

### 6. 卡牌构筑 / 回合制对战

| 项 | 内容 |
|---|---|
| **核心玩法** | 从卡池中构筑卡组，回合内出牌，用数值与组合击败对手 |
| **代表形态** | 卡牌对战、塔防式回合战、资源博弈 |
| **认知匹配** | 高一至高三。形式运算成熟期，能理解**期望值、概率、组合爆炸**；这个年龄对"数值设计"热情极高 |
| **实现难度** | ★★★★☆（逻辑不难，**平衡难**） |
| **技术栈** | React + 数据驱动的 UI；卡牌定义放 CSV / JSON |
| **单机/多人** | 单机 vs AI → 双人同屏 → 末期再做联机 |

**设计要点**
1. **先用表格设计卡牌**（Excel / CSV：名称、费用、效果、tag），代码只负责解释数据。改平衡不需要改代码。
2. **核心是"选择的权衡"**：每张强力卡都要有代价（耗资源 / 弃牌 / 自伤），否则就是单选题。
3. **平衡靠统计，不靠感觉。** 写一个自动对战脚本跑 1000 局，看胜率表和出场率表。
4. **AI 用"贪心 + 权重打分"就够了**，不要碰机器学习。
5. **先做 20 张卡的可玩版本**，验证好玩再加。

## 三档 · 系统（6～10 周，需要系统思维与数值能力）

核心是"设计一个会自我运转的循环"。

### 7. 模拟经营 / 资源管理

| 项 | 内容 |
|---|---|
| **核心玩法** | 管理资源，投入生产，获得收益，扩张规模 |
| **代表形态** | 农场、小店、城市、生态缸、太空基地、食堂运营 |
| **认知匹配** | 高中为主；初中需老师帮忙简化。系统思维在 15 岁后明显成熟。**极适合生物 / 地理 / 经济跨学科** |
| **实现难度** | ★★★★☆ |
| **技术栈** | React 状态管理（本质是"给游戏做一张会算数的表"）；数据持久化用 localStorage |
| **单机/多人** | **单机 + 异步多人性价比最高**（好友的农场、送礼、排行榜） |

**设计要点**
1. **先画资源循环图**（钱 → 种子 → 作物 → 钱），确认循环闭合、没有断点、没有无限印钞漏洞。
2. **设计"决策节奏"**：每 30 秒要有一次有意义的取舍。玩家长时间没事干，游戏就死了。
3. **数值用指数增长**（成本 ×1.15 一档，收益 ×1.3 一档），否则后期没有挑战。
4. **控量是生死线**：5 种作物做出**深度**（相克、季节、加工），胜过 30 种作物做**广度**。

---

### 8. 自动战斗 / 轻量 Roguelike

| 项 | 内容 |
|---|---|
| **核心玩法** | 组队、选增益、看自动战斗，考验"构筑（Build）"能力 |
| **代表形态** | 自走棋简化版、爬塔、随机地牢、放置挂机 |
| **认知匹配** | 高中为主。**Tag 组合系统**对抽象思维要求高，但反馈极其爽快 |
| **实现难度** | ★★★★☆ |
| **技术栈** | 纯前端状态机 + 数据表；不需要服务端 |
| **单机/多人** | 单机 + 分享随机种子（异步社交，几乎零成本） |

**设计要点**
1. **核心乐趣在"组合出意想不到的搭配"**，所以一定要有 **tag 系统**（火 / 雷 / 召唤 / 毒），让 3 个 tag 叠加产生质变。
2. **用种子（seed）控制随机**，方便复现、"分享同一个地牢"和定位 bug。
3. **每战胜一次给"3 选 1"**，把随机变成玩家的选择——纯随机会让人觉得不公平。
4. **自动化反而省事**：不做战斗操作，开发量直接减半，可以把精力放在数值上。

## 四档 · 社交（成本最高，收益也最高）

这个年龄段的**同伴认同 > 老师表扬**，多人就是最大的游戏性来源。

### 9. 派对抢答 / 你画我猜（伪联机）

| 项 | 内容 |
|---|---|
| **核心玩法** | 多人同处一局，通过抢答、猜词、投票产生互动 |
| **代表形态** | 知识抢答赛、你画我猜、谁是卧底、词语接龙 |
| **认知匹配** | 初中至高中全覆盖。**竞争欲与表现欲的峰值期**，课堂使用效果最好 |
| **实现难度** | 同屏版 ★★☆☆☆ / 联机版 ★★★☆☆ |
| **技术栈** | 同屏版纯前端；联机版 Node.js + 内存房间对象 + **轮询**即可 |
| **单机/多人** | 这是多人的主场 |

**设计要点**
1. **最简单的路：本地同屏双人**（一台电脑，两人共用键鼠或左右键盘）。**课堂神器，零网络成本。**
2. **联机不要上 WebSocket。** 每 0.5s 轮询一次房状态，能省掉 80% 的复杂度；抢答类游戏对延迟并不敏感。
3. **题库必须可导入**（JSON），这样**老师能直接塞自己学科的题目**——这一条能把项目变成可复用的教学工具。
4. **超时自动跳过**：等房间、掉线处理是最烦的部分，先做"凑不齐人也能玩"。

---

### 10. 实时联机合作 / 竞速

| 项 | 内容 |
|---|---|
| **核心玩法** | 多人同时在线，同步操作，合作通关或竞速对抗 |
| **代表形态** | 双人合作解谜、实时竞速、团队占点 |
| **认知匹配** | 高三 / 有编程基础的学生。需要理解网络、延迟、状态一致性 |
| **实现难度** | ★★★★★ |
| **技术栈** | Node.js + `ws` / socket.io；或现成方案 Colyseus、云服务托管 |
| **单机/多人** | 真多人（需权威服务器） |

**设计要点**
1. **权威服务器**：客户端只上报**输入**，服务器计算结果再广播。否则必然不同步、必然被作弊。
2. **两条技术路线**：
   - **状态同步 + 插值**：服务器每 33ms 广播一次状态，客户端平滑插值。适合自由度高的游戏。
   - **帧同步**：只同步输入，两端各自计算相同结果。适合物理确定性的游戏，流量极小。
3. **降级策略**：延迟高时用"本地预测 + 后期修正"，避免"按了没反应"。
4. **建议路径**：先做 **2 人 + 回合制**的联机（验证房间、重连、状态同步），**再做实时**。
5. **定位**：这是社团 / 进阶项目，需要老师深度陪跑，不要当作常规作业。

## 认知水平对照：初中 vs 高中

| 维度 | 12～14 岁（初中） | 15～18 岁（高中） |
|---|---|---|
| **思维特点** | 形式运算萌芽期，能推演但不能同时管理多个抽象变量 | 形式运算成熟，可处理多变量系统、概率、组合 |
| **适合的机制** | 规则明确的**状态推演**、即时反馈、可视化强 | **系统设计**、数值平衡、资源循环、联机 |
| **不适合的机制** | 抽象数值平衡、多系统耦合 | —— |
| **兴趣驱动** | 玩得爽、被同学看到、排行榜 | 自我表达、深度策略、"我做的东西很专业" |
| **建议项目规模** | 3 ~ 5 关 / 1 个核心机制 | 完整循环 + 3 ~ 5 个系统 |
| **老师介入方式** | 帮着砍功能、把关架构 | 讨论设计与平衡，放手让学生试错 |

**通用兴趣杠杆（不分学段都有效）**
- **即时反馈**：任何操作都要在 100ms 内被看到
- **可直接分享**：一个链接、一串分享码、一张截图，社交传播是最大动力
- **可自定义**：皮肤、名字、关卡、题目——学生愿意为自己创造的东西花时间
- **排行榜与成就**：性价比最高的"轻多人"手段

## 单机与多人：四种形态的成本阶梯

| 形态 | 实现方式 | 成本 | 适用场景 |
|---|---|---|---|
| **① 本地单人** | 纯前端，localStorage 存进度 | 极低 | 所有方向的起点 |
| **② 本地同屏双人** | 键盘左右分区 / 共用鼠标 | 低 | 课堂演示、抢答、对战 |
| **③ 异步多人** | 排行榜、分享码、幽灵回放、互访 | 低 | **性价比之王**——几乎零成本却有社交性 |
| **④ 真联机** | 权威服务器 + 状态同步 | 高 | 进阶项目 |

> **关键洞察**：想加"多人"时，**优先做 ② 和 ③**。
> "排行榜 + 分享码"能以不到 10% 的成本，拿到 70% 的社交满足感。
> 直接上 ④ 的学生项目，绝大多数败在同步 bug 和没人有一台能长期开着的服务器上。

## 落地节奏建议

**7 天暖场（做出"一个能玩的东西"）**
- Day 1–2：选方向，写出**一句话玩法**，画出核心循环图
- Day 3–4：搭出可操作的原型（占位图形，无美术）
- Day 5：加入失败与重开；调手感 / 调难度
- Day 6：3 个关卡或 1 个完整对局
- Day 7：加音效、加排行榜、截图分享

**4 周标准项目**
- 第 1 周：原型 + 核心循环验证（**不好玩就换机制，别硬扛**）
- 第 2 周：内容生产（关卡 / 卡牌 / 题库），用工具批量生成
- 第 3 周：打磨体验（反馈、动画、音效、平衡）
- 第 4 周：社交层（排行榜 / 分享码）+ 展示与复盘

**8 周进阶项目（系统类或联机类）**
- 前 2 周：原型验证；第 3–5 周：系统与数值；第 6–7 周：联机 / 内容扩充；第 8 周：发布与答辩

**验收标准（建议直接作为评分项）**
1. 一个从没玩过的人，**30 秒内能自己搞懂怎么玩**（不需要你讲解）
2. 核心循环能连续运行 **5 分钟不冷场**
3. 失败后有**明确的"再来一次"按钮**，且重来成本 < 10 秒
4. 有一处**可以分享给别人**的东西（分数 / 截图 / 分享码 / 链接）

## 与现有平台的结合建议

本仓库（eduplay-games）已积累 React + Vite + TypeScript + Three.js 的技术栈，以及"知识型教学游戏"的成熟模式。若要把上面的方向落进平台，建议按此优先级：

1. **先做"学生可自制内容"的方向**（3 文字推理、9 派对抢答、1 网格解谜）——因为它们天然是"引擎 + 数据"结构，**平台提供引擎，老师和学生只填 JSON 题库 / 关卡**，一份代码能长出无数节课的内容。
2. **再补"课堂多人"方向**（9 的本地同屏版）——单台教师机就能全班参与，教室硬件门槛最低，投放效果最好。
3. **物理沙盒（5）和卡牌对战（6）** 适合作为社团 / 选修课的进阶项目，有明确的"设计深度"可以持续迭代。
4. **实时联机（10）** 建议暂缓，等有稳定的服务端与运维能力再启动。

> **选型第一原则（再强调一次）**：优先选能变成"**引擎 + 数据**"的方向，而不是只能做一关的方向。
> 前者一次开发能持续产出内容，后者做完就结束了。
