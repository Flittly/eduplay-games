# 山河三消（shanhe_match3）

省级行政区三要素匹配消消乐：集齐同一省份的【轮廓卡 + 简称卡 + 行政中心卡】三张不同要素牌即可消除，三张相同牌、同省缺牌、跨省混搭均不可消除。

- 关卡 1：8 个高频省区，2–3 层堆叠（课前热身）
- 关卡 2：18 个常见省区（含易混淆），3–4 层堆叠（课中巩固）
- 关卡 3：全部 34 个省级行政区，4–5 层堆叠（会考冲刺）
- 卡槽 6 格，满格无组合即失败；所有布局由构造式算法保证存在通关路径
- **消除即复习（v1.0.0）**：每消除一组弹出记忆卡，把该省的【轮廓 + 简称 + 行政中心】三张
  要素卡 + 省份全名再完整重复一遍；弹窗期间计时暂停，不计入用时
- **提示说清「还差什么」（v1.0.0）**：每局提示 ×3（-5 分/次）。提示会在牌面与卡槽之间播报
  「卡槽里已有【黑龙江省】的轮廓、简称，只差省会，高亮这张点它即可消除」这类具体结论，
  并区分「还差的一张现在就能点」与「还差的一张被压住，要先清障」；卡槽只剩 1 格时附带告警
- **悔棋退回上一张（v1.0.0）**：每局 ×3（-2 分/次）。基于局面快照，把上一手精确还原到点它之前
  ——包括「点下去就凑成三要素并消除」的那一手
- **港澳轮廓细化（v1.1.0）**：香港 12 环 / 68 顶点 → **34 环 / 873 顶点**，澳门 2 环 / 8 顶点 →
  **4 环 / 93 顶点**；港澳的牌面轮廓改用不随缩放走的细描边，形状终于辨认得出来
  （详见下面「为什么港澳原来那么粗」）
- 通关整组 +10 分、过关 +20
- 结束后自动归集薄弱省区到学生本地错题档案（localStorage 永久留存）
- 平台对接：`GAME_READY` / `GAME_INIT(roster)` / `GAME_COMPLETE` / `GAME_SESSION_COMPLETE`

## 数据来源与重新生成

`src/data/provinces.json` 与 province-puzzle 同源（2022 省级矢量，Albers 投影）。
**除港澳外，两个游戏的 `d` 字段逐字节相同** —— 改动投影或尺度参数前先想清楚会不会把两边拆散
（复核脚本会拿 province-puzzle 的产物交叉比对）。

```powershell
C:/Python314/python.exe scripts/prepare_data.py --emit

```

## 为什么港澳原来那么粗（v1.1.0）

用户反馈「香港和澳门的轮廓非常粗，需要更加细致的数据」。查下来是**两层问题叠在一起**，
而且**只修任何一层都不够** —— 用一张隔离对照页
（`.workbuddy/tmp/match3verify/host/_shapeproof.html`，A/B/C/D 四格拆开两个因素）才看清楚：

| 红占比（描边墨量 / 形状总量） | A 旧数据+旧描边 | B 只调描边 | C 只调数据 | D 都调（v1.1.0） |
| --- | --- | --- | --- | --- |
| 香港 | 97% | 24% | 98% | **41%** |
| 澳门 | 100% | 100%（只剩 34 px） | 100% | **22%** |

### 第一层：数据被「用坏」了（源数据本身没问题）

港澳原先跟着全省一起走 `simplify(3800 m)` + `round()` 到整数。整张数据只有 1200 单位宽
（1 单位 ≈ 5.3 km），澳门真实跨度 7.1 × 11.9 km —— **取整之后 47 个顶点只落在 4 个不同位置上**。
实测旧产物里澳门的 `d` 就是 `M727,740L727,740L727,740L727,740Z`，**一条零长度的路径**。
所以澳门原来不是「粗」，是**压根没有形状**（对照图里 B 格只剩一条 34 px 的斜线）。

修法是给小面积行政区单独一组参数（`scripts/prepare_data.py` 的 `SMALL_AREA_OVERRIDES`）：
简化容差 120 m / 50 m、最小岛面积降到 0.00001°²（保住离岛）、坐标保留 2 位小数。

面积可信度对照（这一条决定「该不该上网另找数据」）：源数据香港 1110 km²（官方 1114.57，**−0.4%**）、
澳门 35 km²（官方 33.3，+5.1%）；而阿里云 DataV（高德数据）香港 **+15.6%**、澳门 **+59%**，
且澳门只有 84 个顶点（比源数据的 203 还粗）。**所以没有换数据源，修的是参数。**

### 第二层：描边是 viewBox 单位，会跟着要素一起放大

牌面 svg 是拿**该要素自己的 bbox** 当 viewBox 单独缩放显示的，所以
`stroke-width: 2`（viewBox 单位）换算到屏幕上要乘缩放倍数 —— 要素越小描边越粗：

| | bbox | 牌面缩放 | 旧描边 | 形状短边 | 描边 / 形状 |
| --- | --- | --- | --- | --- | --- |
| 澳门 | 1.59 × 2.41 | 27.8 px/单位 | **55.6 px** | 44 px | **126%** |
| 香港 | 12.19 × 10.02 | 5.58 | 11.2 px | 56 px | 20% |
| 上海 | 23 × 27 | 2.48 | 5.0 px | 57 px | 8.7% |
| 北京 | 34 × 38 | 1.76 | 3.5 px | 60 px | 5.9% |

小要素改用 `vector-effect: non-scaling-stroke`（`stroke-width` 按**屏幕像素**解释）。
阈值 `TINY_BBOX = 22`（`src/gameData.ts`）只圈中港澳（2.41 / 12.19），紧接着的上海是 27 ——
间隔很宽。**定阈值前把所有 34 个对象排了一遍序**，因为误伤是静默的
（那个行政区的牌只是描边细了一点），没人会报 bug。排序脚本：`.workbuddy/tmp/smdata/tiny_budget.cjs`。

### 顺带修掉的两个静默问题

- **`bbox` 与 `d` 的精度必须一致**：牌面是拿 bbox 当 viewBox 的，港澳的 `d` 留了 2 位小数，
  bbox 若仍取整，形状就会偏出取景框 —— 澳门偏半格就够露馅（贴着边或被切掉一角）。
- **出处标记说谎**：`provinces.json` 里的 `"version": "0.1.0"` 是手写常量，从游戏 0.1.0
  一路滞后到 1.0.1 都没人发现。改成从 `package.json` 读，发版时改一处就自动跟上。

### 验证

- **数据层**：32 个未改动要素的 `id/name/abbr/capital/bbox/d` **逐字节相同**（32/32），
  且与 province-puzzle 的 `d` **逐字节相同**（34/34）—— 同源的最强证据。
  港澳几何：香港顶点 68 → **873**（12.8×）、周长 82.23 → 140.68、最大环不同坐标 16 → **307**；
  澳门顶点 8 → **93**（11.6×）、周长 2.83 → 10.44（3.7×）、最大环不同坐标 2 → **46**；
  bbox 中心位移 0.63 / 0.36 单位。
- **渲染层**：同一套探针先在**已发布的旧包**（`zips/shanhe_match3-1.0.1.zip`）上跑出 8 项红，
  再在新产物上全绿（11 项）—— 两份 report 都归档在 `.workbuddy/tmp/match3verify/`。
  判据用的是**匹配物理尺度**的量（描边宽 ÷ 形状短边：22.2% → 2.2%、200% → 2.7%），
  不是"截图里像素多了几个"。
- ⚠ **「红占比」不能当"描边粗不粗"的判据**：香港 34 个岛的海岸线极曲折，周长/面积比很高，
  1.1 px 的细描边总面积本来就和填充同量级（实测 41%）。它只在隔离对照页里用来分因素。
- ⚠ 真机牌面是**分层叠放、每局随机**的，目标卡的取景框会被相邻牌盖住一部分
  （同一份旧产物两次跑出「红 434 / 墨 0」与「红 9 / 墨 450」）。所以真机探针只把像素量
  当辅助证据，硬判据放在计算样式与几何量上。

## 构建

```powershell
cd shanhe-match3
npm install
npm run build
```

产物：`dist/web/`，随 `manifest.json` 打包为 `shanhe_match3-1.1.0.zip` 上架。
⚠ 数据变了**必须重新 build** —— 漏掉这一步 zip 照样结构合法、照样装得上、界面上照样有港澳两张卡，
只是画出来还是粗的。`publish_match3.py` 里用**细粒度几何的路径前缀**当指纹把这一步钉住了。
