## 为什么这一版的三维不像以前那么假

v1.0 那版三维是**程序化噪声**堆出来的（`fbm2D`），它的问题不是分辨率，是**没有地貌逻辑**：
噪声山永远只有一层均匀的皱褶，看不出"这里是一条脊、那里是一条被水切出来的谷"。

改成真实 DEM 后，地形自带真实的水系切割与山脊走向 —— 贡嘎山有放射状山脊 + 深切河谷，
珠峰有冰川谷与山群，太白山有连片高山草甸。**真实地形的皱褶感是噪声函数做不出来的。**

## 数据管线（`/` 全离线）

**先分清两个来源** —— 11 个样本里有两种完全不同的来路，改哪一档就走哪一条：

| 档 | 生成器 | 数据的性质 |
| --- | --- | --- |
| 3 个模板地形 | `scripts/gen_templates.cjs`（`npm run gen:templates`） | **解析函数算出来的**（圆锥/圆顶/高斯脊叠加），无随机数 ⇒ 逐字节可复现 |
| 8 个真实样本 | `.workbuddy/tmp/dem-probe/build_dem.py` | 真实 DEM 数据，改山体只需改里面的经纬度与跨度 |

- **真实样本来源**：[AWS Terrain Tiles](https://registry.opendata.aws/terrain-tiles/)（Terrarium 编码），
  免 key、公有领域。解码 `h = R*256 + G + B/256 − 32768`，精度 1/256 m。
- **地面等距重投影**：瓦片本身是 Web Mercator，直接采样会让高纬山体横向拉伸。
  生成时按 `cos(center_lat)` 修正，把 3×3 瓦片重采样成 **256×256 的地面等距网格**
  （x/y 方向每像素对应的实际米数相同）。
- **峰顶自动居中（只对真实样本）**：先在大窗口里搜最高点 → 反算该点的经纬度 →
  以它为中心重新裁窗口。四座山最终峰顶偏移全部为 **0%**（数据见下表）。
  ⚠️ 模板地形**不适用**这条 —— 模板是"整个山体填满图幅"，不是"峰顶居中取景"，
  所以它的最高峰允许偏离图幅中心（回归里对模板单独放了一档更宽的判据）。
- **编码（两档共用）**：整数米 → `Uint16` 小端 → base64，**不做 zlib**。实测压缩率只有 0.767
  （地形数据本来就很紧），却会把解码变成异步（`DecompressionStream`），
  换来异步初始化 + loading 态 + 测试要 `await` —— 省 160 KB 不值这个复杂度。
  每个样本约 172 KB，**11 个共 1.85 MB**，全部内嵌进 bundle，运行时不需要联网。

### 为什么临汾盆地要 60 km（这条重要）

盆地要讲的是**"四周高、中间低"**，取景必须**把盆缘一起框进来**，30 km 框不到周围的
霍山与吕梁山，就退化成一块缓坡，讲不出"盆地"。所以它单独用 60 km。

⚠️ 由此全库有**四种图幅**（模板 20/40 km、真实 30/60 km）。而**渲染网格的跨度是构造时锁死的**，
见「踩过的坑」第 9 条。
**以后再加不同跨度的样本，务必重跑真机回归 E 节**（11 个样本逐一核对
`view3d.debug().terrainSpanM === terrainInfo().spanM`）。

## 「海拔」与「视觉高度」必须分开（本轮最重要的架构决策）

这是两个完全不同的东西，混在一起会立刻产生荒谬读数：

| 参数 | 改什么 | 谁跟着变 |
| --- | --- | --- |
| `elevationOffset`（±2000 m） | **真改海拔** | 面板读数、等高线注记与条数、带谱边界、林线雪线判定，全跟着变 |
| `verticalExaggeration`（×0.5~2.0） | **只改视觉纵轴** | 只有渲染顶点用它；不影响"这座山有多高" |

实现上靠两份数组：

- `field.raw` —— 真实 DEM 的只读副本，**永不改写**，"还原真实地形"的依据
- `field.alt` —— 当前海拔 = `max(0, raw + elevationOffset)`，是面板与所有判据的真实来源

**视觉高度 `visualY(f, alt) = alt × verticalExaggeration` 只在拼渲染顶点时临时算。**
早期若图省事把夸张乘进 `alt`，就会出现"夸张调到 2 倍 → 面板显示贡嘎山 14828 m"的静默错误。

## 底部等高线栏（v2.2.0 起四个页签）

窗口底部固定一栏，四个页签共用同一份数据：

| 页签 | 画什么 |
| --- | --- |
| **平面等高线图** | 自然带淡色底图 + 等高线（计曲线每 5 条加深加粗）+ 计曲线高程注记（垫纸色背景）+ 山脊点 + 河道 + 峰顶红三角 + 指北针 + 比例尺 |
| **等高线清单** | 逐条列出海拔与圈数，点击即高亮；雪线以上的条目带"雪线以上"标签 |
| **垂直剖面图** | 手动点的各段剖面（最多 4 段**四色叠加在同一套坐标轴上对比**）；没有手动段时回落成"山麓→峰顶"参考路径剖面 |
| **地貌图鉴** | 11 个样本的卡片墙：地形类型 / 部位标签 / 海拔范围 / 判据说明，可按**地形类型**与**地形部位**两组标签筛选；模板地形的卡片带一枚**「模板」角标**（教学材料里"哪些是编的"必须一眼可分） |

宽屏时平面图画布右侧还会画出**图廓要素**：自然带图例（含海拔区间）、本图说明
（等高距 / 条数 / 图幅 / 网格 / 当前海拔范围 / 峰顶）、符号例。这不是为了填满空白 ——
这一栏是"矮而宽"（约 1100×230）而地形窗口是正方形，**正方形居中摆放时只占 15% 宽度**，
不补上这些内容就看着像界面没画完。回归里有条像素断言专门守这个（右侧 2/3 非纸色像素 > 2%）。

## 二维投影面，以及它下面那道缝（v2.2.0 加图 · v2.3.0 修缝）

学生要能从"摸得着的山"过渡到"纸上的等高线"，中间必须有座桥。桥就是**垂直投影**：

- 图纸画的是**同一份**高程场（复用 `extractContour` 的折线，**不是**另算一套），
  所以纸上的圈圈和山上的圈圈逐条对得上；
- 四角各一条**竖直引线**从图纸拉到沙盘**底座**（不拉到地表 —— 地表有起伏，
  四条线长短不一反而乱；拉到同一水平面读起来才是"这块沙盘从下面那张图纸长出来"）；
- 沙盘悬在图纸上方留一道缝，贴上去就分不清哪条是山、哪条是线了。

贴图是**调用方画好交给 `terrain.ts` 的**（`setProjection({ draw })` 回调）：
`terrain.ts` 不认识等高线、不认识纸色，避免它 import `panels.ts` 形成循环依赖。

### 这道缝必须够大，而且是**算出来**的（v2.3.0 修的就是它）

图纸与沙盘**水平范围完全相同**，只差一个垂直间隙 `gap`。于是从斜上方看，
图纸在屏幕上不过是"沙盘整体向下平移 `gap·cos(俯角)`"，而沙盘自身占 `L·sin(俯角)`
—— `L` 是视线方向上的水平进深，正方形沿**对角**看时是 `1.41 × 边长`（不是边长）。于是：

```
gap·cos(俯角) ≥ L·sin(俯角)   ⟹   gap ≥ tan(俯角) × 1.41
```

v2.2.0 取 `gap = 0.05`，而门槛是 `tan(21°) × 1.41 ≈ 0.54` —— 差一个数量级：
**图纸 94% 被沙盘自己压住**，屏幕上只有最近那个角露出 6%，看着就是"根本没有图纸"。
它不报错、不警告，八张截图里那张纸若隐若现，很容易被当成"相机角度不对"糊过去。
现在取 `gap = 0.62`（俯角 24°），实测可见率 **100%**。

推论：**间隙与相机俯角是一对耦合参数**，改一个必须回头看另一个。所以它们连同相机取景
一起收进 `layout.ts`（纯数学、不依赖 three.js）：`terrain.ts` 引用它摆图纸，
`view3d.ts` 引用它摆相机，`layout.test.cjs` 引用它**验算** —— 同一条判据跑新旧两组参数，
新 100% / 旧 5.7%（见「开发与验证」）。

相机距离也不是写死比例：装配体高度 = 沙盘起伏 + 底座 + 图纸间隙，随样本与开关变化。
`fitCameraPose()` 解的是**精确不等式**（`|横向偏移| ≤ 深度 × tan(半视场角)`，
代入 `深度 = 距离 − 角点在视线方向的投影`），而不是"半高 ÷ tan(半视场角)"那个正交近似 ——
后者忽略了**近侧的角深度更小、在屏幕上张得更大**，实测会把它们顶出画面 26%。

### 两个开关各自独立（v2.3.0）

| 三维地形 | 二维投影图纸 | 画面 |
| --- | --- | --- |
| 开 | 开 | 沙盘悬在图纸上方（默认，最能讲清"投影"这件事） |
| 开 | 关 | 纯立体；取景自动收近到沙盘 |
| 关 | 开 | 纯平面；取景俯到 52° 把图纸摊开，占屏约 68%×89% |
| 关 | 关 | **不允许** —— 自动把图纸打开（画面不许只剩天空） |

关掉沙盘时**拾取平面从地表高度场切换到图纸平面**（同一个 `worldToGrid` + `sampleGrid`），
所以 hover 读数照常、**还能直接在平面图上点两个点画剖面**。这不是额外加的功能，
是"取样面换成纸面"这一件事的自然结果 —— 反过来，若只切可见性而不切拾取平面，
学生关掉沙盘后会发现鼠标点什么都没反应，而没有任何提示。
巡游模式此时自动退回观察（巡游是沿最陡上升路径爬的，没地表可爬）。

取景也跟着两个开关走：关图纸 ⇒ 下端从"图纸高度"收到"沙盘底边"（相机从 2.22 收到 1.61 跨度）；
关沙盘 ⇒ 装配体退化成一张平面，用更俯的角度对准纸面。

## 手动剖面 + 多段对比（v2.2.0 需求②）

- **怎么算"这是一次点击"而不是"拖动转视角"**：三维视图里指针按下必然同时是这两件事之一，
  OrbitControls 只要收到 `pointerdown + move` 就转，所以判据必须自己定，而且**两条都要满足**：
  位移 < 4 px（生理抖动 1~2 px）**且**时长 < 500 ms。只判位移不够 ——
  学生按着不动想一下再移开，松手时位移可能很小，但视角已经被转走了一点。
- **最多 4 段，四色叠加**：颜色按段的 `index` 派生（不是存下来的），
  所以删掉中间一段后**序号与颜色必须一起重排**，回归里守了这条（`1/2/3/4` → 删首段 → `1/2/3`）。
- **同一条线同时画在三处**：三维地表 / 二维投影图纸 / 平面等高线图，
  **三处坐标严格一致**（都从 `ProfileSegment` 的网格坐标折世界坐标，只有一份口径）。
- **长度口径只有一份**：`cellM = spanM / (grid - 1)`，回归脚本拿它**自校准**期望值 ——
  第一版把 30~90 km 写死，结果当前样本从贡嘎（30 km）换成临汾（60 km）就整片红，
  而红的原因是"我记错了当前是哪个样本"，跟剖面本身无关。

## 地貌图鉴：人工口径 + 机器反向校验（v2.2.0 需求③）

**类型与部位是两套标签，不能混**（按教材口径）：

- **地形类型**（5）：平原 / 高原 / 山地 / 丘陵 / 盆地 —— **盆地属类型，不属部位**；
- **地形部位**（5）：山峰 / 山脊 / 山谷 / 鞍部 / 陡崖。

部位的检出全部是**真算出来的**，不是手写标签：

| 部位 | 判据 | 为什么这么定 |
| --- | --- | --- |
| 山峰 | 局部极大 + 邻域高差够 | 最直接 |
| 山脊 / 山谷 | TPI 高分位（`RIDGE_TPI = 70`，≈ p90） | 阈值取中位数会标出 25% 的格子（见坑 5） |
| 鞍部 | **merge tree / 最大生成树**的 key col | 教材说"两峰之间最低处"，但那是**错**的：真正的鞍部是两峰之间**沿山脊线**的最低点，用 `w(u,v) = min(h(u),h(v))` 跑 Kruskal 才拿得到 |
| 陡崖 | 三道物理闸门同时成立 | ①坡度上限 `CLIFF_SLOPE_CAP_DEG = 80`；②几何推导的窗口落差；③单格落差上限 `CLIFF_MAX_CELL_DROP = 1400`（挡 SRTM 空洞填充） |

`landform.test.cjs` 会**拿真实判据重跑一遍，逐样本核对人工标注的 `landType`** ——
标注错了就红。这样"人工口径"和"机器结论"互相盯着。

### 图鉴是**生成物**，而判据有"下限"与"精确"两种（v2.4.0 量出来的）

`data/landforms.ts` 里的 `counts` / `parts` **不是手写的**，是 `gen_landforms.cjs` 调
`landParts` 算出来写进去的。所以那条"图鉴里的部位计数与现算一致"的红线，
真实含义是**「改了地形、忘了重新生成图鉴」**（与坑 8 同一类）。

v2.4.0 做反证时顺手量出了这些判据各自的**强度**（把模板山地两座主峰拆掉一座）：

| 判据 | 拆掉一座主峰后 |
| --- | --- |
| `template.test.cjs` 的**网格指纹** | ✘ 红（`9d5eb0e7…` ≠ 基线 `8593ddfe…`） |
| `landform.test.cjs` 的**图鉴↔现算交叉核对** | ✘ 红（图鉴 peak3/脊76/谷63/鞍2 vs 现算 peak2/脊74/谷52/鞍1） |
| `山峰 ≥ 2` / `鞍部 > 0` / `五类部位齐全` | ✔ **仍然全绿**（剩 2 峰 1 鞍，都还满足下限） |

**结论：「部位 > 0」这类判据只是下限，只防"从无到有"，防不住"悄悄改形状"。**
真正咬住形状改动的是**指纹基线**与**图鉴交叉核对**这两道精确判据。
以后写新判据时先想清楚要它防哪一类 —— 别指望 `> 0` 替你看住标定。

### `isTemplate` 契约（v2.4.0 新增 · 一个**静默**陷阱）

模板地形**没有地理位置**，这个事实必须由**一个字段**声明、由各处引用，不许各自推断：

| 约束 | 为什么 |
| --- | --- |
| `isTemplate: true`（数据源与图鉴都带） | 界面拿它决定走哪条分支，**不重新推导**（`Snapshot` 里逐条注释"单一事实来源"） |
| **不在 `locations.ts` 里** | 没有省份可标 ⇒ 界面才敢不画中国地图 |
| `lat` / `lon` 是**占位值 30 / 105** | 模板没有真实经纬度；纬度滑块只用来讲垂直带谱 |

⚠️ 那个占位点（30°N / 105°E）**在成都附近、在中国国境线以内** ——
于是"这个坐标在中国境内吗"这类校验**全部通过，界面上什么都不报**。

真正的危险是另一条链路：`locationByTag(tag)` 查不到时会**静默回落**到
`SAMPLE_LOCATIONS[0]`（贡嘎山 / 四川省）。只要有人忘了走 `isTemplate` 分支，
模板山地就会一本正经地显示"四川省"并在中国地图上点一个红点 ——
**数据错了、位置偏了，屏幕上一点异常都没有。**

所以 `locmap.test.cjs` 新增第 6 节把这条**当契约钉住**：模板不在 `locations.ts` 里、
经纬度必须是占位值、`locationByTag` 的回落必须是那个哨兵值。下一次谁动这块，测试先红。

**"相对高度"用的是地块自身的起伏**（移动窗口中位数 `localReliefMedian`），
不是整个取景窗口的起伏 —— 后者在"盆地"上会把盆缘的山也算进盆底，读数虚高。

**计数带「+」表示已到检出上限**：`PEAK_MAX_COUNT = 6` / `CLIFF_MAX_COUNT = 16` 是
**截断后的长度**，不是真实个数。界面上必须写成 `6+` / `16+`，
否则就是拿截断值冒充精确值。回归里有静态断言守着渲染分支不许退回 `{counts[p]}`。

## 三维层实现要点

- **`terrain.ts`** —— `PlaneGeometry(span, span, grid-1, grid-1).rotateX(-π/2)` 之后
  顶点索引**恰好等于 `j*grid + i`**，与 DEM 的行主序完全对齐，可以直接 `setY(k, ...)`，
  不需要任何索引映射表。
- **等高线用 shader 注入**（`material.onBeforeCompile`）：片元按顶点世界坐标 y 取模画线，
  用 `fwidth` 做屏幕空间抗锯齿 —— 线宽远近恒定，不受 `LineWidth = 1px` 的限制。
  `varying float vVisualY` 传视觉高度，所以夸张滑块拉起来线会跟着走。
- **地形裙边（地质标本块）**：只渲染地表会得到一张"悬空方片"，一转到侧视角就露馅。
  四壁 + 底板做成博物馆地形沙盘的样子（`SKIRT_DROP`）。
- **拾取用 ray-march**：沿射线步进比较"射线高度 vs 地表高度"，符号翻转后二分 22 次。
  比 `Raycaster` 遍历 13 万个三角形快一个量级。
- **巡游视角**：从峰顶沿最陡下降方向追到低处再反向，得到"山麓→峰顶"的登山路线，
  按弧长参数化，相机沿它来回走。

## 山脊与河谷怎么认出来

- **山脊/山谷用 TPI 法**：`TPI = h(自己) − mean(菱形邻域 R)`。
  比"垂直于最陡下降方向比较两侧"好 —— 后者在**脊顶失效**（梯度恰好消失，
  `mag < 1e-6 → continue`，最该标成脊的点反而全被跳过）。
  真实 DEM 实测 `p50 = 24 m / p90 = 66 m`，脊点占 6.34%、谷点 3.22%。
- **水系用 D8 流向 + 流量累积**：八邻域最陡下降 + 自高向低累积汇流量，
  支流会自然汇成干流，得到树枝状水系（dendritic drainage）。真实 DEM 自带沟谷，
  比"撒水珠"真实一个量级。
- 阈值取 `maxAcc` 的一个比例，雨越大比例越小（越小的沟也能成河 → 支流越多）。
  **必须守卫 `maxAcc > 0`** —— 见下方"踩过的坑"第 3 条。

## 模型要点（都对着一句"为什么"）

- **为什么"山越高越完整"**：气温直减率 0.6℃/100m，山顶越高，跨过的年均温区间越多，
  带谱条数越多（4000 m 以上才可能出现积雪冰川带）。
- **为什么基带要等于同纬度的水平自然带**：这正是"垂直地带性是水平地带性的缩影"的落点。
  所以带谱**不随季节改换**（北京山麓不会夏天变成常绿阔叶林）。
- **为什么雪线要拆成"多年平均"与"季节"两条**：带谱的雪带下界必须用
  `snowlineAnnual(lat)`（只随纬度变），季节位移只用于**季节性积雪**这个另一概念。
  混用会导致"4200 m 的山夏季没有积雪冰川带、冬季凭空多一条"—— 被真机回归抓到。
- **为什么雪线以上算不产流**：降水以固态为主，要等消融，当期不形成径流。

## 踩过的坑（都是测试或真机抓出来的）

1. **带谱随季节变形。** `bandsFor` 原本用**季节**雪线切积雪带下界 ⇒ 同一座山的带谱夏冬两张脸，
   与"带谱全年稳定"这条要讲的结论直接矛盾。修法：拆出 `snowlineAnnual`，`bandsFor` 改用年均值。
2. **雪线以上当"无植被裸地"处理。** 结果径流河源全跑到雪线以上去了。修法：`runoffWeight`
   遇 `snow` 带直接返回 0。守门断言在 `runoff.test.cjs` §5。
3. **`maxAcc = 0` 时河道阈值也是 0，`acc[k] >= 0` 恒真 → 整张网格全被判成河道。**
   触发条件是"整座山抬到雪线之上"（所有格子产流权重为 0）。实测 `河道 4926 → 65536`。
   修法：筛选时显式要求 `maxAcc > 0 && acc[k] > 0`。
   顺带修了读数文案：这种情况原来统一报"无降雨"，把"雪线抬到了山顶"说成了"没下雨"。
4. **纬度对照被雪线污染，测出的是"雪带面积"不是"植被稀疏度"。**
   最早拿贡嘎山 10°N vs 55°N 做对照，55°N 雪线只有 2946 m 而贡嘎山顶 7414 m，
   **97.8% 的格子都在雪线之上、产流权重直接归零**。改用山顶 3743 m 的太白山、
   10°N vs 40°N（两端雪线 5289 / 4011 m，都是 0% 越线），产流从 22699 单调升到 43573。
   断言里**显式守住了"两纬度都没有格子高于雪线"这个前提** —— 前提不成立时对照本身就无效。
5. **TPI 阈值取在中位数上，标出了 25% 的格子。**
   最初按"中位数附近"取 22 m（实测 |TPI| p50 = 24 m），结果平面上满屏碎点。
   根因是**方向搞反了**：阈值取在中位数上，等于把正半轴的一半全选中。
   "肉眼认得出的那几条脊"对应的是**高分位**。四座真实 DEM 实测（半径 3 格）：
   40 m → 15.6%、60 m → 8.3%、**70 m → 5.8%**、100 m → 1.8%。
   现在 `contour.ts` 导出 `RIDGE_TPI = 70`（≈ 四山 p90），四座山一致落在 5.7%~6.0%；
   纯逻辑测试拿这个常量在四座山上逐个守门。
6. **`ridgeValley` 的第 4 个参数是邻域半径，被误传成了阈值。**
   两处调用写成 `ridgeValley(h, grid, 22, 22)` —— 半径从默认的 3 格放大到 22 格（≈2.6 km）后，
   TPI 从"局部凸凹"退化成"区域坡度"，同一阈值下脊点从 25% 飙到 **44.5%**（实测 20020 格）。
   守门断言是"脊点占比落在 3%~10%"，直接把这个静默错误钉住了。
7. **离屏截帧有几百毫秒滞后，截图会拍到"上一帧的状态"。**
   把高程偏移重置为 0 之后立刻截图，图里却还写着 -2000 m ——
   因为 `paint` 事件不是紧随状态变化而来的。修法：`shot()` 里先 `waitFrames(3)`
   再取帧，并把等待时长记进报告（实测每张 45~140 ms，说明离屏渲染没有被节流）。
   **结论：截图只能用于人眼复核，判定状态一律走 `readState()`。**
8. **`rolldown` 生成的 `_*.cjs` 是构建产物。** 改了源 TS **必须重跑生成**，
   否则测试跑的是旧版本 —— 但测试全绿，看着一切正常。v2.2.0 又踩了一次：
   改了 `src/data/index.ts` 换上"内蒙古高原"样本，`gen:landforms` 却仍在报已删除的
   `loess_plateau`，因为驱动脚本 `scripts/gen_landforms.cjs` 读的是 `scripts/_data.cjs`
   这个**旧产物**、从不读 `src/`。修法两条一起上：
   ① `gen:landforms` 把 rolldown 生成串在自己前面（刷新自己的输入）；
   ② 生成脚本开头加**新鲜度守门**，比对 `_*.cjs` 与 `src/` 的 mtime，不新鲜就
   `print + exit(3)`（退出码 3 = "先重新生成"，别当成断言失败）。
9. **渲染网格的跨度是构造时锁死的，换样本只 `update` 不重建 —— 静默错位。**
   `terrain.ts` 顶部的 `const span = field.spanM` / `const grid = field.grid` 是**闭包捕获**的，
   地表平面 / 裙边 / 底板 / 投影面四块几何的 X/Z 全按它摊开；而 `view3d.refresh` 只在
   `terrain === null` 时 `createTerrain`，之后永远 `terrain.update()` ⇒ **网格永远停在
   第一个样本的跨度**。偏偏拾取（`worldToGrid`）、屏幕投影（`project`）、剖面折世界坐标
   （`buildProfile`）用的一律是**当次** `field.spanM`。
   当时（v2.2.0）8 个样本里只有临汾盆地是 60 km，于是选中它时：
   · 剖面端点被画到滑板外 4~8 km 的空中（网格 30 km、剖面按 60 km 折）；
   · 整块地形按**一半的水平尺度**显示（垂直夸张实际翻倍）；
   · 剖面读数 29.1 km 是地面真实长度的 2 倍。**全程零报错、零日志。**
   抓它的过程也有个教训：先算"抬升量 / 地形起伏"，发现平原上 `lift` 是起伏的 4.5 倍，
   就以为是端点球被抬太高 —— 可一换算到**屏幕**，180 m 在 30 km 跨度上只有 1.8 px，
   根本看不见。**判"看不看得见"必须换算到屏幕像素，不能只比物理量。**
   真正的线索是"四段里只有真鼠标画的那段端点贴在板上"：鼠标拾取走 `worldToGrid(field)`，
   网格世界范围 ±15000 被映射成网格索引 [63,192]，所以鼠标能画出的段**天然落在错位后的板内**。
   修法：`view3d.refresh` 在 `terrain.spanM !== f.spanM || terrain.grid !== f.grid` 时
   **重建**地形（`scene.remove` + `dispose` + `createTerrain`）。显示设置不用自己补 ——
   `engine.apply` 的 `mountainChanged` 分支紧接着就会重新灌 `setContours / setProjection / setProfile`。
   守门断言两条：`dem.test.cjs` §13（数据上确实存在 ≥2 种跨度 + 源码静态成对检查），
   真机回归 E 节（**全部样本**逐一核对 `view3d.debug().terrainSpanM === terrainInfo().spanM`）。
   ⚠️ v2.4.0 之后跨度变成**四种**（模板 20/40 km、真实 30/60 km），
   这个 bug 的触发面比原来更大 —— 跨档切换时更要紧。
   修复前后同一个 `E1/E2` 差集判据：端点球周围天空占比 **100% → 37%**，
   canvas 内天空占比 **82.9% → 46.3%**（后者就是"地形按一半尺度渲染"的量化证据）。
10. **断言的作用域会过时，而且红得莫名其妙。** 扩到 8 个样本后，
   `contour.test.cjs` 的"四山一致"（脊点占比 3%~10%）、`dem.test.cjs` 的"≥1000 m 高差"、
   `locmap.test.cjs` 的"四座山分属四个省"全红了 —— **数据是对的，是断言的作用域过时了**
   （平原本来就没有脊点、川中丘陵与贡嘎山本来就同属四川）。
   修法：一律按 `landType` 分流，并**补一条反方向的断言**（非山地必须 `rr < 0.03`，
   平原的等高线要么两边都是 0、要么同一个数量级）。教训：**判据的隐式前提要写出来**，
   不然下次扩数据时你得重新推一遍自己当初在想什么。
11. **React 不会自己知道引擎变了。** 三维画面走 rAF 直读引擎，所以引擎一改画面立刻动；
   可侧栏列表、剖面页这些读的是 React 的 `snap` ⇒ **凡是"引擎改了但界面没反应"，
   十有八九是漏了 `setSnap(engine.snapshot())`。** 真踩的是 `onPointerUp`：
   真鼠标画完一段，三维里线出来了，但操作条还写 `0/4 段`、侧栏没有行、剖面页还是"参考剖面"。
   调试钩子那几个入口（`addSegment` / `moveSegmentEnd` / `removeSegment` / `clearSegments`）
   每个都补了 `setSnap` 并返回真实值 —— 钩子与界面点击走**同一个**引擎入口，
   否则回归测的就不是用户走的那条路。
12. **截断计数是"伪精度"。** `PEAK_MAX_COUNT = 6` / `CLIFF_MAX_COUNT = 16` 是检出数组的
   **截断长度**，不是真实个数。直接显示 `counts[p]` 就是拿截断值冒充精确值 ⇒
   统一走 `isCappedPart` + `LAND_PART_CAP`（上限是**算法的属性**，只声明一次，
   不许复制到 8 张卡片上），渲染成 `6+` / `16+`，页脚也要说明"+"的含义。
13. **"图纸在沙盘正下方"是对的，但它有一条硬几何门槛 —— 而门槛的两半分居两个文件。**
   图纸与沙盘水平范围相同，只差垂直间隙 `gap`；从斜上方看，图纸在屏幕上只是"整体下移
   `gap·cos(俯角)`"，而沙盘自身占 `L·sin(俯角)`（`L` 是视线方向的水平进深，沿对角看是
   `1.41 × 边长`）。于是 `gap < tan(俯角) × 1.41` 时图纸**整个被沙盘自己压住**。
   v2.2.0 取 `gap = 0.05`（门槛 ≈ 0.54），实测可见率 **5.7%** —— 屏幕上只有最近那个角
   露出一小条，用户的原话是"完全看不到二维的面"。**不报错、不警告。**
   根因是口径分散：间隙写在 `terrain.ts`、相机俯角写在 `view3d.ts`，**谁也不知道对方**，
   所以没人会发现这对参数必须一起改。修法：三样（间隙 / 俯角 / 取景）收进 `layout.ts`，
   渲染两侧**引用**，测试**验算**。
   顺带记一条**建模坑**：判"视线是否被沙盘挡住"时**不能把"终点在地表之下"算作遮挡** ——
   图纸本来就该在地表之下。第一版这么写，8 个样本全部报 100% 被挡。
   正确判据是"射线一旦降到沙盘底边以下就停止检查"（遮挡物只存在于底边之上），
   因为"从裙边底下钻进去看图纸"是一条**合法**视线路径。
14. **判"某个东西在屏幕上到底占多少"：同机位差集最干净，但有两个陷阱。**
   ① **读数要先把帧推出去。** `renderer.info.render.calls` 是**最后一帧**的统计，
      改完状态直接读会拿到上一帧的数 —— 实测现象是"子对象 `visible` 全对、`drawCalls`
      纹丝不动"，看着像"隐藏没生效"，其实只是 rAF 没推进。先用一次截图
      （`capturePage` 会驱动合成）把帧推出去再读就对了（`5 → 2`）。
   ② **差集要求两张图机位一致，而切开关会触发重新取景**（关图纸要把镜头收近、
      关沙盘要俯到纸面）。所以回归里加了 `lockCamera(eye, target)` 钩子：
      先切状态、再把相机摆回原处，差集才干净。
      判读脚本 `analyze_proj.py` 会把**差异图落盘** —— 它一眼就能看出"差异到底是不是图纸的形状"，
      比只看百分比可靠。教训来自一个失败的判据：起初想直接数"纸色像素占比"，
      结果被地形雪带的浅色污染，**修前 9.35% 反而大于修后 6.78%**，完全误导。
15. **用下标取样本，会在"往前面插一个样本"时静默指错人。**（v2.4.0 一次踩到 4 处）
   测试里一直写 `DEM_SOURCES[0]` / `SOURCES[3]`。这一版把 3 个模板地形**插在数组最前面**，
   于是：`[0]` 从贡嘎山变成模板山地（"真实 DEM 的 TPI 量级"开始量一个解析山包，
   p50 掉到 0.3 m）；`[3]` 从太白山变成贡嘎山（"下切"的最小海拔从 0 变成 204 m）；
   `locmap` 的样本数从 8 变 11、三处红点全叠在同一点（模板共用同一个占位经纬度）。
   **四处红，四处原因各不相同，但根只有一个：断言点名了一个"位置"而不是"东西"。**
   修法：统一改成语义查找 `sourceByTag("gongga")` / `sourceByTag("taibai")`，
   并把"真实样本清单"显式改成 `REAL_SOURCES`（模板单独用 `TEMPLATE_SOURCES`）。
   顺带加了反方向断言：「真实样本清单里恰好 4 座山 + 4 个非山地」——
   下次再往数组里插东西，它会先红。
   **教训：数组下标是"位置"，不是"身份"。凡是断言里出现 `[数字]`，都要问一句
   "这个位置以后会被别人占掉吗"。**
16. **"占位值恰好落在合法区间内"会让校验全部失效。** 模板地形的 `lat/lon` 填的是
   占位值 `30/105`，而这一点**在成都附近、在中国国境线以内** ⇒ "坐标是否在中国境内"
   这类校验**全部通过**。更险的是 `locationByTag` 查不到时会**静默回落**到
   `SAMPLE_LOCATIONS[0]`（贡嘎山 / 四川省）—— 谁忘了走 `isTemplate` 分支，
   模板山地就会显示"四川省"并在地图上点一个红点，**屏幕上毫无异常**。
   修法：把"模板没有地理位置"这件事升格成**一个字段**（`isTemplate`），
   由数据源一路带到 `Snapshot`，界面按它分支、**不重新推导**；
   并在 `locmap.test.cjs` §6 把这个契约钉住。
   **推论：占位值必须选一个"一看就不对"的值，或者干脆配一条测试守住它。**
   落在合法区间里的占位值，比报错的占位值危险得多。
17. **`&&` 串起来的测试链，第一个失败就停 —— 别把"只红一条"当成"只影响一处"。**
    v2.4.0 做反证（把模板山地两座主峰拆掉一座）时，看到输出里只有 LANDFORM 套件报红，
   差点得出"这个改动只影响图鉴"的结论。实际上 `template.test.cjs` 排在链尾，
   **根本没跑**；单独一跑，网格指纹基线也是红的。
    顺带量出了判据强度这件事（详见「地貌图鉴」一节）：`山峰 ≥ 2` / `鞍部 > 0` /
   `五类部位齐全` 三条在拆掉一座主峰后**仍然全绿** ——
   **`> 0` 这类下限判据只防"从无到有"，防不住"悄悄改形状"**，
    真正咬住形状的是**指纹基线**与**图鉴↔现算交叉核对**这两道精确判据。

## 参数 → 重算代价分配（改 UI 前必读）

`engine.apply(patch)` 按改动类型分配重算范围，这是本游戏性能的关键：

| 参数 | 重建 DEM | 重算等高线 | 重算径流 |
| --- | :---: | :---: | :---: |
| 山体（换山） | ✔ | ✔ | ✔ |
| 海拔偏移 / 垂直夸张 | ✔（只改 `alt`） | ✔ | ✔ |
| 纬度 / 季节 | | 纬度要（带谱变了）/ 季节不用 | ✔ |
| 等高距 / 显示开关 | | ✔ | |

注意**季节只重算径流**（降水强度变了），等高线完全不用动 —— 早先一刀切"全重建"，
拉一下季节滑块就卡顿。

五个必须注意的前提：

- `postToPlatform` 里有 `if (window.parent !== window)`，**顶层页面根本不发 `GAME_READY`**
  ⇒ 站点必须是 `host/wrapper.html` 套 iframe，用 `webContents.mainFrame.frames[0]` 驱动子框架，
  且 `sendInputEvent` 要用**顶层窗口坐标**（iframe 内元素坐标要加偏移）。
- **这一版是 WebGL，像素级结论不能用 `getImageData`**（软渲染会读回半成品帧）。
  像素只保留两种用法：①**帧差**（回答"画面真的重画了吗"，不回答"画得对不对"）；
  ②**底部栏的 canvas 2D**（同步确定，可以放心数像素，用来守"这一栏不许大片留白"）。
  颜色对不对交给 `dem.test.cjs` / `zonation.test.cjs` 的纯逻辑断言。
  ⚠️ 做帧差取证时**必须先把区域裁到 canvas**：整张截图里有 DOM 面板，
  加一段剖面会同时改动底部的剖面图与侧栏列表 —— 第一版没裁，
  检出的 4 个"球"全是底部剖面图里的大色块（y≈985，而 canvas 只有 677 高），
  连"天空底色"都取到了左上角白底信息卡上。
- **验证目录同步用覆盖式，不要删文件**：`shutil.rmtree` 一次删 85 个文件会被
  "批量删除保护"拦下（阈值 50），静默失败后你会**拿着旧产物跑完全程还以为测的是新代码**。
  直接 `copytree(..., dirs_exist_ok=True)` 即可 —— `index.html` 只引用新 hash，旧文件留着无害；
  探活时**从 `index.html` 里解析真实的 assets 名字**再请求，别自己拼 hash。
- **判据的期望值要"量"不要"记"**：第一版把剖面长度写成 30~90 km、把四座山的陡崖数都当成 16，
  结果当前样本一换（贡嘎 30 km → 临汾 60 km）、数据一对（实际 16/16/15/4）就整片红，
  红的原因却是"我记错了"，跟被测代码无关。现在长度用 `cellM` 自校准、
  陡崖数先量出 `["陡崖16+","陡崖16+","陡崖15","陡崖4"]` 再断言。
- **"改状态"和"画面真的变了"是两件事，读渲染统计前必须先推一帧**：
  `renderer.info.render.calls` 是**上一帧**的统计，`setProjection(false)` 之后立刻读，
  拿到的是切换前的数 —— 实测 `5 → 5`（六个 mesh 的 `visible` 明明全对）。
  先 `capturePage()` 推一帧再读，才是 `5 → 2`。
  所以 `debug()` 里现在同时报 `meshes`（逐子节点的 `name + visible`）——
  单个布尔量会被"状态改了、图没动"骗过去，逐节点清单不会。
  ⚠️ 同理，**开关会连带改变取景**（关图纸后组件下端从图纸 Y 掉到裙边底部、关沙盘后俯仰角
  24°→52°），于是"同机位差集"会因取景变化而失真。这两件事都得要：
  取景必须跟着变（否则沙盘缩成屏幕中间一小块，本来就是缺陷），
  取证又要同机位 ⇒ 加了 `lockCamera(eye, target)` 钩子把相机钉死，
  让像素差集与 UX 取景各自成立、互不干扰。

  单纯加功能、加样本**不动简介**，写 `CHANGELOG.md`。
- **每次更新收尾必出「比上版改了什么」**：更新 `CHANGELOG.md`（新版在最上面）
  + 在给用户的回复里同步一遍。**基线以云端已发布那版为准**（查 `game_package`
  关联 `game_product`），**不看 `git log`** —— 本仓库长期带着未提交的工作区。
