# 真实地形山地 · 垂直地带性（mountain_zones）

> 课堂演示型**三维真实地形**沙盘：用真实 DEM（数字高程模型）重建四座真山，
> 拖动海拔偏移与垂直夸张重塑山体，改纬度、切四季，看垂直自然带如何随高度更替；
> **窗口底部固定一栏专门显示等高线**（平面等高线图 / 等高线清单 / 垂直剖面图三页签），
> 可按需叠加山脊线、水系与降雨径流。
>
> `gameCode = mountain_zones` · `requiresRoster = false`（`GamePage` 据此跳过选人环节，
> 打开即教学）· 版本号三处同步：`manifest.json` / `package.json` / `src/main.tsx`。
>
> **v2.0.0 是一次彻底重构**：删掉 v1.2.0 的二维像素渲染整套（`world2d` / `species` /
> `sprites` / `render` / `sim` / `rand` 六个模块 **全部删除**），回到 WebGL。
> 这次不是"再画一个假山"—— 山体是**真实 DEM 数据**。
> **动物全部移除**（v1.2.0 的 45 种动物精灵一并删除，知识改由图鉴文字承载）。

## 为什么这一版的三维不像以前那么假

v1.0 那版三维是**程序化噪声**堆出来的（`fbm2D`），它的问题不是分辨率，是**没有地貌逻辑**：
噪声山永远只有一层均匀的皱褶，看不出"这里是一条脊、那里是一条被水切出来的谷"。

改成真实 DEM 后，地形自带真实的水系切割与山脊走向 —— 贡嘎山有放射状山脊 + 深切河谷，
珠峰有冰川谷与山群，太白山有连片高山草甸。**真实地形的皱褶感是噪声函数做不出来的。**

## 数据管线（`/` 全离线）

- **来源**：[AWS Terrain Tiles](https://registry.opendata.aws/terrain-tiles/)（Terrarium 编码），
  免 key、公有领域。解码 `h = R*256 + G + B/256 − 32768`，精度 1/256 m。
- **生成脚本**：`.workbuddy/tmp/dem-probe/build_dem.py`（改山体只需改里面的经纬度与跨度）。
- **地面等距重投影**：瓦片本身是 Web Mercator，直接采样会让高纬山体横向拉伸。
  生成时按 `cos(center_lat)` 修正，把 3×3 瓦片重采样成 **256×256 的地面等距网格**
  （x/y 方向每像素对应的实际米数相同）。
- **峰顶自动居中**：先在大窗口里搜最高点 → 反算该点的经纬度 → 以它为中心重新裁 30 km 见方窗口。
  四座山最终峰顶偏移全部为 **0%**（数据见下表）。
- **编码**：整数米 → `Uint16` 小端 → base64，**不做 zlib**。实测压缩率只有 0.767
  （地形数据本来就很紧），却会把解码变成异步（`DecompressionStream`），
  换来异步初始化 + loading 态 + 测试要 `await` —— 省 160 KB 不值这个复杂度。
  每座山 175 KB，四座共 700 KB，全部内嵌进 bundle，运行时不需要联网。

| tag | 名称 | 主峰 | DEM 范围 | 纬度 | 网格 |

## 「海拔」与「视觉高度」必须分开（本轮最重要的架构决策）

这是两个完全不同的东西，混在一起会立刻产生荒谬读数：

| 参数 | 改什么 | 谁跟着变 |
| --- | --- | --- |
| `elevationOffset`（±2000 m） | **真改海拔** | 面板读数、等高线注记与条数、带谱边界、林线雪线判定，全跟着变 |
| `verticalExaggeration`（×0.5~2.0） | **只改视觉纵轴** | 只有渲染顶点用它；不影响"这座山有多高" |

实现上靠两份数组：

- `field.raw` —— 真实 DEM 的只读副本，**永不改写**，"还原真实地形"的依据
- `field.alt` —— 当前海拔 = `max(0, raw + elevationOffset)`，是面板与所有判据的真实来源

**视觉高度 `visualY(f, alt) = alt × verticalExaggeration` 只在拼渲染顶点时临时算。**
早期若图省事把夸张乘进 `alt`，就会出现"夸张调到 2 倍 → 面板显示贡嘎山 14828 m"的静默错误。

## 底部等高线栏（本次新增的第四个要求）

窗口底部固定 300 px 的横栏，三个页签共用同一份数据：

| 页签 | 画什么 |
| --- | --- |
| **平面等高线图** | 自然带淡色底图 + 等高线（计曲线每 5 条加深加粗）+ 计曲线高程注记（垫纸色背景）+ 山脊点 + 河道 + 峰顶红三角 + 指北针 + 10 km 比例尺 |
| **等高线清单** | 逐条列出海拔与圈数，点击即高亮；雪线以上的条目带"雪线以上"标签 |
| **垂直剖面图** | 沿路径采样 → 自然带填色 → 地形轮廓墨线 → 雪线（蓝实线）/ 林线（绿虚线）标记 → 各带海拔区间右侧竖排标签 |

宽屏时平面图画布右侧还会画出**图廓要素**：自然带图例（含海拔区间）、本图说明
（等高距 / 条数 / 图幅 / 网格 / 当前海拔范围 / 峰顶）、符号例。这不是为了填满空白 ——
这一栏是"矮而宽"（约 1100×230）而地形窗口是正方形，**正方形居中摆放时只占 15% 宽度**，
不补上这些内容就看着像界面没画完。回归里有条像素断言专门守这个（右侧 2/3 非纸色像素 > 2%）。

## 三维层实现要点

- **`terrain.ts`** —— `PlaneGeometry(span, span, grid-1, grid-1).rotateX(-π/2)` 之后
  顶点索引**恰好等于 `j*grid + i`**，与 DEM 的行主序完全对齐，可以直接 `setY(k, ...)`，
  不需要任何索引映射表。
- **等高线用 shader 注入**（`material.onBeforeCompile`）：片元按顶点世界坐标 y 取模画线，
  用 `fwidth` 做屏幕空间抗锯齿 —— 线宽远近恒定，不受 `LineWidth = 1px` 的限制。
  `varying float vVisualY` 传视觉高度，所以夸张滑块拉起来线会跟着走。
- **地形裙边（地质标本块）**：只渲染地表会得到一张"悬空方片"，一转到侧视角就露馅。
  四壁 + 底板做成博物馆地形沙盘的样子（`SKIRT_DROP`）。
- **拾取用 ray-march**：沿射线步进比较"射线高度 vs 地表高度"，符号翻转后二分 22 次。
  比 `Raycaster` 遍历 13 万个三角形快一个量级。
- **巡游视角**：从峰顶沿最陡下降方向追到低处再反向，得到"山麓→峰顶"的登山路线，
  按弧长参数化，相机沿它来回走。

## 山脊与河谷怎么认出来

- **山脊/山谷用 TPI 法**：`TPI = h(自己) − mean(菱形邻域 R)`。
  比"垂直于最陡下降方向比较两侧"好 —— 后者在**脊顶失效**（梯度恰好消失，
  `mag < 1e-6 → continue`，最该标成脊的点反而全被跳过）。
  真实 DEM 实测 `p50 = 24 m / p90 = 66 m`，脊点占 6.34%、谷点 3.22%。
- **水系用 D8 流向 + 流量累积**：八邻域最陡下降 + 自高向低累积汇流量，
  支流会自然汇成干流，得到树枝状水系（dendritic drainage）。真实 DEM 自带沟谷，
  比"撒水珠"真实一个量级。
- 阈值取 `maxAcc` 的一个比例，雨越大比例越小（越小的沟也能成河 → 支流越多）。
  **必须守卫 `maxAcc > 0`** —— 见下方"踩过的坑"第 3 条。

## 模型要点（都对着一句"为什么"）

- **为什么"山越高越完整"**：气温直减率 0.6℃/100m，山顶越高，跨过的年均温区间越多，
  带谱条数越多（4000 m 以上才可能出现积雪冰川带）。
- **为什么基带要等于同纬度的水平自然带**：这正是"垂直地带性是水平地带性的缩影"的落点。
  所以带谱**不随季节改换**（北京山麓不会夏天变成常绿阔叶林）。
- **为什么雪线要拆成"多年平均"与"季节"两条**：带谱的雪带下界必须用
  `snowlineAnnual(lat)`（只随纬度变），季节位移只用于**季节性积雪**这个另一概念。
  混用会导致"4200 m 的山夏季没有积雪冰川带、冬季凭空多一条"—— 被真机回归抓到。
- **为什么雪线以上算不产流**：降水以固态为主，要等消融，当期不形成径流。

## 踩过的坑（都是测试或真机抓出来的）

1. **带谱随季节变形。** `bandsFor` 原本用**季节**雪线切积雪带下界 ⇒ 同一座山的带谱夏冬两张脸，
   与"带谱全年稳定"这条要讲的结论直接矛盾。修法：拆出 `snowlineAnnual`，`bandsFor` 改用年均值。
2. **雪线以上当"无植被裸地"处理。** 结果径流河源全跑到雪线以上去了。修法：`runoffWeight`
   遇 `snow` 带直接返回 0。守门断言在 `runoff.test.cjs` §5。
3. **`maxAcc = 0` 时河道阈值也是 0，`acc[k] >= 0` 恒真 → 整张网格全被判成河道。**
   触发条件是"整座山抬到雪线之上"（所有格子产流权重为 0）。实测 `河道 4926 → 65536`。
   修法：筛选时显式要求 `maxAcc > 0 && acc[k] > 0`。
   顺带修了读数文案：这种情况原来统一报"无降雨"，把"雪线抬到了山顶"说成了"没下雨"。
4. **纬度对照被雪线污染，测出的是"雪带面积"不是"植被稀疏度"。**
   最早拿贡嘎山 10°N vs 55°N 做对照，55°N 雪线只有 2946 m 而贡嘎山顶 7414 m，
   **97.8% 的格子都在雪线之上、产流权重直接归零**。改用山顶 3743 m 的太白山、
   10°N vs 40°N（两端雪线 5289 / 4011 m，都是 0% 越线），产流从 22699 单调升到 43573。
   断言里**显式守住了"两纬度都没有格子高于雪线"这个前提** —— 前提不成立时对照本身就无效。
5. **TPI 阈值取在中位数上，标出了 25% 的格子。**
   最初按"中位数附近"取 22 m（实测 |TPI| p50 = 24 m），结果平面上满屏碎点。
   根因是**方向搞反了**：阈值取在中位数上，等于把正半轴的一半全选中。
   "肉眼认得出的那几条脊"对应的是**高分位**。四座真实 DEM 实测（半径 3 格）：
   40 m → 15.6%、60 m → 8.3%、**70 m → 5.8%**、100 m → 1.8%。
   现在 `contour.ts` 导出 `RIDGE_TPI = 70`（≈ 四山 p90），四座山一致落在 5.7%~6.0%；
   纯逻辑测试拿这个常量在四座山上逐个守门。
6. **`ridgeValley` 的第 4 个参数是邻域半径，被误传成了阈值。**
   两处调用写成 `ridgeValley(h, grid, 22, 22)` —— 半径从默认的 3 格放大到 22 格（≈2.6 km）后，
   TPI 从"局部凸凹"退化成"区域坡度"，同一阈值下脊点从 25% 飙到 **44.5%**（实测 20020 格）。
   守门断言是"脊点占比落在 3%~10%"，直接把这个静默错误钉住了。
7. **离屏截帧有几百毫秒滞后，截图会拍到"上一帧的状态"。**
   把高程偏移重置为 0 之后立刻截图，图里却还写着 -2000 m ——
   因为 `paint` 事件不是紧随状态变化而来的。修法：`shot()` 里先 `waitFrames(3)`
   再取帧，并把等待时长记进报告（实测每张 45~140 ms，说明离屏渲染没有被节流）。
   **结论：截图只能用于人眼复核，判定状态一律走 `readState()`。**
8. **`rolldown` 生成的 `_*.cjs` 是构建产物。** 改了源 TS **必须重跑生成**，
   否则测试跑的是旧版本 —— 但测试全绿，看着一切正常。

## 参数 → 重算代价分配（改 UI 前必读）

`engine.apply(patch)` 按改动类型分配重算范围，这是本游戏性能的关键：

| 参数 | 重建 DEM | 重算等高线 | 重算径流 |
| --- | :---: | :---: | :---: |
| 山体（换山） | ✔ | ✔ | ✔ |
| 海拔偏移 / 垂直夸张 | ✔（只改 `alt`） | ✔ | ✔ |
| 纬度 / 季节 | | 纬度要（带谱变了）/ 季节不用 | ✔ |
| 等高距 / 显示开关 | | ✔ | |

注意**季节只重算径流**（降水强度变了），等高线完全不用动 —— 早先一刀切"全重建"，
拉一下季节滑块就卡顿。

## 开发与验证

```bash
npm run test:data   # rolldown 打包纯逻辑模块 → 跑 203 项断言
npm run build       # tsc --noEmit && vite build（产物 dist/web/）
```

`test:data` 依赖 **Vite 自带的 rolldown**（本机没有 esbuild）把含 `import` 的 TS 打成 CJS；
**改了源文件必须重跑生成**，脚本已把生成与断言串在一条 npm script 里。

⚠️ **不要把 `npm run test:data` 与 `npm run build` 串在同一条 shell 命令里。**
两者都用 rolldown，实测串起来跑时 `vite build` 会偶发失败，且错误被包成
`Build failed with 1 error ... errors: [Getter/Setter]`（真实报错被吞掉，看着像代码错了）。
分开两次调用就稳定通过。

真机渲染回归（Electron 指向真实 `dist/web`）：`.workbuddy/tmp/mzverify3/shot.js`，129 项断言。
分组：A 启动/协议/挂载 · B 真实 DEM 数据 · C 海拔 vs 视觉高度 · D 底部等高线栏 ·
E 帧差（渲染真的变了）· F 没有动物（源码/DOM/产物三处）· G 水系与山脊 · H 真实鼠标交互 ·
I 样式是否真生效 · J 确定性 · K 截图落盘。

三个必须注意的前提：

- `postToPlatform` 里有 `if (window.parent !== window)`，**顶层页面根本不发 `GAME_READY`**
  ⇒ 站点必须是 `host/wrapper.html` 套 iframe，用 `webContents.mainFrame.frames[0]` 驱动子框架，
  且 `sendInputEvent` 要用**顶层窗口坐标**（iframe 内元素坐标要加偏移）。
- **这一版是 WebGL，像素级结论不能用 `getImageData`**（软渲染会读回半成品帧）。
  像素只保留两种用法：①**帧差**（回答"画面真的重画了吗"，不回答"画得对不对"）；
  ②**底部栏的 canvas 2D**（同步确定，可以放心数像素，用来守"这一栏不许大片留白"）。
  颜色对不对交给 `dem.test.cjs` / `zonation.test.cjs` 的纯逻辑断言。
- **验证目录同步用覆盖式，不要删文件**：`shutil.rmtree` 一次删 85 个文件会被
  "批量删除保护"拦下（阈值 50），静默失败后你会**拿着旧产物跑完全程还以为测的是新代码**。
  直接 `copytree(..., dirs_exist_ok=True)` 即可 —— `index.html` 只引用新 hash，旧文件留着无害；
  探活时**从 `index.html` 里解析真实的 assets 名字**再请求，别自己拼 hash。
