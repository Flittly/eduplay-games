### 题库设计：五维配平是硬约束（这次的重点）

原有五维人格框架：`thermal` 温度（冷静内敛↔炽热张扬）、`relief` 起伏（平和低调↔高远出众）、
`hardness` 质地（柔韧随和↔刚强棱角）、`dynamics` 动态（沉静恒定↔激荡多变）、
`moisture` 水意（独立自持↔丰盈亲和）。

**写在 `logic.ts` 里的归一化机制决定了配平规则**：
`ceil[d] = Σ_q max_o |delta_o[d]|`，`t = clamp(raw[d] / (ceil[d] * 0.62))` → `50 + 50t`。
所以每个维度必须满足：

1. **该维度「各题最大正值之和」≥ 0.62 × ceil**，否则回答再热情也到不了 100；
   负向同理，否则到不了 0。（本轮五维的 max正和 = 13/14/16/14/16，max负和 = 16/16/14/14/16，
   ceil 全为 16 —— 都过线。）
2. **维度覆盖要均**：20 题 × 每题 2 维 = 40 个槽位 ÷ 5 维 = **每维出现恰好 8 次**。
   我先把「题号 → 维度对」排成一张 20 行的表，让 T/R/H/D/M 各出现 8 次，再填地理情境；
   先定情境后配维度必然会偏（第一版 H 出现了 14 次、R 只有 6 次）。
3. **选项顺序会带来系统性偏差**：模拟「每题都选第 N 项」，全选第 1 项得
   `温度90/起伏85/质地75/动态75/水意100`，全选第 2 项 `温度0/起伏5/...` —— 因为多数题的
   第 1 项是「热/湿」极。这是情境题的自然结果，真实作答不受影响，但**说明里别宣称**能靠它测出
   绝对分数。若要彻底消除，需要逐题打乱选项顺序（本轮没做）。
4. 把这份规则写成脚本 **`scripts/check_questions.py`**（两端各一份）：查 JSON 结构、
   delta 键合法与 −2~2、维度出现次数、正/负可达性（≥0.62×ceil）、并打印三种极端作答的
   五维得分。**改题后必须跑它**——它就是这套题目的守门人。

20 道题的地理情境（全部命中地理关键词，实测覆盖 20/20）：气候带选居地、大河上中下游、

## weather-quiz 暖锋符号修正：半圆直径必须压在锋线上

用户反馈「暖锋符号的半圆太靠上，直径应与锋线在同一水平面」。

**根因**：`scripts/svgkit.py` 的 `front_line()` 里，暖锋半圆的圆心被放在**法向 r 处**
（`ax, ay = x + px*r, y + py*r`），于是直径悬在线外 10px、只有弧顶碰到线 ——
整个半圆"骑"在线的上方。冷锋三角的底边本来就在线上，两者不一致。

**修法**：圆心落回锋线上的采样点，直径与线重合，弧沿 -p 侧鼓出（`sweep=1` 固定 ⇒
弧脊在 `圆心 + r*(uy, -ux)`）。抽成内部闭包 `half_disc(r, fill)`，暖锋 r=10、
准静止锋的暖侧标记也从「整圆骑线」改成同款半圆 r=9，与三角分列两侧的语义不变。

几何自证：`front_warm.svg` x=222 处锋线 y=196，半圆两端点 (231.767,198.144) 与
(212.232,193.856) 的中点正好是 (222.000,196.000)。

**回归脚本** `.workbuddy/tmp/wqverify/front.js`（新）：把三个符号 `<img>` 画进 canvas，
扫**锋线法线那一列**的像素，断言红色不从线的上方开始（旧写法 red[0]≈186 会被判失败）、
朝线的一侧鼓出、以及两标记之间只剩线宽。9 条断言全绿。
注意准静止锋 pts=[(58,186),(140,186),(222,186),(302,186)] 下 **i=1⇒x=140 是半圆（向上）、
i=2⇒x=222 是三角（向下）** —— 采样列搞反过一次，白跑一轮。

**顺带**：素材改完 → `npm run build`（js/css hash 不变，只 public 变了）→
`publish_weather.py` 重传，双端 `weather_quiz v0.1.0` 覆盖成功（同版本覆盖平台是允许的）。

**新坑**：Electron 截图脚本漏写 `--disable-gpu-sandbox`（只写了 `--no-sandbox`）时，
`loadURL()` 永不 resolve、脚本静默挂死且无任何输出 —— 以后一律照 `diag.js` 的完整开关列表抄。

## 新游戏：地图图例消消乐（legend-match，gameCode `legend_match` v1.0.0）

初中地理「识别地图图例」。用户给的核心要求是一条玩法硬约束：
**配对成功时，这一对必须在屏幕中央放大复现一次**（符号 + 全称 + 一句话解释），
点一下可立刻继续、否则 1.7 秒自动收起 —— 复现是必经的中间态，不是一闪而过的动画。

**玩法与结构**
- 牌面散落「图例符号卡」和「名称卡」，点一张符号再点它的名称即配对消除。
- 六关逐关加量：对数 6 / 8 / 10 / 12 / 14 / 16（整局 66 对），共 60 个初中地理常见图例、7 类。
- 双人 PK 与兄弟游戏同构：三阶段 `arrange → battle → result`，共享一副牌面**轮流出手**
  （配对成功 +10 继续出手、配错换手且不扣分），负者下场不回流，全程显示姓名。
- 单人闯关额外有「提前结算」：只在本关已完成（分数是有效阶段成绩）时才允许，
  课堂时间不够可以直接交成绩。结果页「下一位上场：李四」逐位学生轮流。

## 新游戏：三维山地·垂直地带性（mountain-zones，`mountain_zones` v0.1.0，已上架双端）

用户要六件事：①可调**海拔**（越高植被越稀疏，落叶阔叶林 / 针叶林 / 常绿阔叶林要**专门建模**）
②可调**纬度** ③可切**四季** ④**等高线**开关 + 疏密可调 ⑤林中**能动的动物**（鹿 / 黑熊 / 虎，
时而出现时而消失）⑥**雨水** → 地表径流。三个架构决策走 AskUserQuestion 定下：
**纯探索沙盘**（不判分）、**程序化生成山体**、**低多边形卡通**。

### 模型（都是解析式，因此可以被单测钉住）

- **垂直地带性**：气温直减率 0.6℃/100m；`T0(lat) = 28 − 0.4|lat|`；
  雪线 `5000·cos^1.2(lat) + 季节位移`；林线 `min(T0/LAPSE, 雪线−60)`；
  **基带 = 同纬度水平自然带**（热带山脚常绿阔叶林，60°N 山脚针叶林）。
- **带谱不随季节改换，只有雪线上下挪** —— 否则"四季"会把"垂直带谱"这个概念讲糊；
  季节只改雪线位置 + 落叶林季相配色。
- **地表径流**：D8 最陡下降 + 汇流累积 → 河网；产流权重 = `1 − 植被覆盖`（雪带固定 0.05）
  ⇒「植被越稀 → 冲刷越强」是被断言过的结论，不是画着好看。
- **确定性值噪声**：mulberry32 + hash2 + smoothstep 双线性 + fbm ⇒ 同一 seed 每次进页面山形一致。

### 三个真·建模缺陷（都靠真机读数暴露，纯读代码看不出来）

1. **山麓平原被抬高，30°N 的基带被整体挤掉**（真机 `vegCounts.broadleafEvergreen === 0`）。
   `PLAIN_U = 0.045` 让 4200m 山的山麓顶在 189m，而 30°N 常绿阔叶林上限只有 167m。
   改 `PLAIN_U = 0.004`（山麓落到 17~28m），并加守门断言「山麓平原要真的落在基带里」。
2. **坡度闸门 `slope > 0.35` 把动物候选点筛光**（鹿 / 熊 / 虎全部 inactive）。
   用 Node 复刻筛选逻辑逐条统计定位：坡度筛掉 57/126，密度只筛掉 2。
   改成 `pickHabitatSpots()`：**自然带 + 密度是硬判据，坡度只用来「排序择优」**
   （`candidates.sort((a, b) => rank(a.slope) - rank(b.slope))`），兜底上限 tan 62°。
   注释写死一句话：「带在，动物就在」——自然带与密度决定有没有，坡度只决定站哪儿舒服。
3. **剖面指数 0.82 让山麓坡度发散**（`du/dt = k·t^(k−1) → ∞`），低海拔带被压成山脚一圈
   "近乎垂直的薄环"：7000m 山在 45°N 时落叶阔叶林只占半径最外 0.2%，老虎抽不到点。
   改 `PROFILE_POW = 1.15` 后，45°/7000m 虎从 0 → 2 只。

### 一个会让整页白屏的坑：`mergeGeometries()` 失败是**静默返回 null**

动物终于能出现之后页面直接进错误边界，真因是 `IcosahedronGeometry`（做树冠 / 石头 blob）是
**非索引**几何体，而 `Box / Cone / Cylinder` 是**索引**的，混着合并时 `mergeGeometries()`
只打一条 `console.error` 然后**返回 null**（不抛错），下游 `new THREE.Mesh(null, …)`
在 `morphAttributes` 上炸。修法：几何构建抽到独立 `models.ts`，统一入口
`mergeParts(parts) { return mergeGeometries(parts.map(flatten), false); }`，
`flatten = (g) => (g.index ? g.toNonIndexed() : g)`；并在 `makeAnimalGeometry` 末尾
`if (!merged) throw new Error(...)` —— **合并失败要大声死，不要静默变 null**。
配 `models.test.cjs` 7 条钉住：9 个模型非 null、有顶点色、非索引、底部不穿地（`bb.min.y ≥ 0`）、
虎比鹿长、熊比鹿敦实。

### 唯一的假失败，也是本轮最有价值的一条：「疏密」不能用「被压暗的面积」衡量

原断言「100m 等高距覆盖的像素点显著多于 500m」红了，读到反直觉的数
`100m 184 / 200m 96 / 500m 781`。为此写了 `probe2.js`（200×140 = 28000 点，每种等高距
"先关后开"成对差分）与 `probe3.js`（竖直扫描线 900 点/条），先跑**漂移自检 = 0**
（证明采样确定性没问题），再看清：500m / 1000m 时大面积"整片压暗"（`gt35` 占比 79% / 93%），
**已经变成"面"** —— 细线密到一定程度就在屏幕上连成一片，所以"覆盖面积"这个指标**非单调**，
物理上就不成立。

换成**数暗带条数**（扫描线逐点求"关/开"暗度，数下降穿过阈值的连续段）：

| 等高距 | 模型条数 | 三列合计暗带 | 中心列暗带 |
|---|---|---|---|
| 100m | 42 | 108 | **42** |
| 200m | 21 | 55 | **21** |
| 500m | 8 | 24 | **9** |
| 1000m | 4 | 15 | **6** |

中心那条扫描线过山顶、恰好穿过每圈等高线一次 ⇒「中心列暗带 / 模型条数」应 ≈ 1，实测严丝合缝。
这条既证"疏密"又证"像素上真画出了那么多条线"，比面积计数强得多。四条断言：
模型条数单调递减、暗带条数单调递减、中心列与模型量级一致（0.6~1.6 倍 + 4 条余量）、
面板文本随等高距同步。

### 验证与上架

- 纯逻辑：**82 项**（zonation 56 + runoff 19 + models 7），rolldown 打 CJS 后 node 跑。
- 真机：`.workbuddy/tmp/mzverify/shot.js` **54 项断言 0 失败**，18 张截图全部非空（233~376 KB）。
- 上架：`publish_zones.py` → zip 0.20 MB（顶层 `manifest.json` + `web/`，5 文件，自检 entry/cover 真实存在）。
  **7070 id=70 / 17070 id=9，v0.1.0 ACTIVE**，教师端 `GET /store/games` 双端可见。
- `requiresRoster:false` 没法端到端读到：`/store/games/{code}/manifest` 要**先装后取**，
  而 install 需要**激活码兑换**出的 entitlement（7070 返回 `ENTITLEMENT_REQUIRED`），
  云端的 install 对所有游戏（weather_quiz / landform_quiz 同样）都 500 —— 平台既有问题，与本次无关。
  结论：该字段是**包内 manifest 原样透传**（`GameStoreService.installedManifest()` 直接
  `readManifest()` 返回字符串，管理端上传也不改写它），前端 `GamePage.tsx` 读
  `manifest.requiresRoster === false` 跳过选人 ⇒ 包里写着就成立。
- 上架脚本回显的 `requiresRoster=None` 是**接口没暴露该字段**，不是包里没写 —— 别被误导去改包。

**本轮修掉的 5 处游戏本体真实缺陷**（都是真机回归抓出来的，不是看着不顺眼改的）：

  现在落在 782m（离带界 552m）Δ=0。
