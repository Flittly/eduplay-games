## geo_gomoku 1.0.1 → 1.1.0：坐标新增「下拉选择」输入方式，已双端上架

需求：经纬度输入除手动输入外，再加一种「下拉框选度数（等间隔）+ 另选半球符号」，手动输入保留。

### 做法（核心是"不新增第二条校验路径"）

- `src/geo.ts` 新增 4 个纯函数：
  - `axisDegreeOptions(kind, range)` —— 该轴格线度数的**绝对值**升序去重（= 下拉框那一列）。
    窗口连续 ⇒ |度数| 必是 0,5,10,… 的等差数列；跨 0° 线时同一绝对值出现两次（±5）故必然去重，
    所以跨线棋盘是 14 档而不是 15 档。
  - `composeDegreeInput(kind, degree, hemi)` —— 把两个选择合成**手动输入也能识别的文本**（`北纬30°`）。
    0° 时合成 `赤道 / 本初子午线`，不带半球。
  - `defaultHemi(kind, range)` —— 取本轴**实际存在**的第一个半球（单半球棋盘的默认值不会一上来就必错；
    跨 0° 线的棋盘两个半球都在，默认北纬，学生想去南边得自己切）。
  - `hemiOptions(kind)`。
- `src/GeoGomoku.tsx`：
  - `HideModeSwitch` 泛化成通用 `SegmentedSwitch`（格线标注 / 输入方式 共用一套类名与外观）。
  - 新增 `AxisField` 组件：`手动输入` 出文本框，`下拉选择` 出 `<select>`（每 5° 一档）+ 两个半球按钮 +
    一行小字提示；0° 时半球按钮置灰并提示"不用再选半球"。
  - `axisText(kind)` 在提交前把两种方式**汇成同一句话**再交给 `parseDegreeInput` —— 下拉框因此
    不可能成为后门，也不可能出现"同一个交点换个输入方式结果不一样"。
  - 落子后清空下拉（连点两次确认只会撞"该交点已有棋子"，把读书练习变成报错练习）。
- 样式：`.degree-picker / .degree-select / .hemi-options / .degree-picker-tip`；
  `select` 关掉原生外观（`appearance:none` + 两个渐变拼的实心三角），否则圆角灰块跟粗野派视觉不搭。

  1357 档窗口 × 两条轴，把每条格线翻译成(度数+半球)再 `composeDegreeInput` 合成，必须解析回原值。

  defaultHemi 写死 → 红 4 条。确认新断言不是空跑，然后重跑 `rolldown` 还原。
- `shot.js`（Electron 指真实 `dist/web`）加到 **158 项**断言：新增 E2（下拉结构 / 选项逐个等于棋盘格线度数 /

## china_relief（山河塑形·中国地形）v0.0.1：新游戏从开发到双端上架

需求（用户原话）：一张中国地图，拖动旁边的山脉/地形区卡片来学地形区与山脉；
要有积分规则；地形要尽量真实还原、拖对后地图上起伏起来；有颜色；点开有图片和介绍。
知识范围：四大高原 / 四大盆地 / 三大平原 + 27 条山脉（其中 5 条括号内为"了解性"）。

定名 **「山河塑形·中国地形」**，`gameCode: china_relief`，`requiresRoster: false`
（纯展示型、不做点名，所以必须是 `false` 才能跳过选人页）。38 张卡 = 11 地形区 + 27 山脉。

### 技术要点

- 地形：AWS Terrain Tiles (Terrarium)，`h = R*256 + G + B/256 − 32768`；
  用**等距圆柱 + cos(36°) 经度修正**，保证 DEM 网格与顶点索引一一对应。
- 拖对后按"卡片海拔增量"抬升真实地形；拖错给方向提示。
- 照片：38 张实景照片随包发布（`public/assets/photos/<id>.jpg`），全部来自 Wikimedia Commons。
- 纯逻辑（`src/game.ts` / `src/geo.ts`）用 rolldown 打成 CJS 供 Node 断言，`npm run test:data` **62 项**。

## 澄清「是不是换了 MySQL」：三套存储的辨识与取证

用户假设：「商城其实是本机测试的，Windows 上有两个 MySQL（本机 3306 / Docker 3307），
以前用 Docker 的、现在用本机的，所以数据对不上」。**结论：方向对了一半，具体机制不对。**

### 真相：eduplay 有三套存储，只有两套跟游戏有关

| 存储 | 位置 | 谁在用 | 内容 |
|---|---|---|---|
| **H2 文件库** | `eduplay/backend/data/eduplay.mv.db` | **本地 7070** | **11 款游戏全在这里**（本地商城根本不碰 MySQL） |
| **MySQL 库** | `localhost:3306/eduplay_cloud` | **云端 17070** | 云端商店数据（补齐后 12 行 / 11 款） |
| MySQL（Docker） | `localhost:3307`，容器 `mysql` | 研究生项目 / nacos | 只有 `conductor`、`nacos_config` |

配置出处：
- `backend/src/main/resources/application-local.yml` → `jdbc:h2:file:./data/eduplay`（默认 profile=local）
- `server/src/main/resources/application.yml` → `${MYSQL_URL:jdbc:mysql://localhost:3306/eduplay_cloud...}`

⇒ **用户"看到数据库里都有"的那份 = 本地 7070 的 H2 文件库**，不是任何 MySQL。
另外 17070 虽叫"云端"，进程跑在本机、连的也是本机 MySQL —— 是**用本机模拟云端**（这半句直觉是对的）。

### 脚手架上的两条通用经验（已写进 skill `frontend-visual-verify`）

## china_relief 1.1.0 → 1.2.0：低难度随机预置 / 分类专练 / 地形轮廓开关

用户三条原话：①「现在的模式一上来就是空白的，难度有些高，可以开发低难度模式，就是图上已经有了很多的地形，只需要补充上面的没有的即可，**每次随机**」②「高原、盆地、平原、山脉**同时可以分**，地图上只缺少高原/盆地/平原/山脉，针对性训练」③「希望在地形的周围能够有颜色区分开……可以设置一个**开关**，有轮廓或者没有轮廓」。

### 设计收敛：① 和 ② 是同一件事，只做一个 `preset` 集合

两条需求表面不同（"预置一部分" vs "只留某一类"），落到代码都是**「有一批条目不由学生完成」**。
新增 `src/plan.ts`，只产出两个集合：

- `required` = 本局**要学生塑的** —— 进度分母、结算判据、上报 `totalCount` 用它；
- `preset`   = **一进场就已在图上的** —— 老师划的起点，**不计分、不记归属**。

`scope`（全部/只练高原/盆地/平原/山脉）× `start`（空白地图/随机预置）两条选择各自只回答一个问题，
十种组合全部自然成立。范围之外的**整类**直接进 `preset`，这就是"地图上只缺山脉"的实现方式。

**`EASY_KEEP = 0.6` / `MIN_REQUIRED = 2`**：38 张留 23、要塑 15；至少给 2 张（否则这一局没意义）。

### 由此刻意的三个分离

| 分离 | 不做会怎样 |
| --- | --- |
| `preset` ≠ `placed` | 进度条起点不是 0；预置被算成"某人塑的"，分给没动手的人；地块上挂一个无归属的"谁塑的"标记 |
| `isSettled()`（=并集）≠ `isPlaced()`（=只算学生塑） | 两个判断合成一个，必然在一个方向上出错（预置卡要么被当成"学生塑的"、要么被当成"还没做"） |
| `plannedCount()` 独立成函数 | 大厅「本局要塑 N 张」与开局后的进度分母各算一遍 ⇒ 迟早漂，学生第一眼就发现两个数字不一样 |

### 随机必须可注入

`planRound(items, scope, start, rng = Math.random)`：产品传默认值，**回归传 `mulberry32(seed)`**。
否则"每次随机"这条需求在自动化里只能测出"看起来不太一样"，而「换一局确实换了一批」「数量恒等于 23」
都无从断言。有了种子两条都能精确锁死，且不用往产品里塞测试开关。

### 轮廓：归属图 + HSL 描边

- **归属图 `owner`（`Uint8Array`）**：每格记「归哪一条目」（0 = 无，n = 第 n 个条目 + 1）。
  **必须与 `lift`/`add` 同一批格子、同一时刻写入**，否则三者会漂。
- **描边色走 HSL 不是 `rgb × 0.5`**：乘系数**不控制结果亮度**（浅色乘完还偏亮、深色糊成黑），
  13 种条目色的轮廓深浅完全不齐。改成**明度压到固定档 0.26**、饱和度提到 0.62~0.86 ⇒
  13 条轮廓感知深浅一致，只是色相不同。
- **轮廓先于底图分支算**：影像底图下已塑形区是**抠成透明**的，轮廓跟着透明就看不到分界。
- **轮廓 ≠ 档界**：档界表达**海拔**、轮廓表达**归属**；开关**管不着档界**（一刀切会丢掉海拔信息）。

### 归位卡：拖不动，但点得开

`dragRef` 加 `locked` 字段，**在 `pointerdown` 就定下来**（等到 `pointerup` 再判，中间 16 帧幽灵卡已跟出去）。
`locked` ⇒ 不挂幽灵卡；`pointerup` 时没移动过就 `openIntro()`，拖动过则提示「已经在图上了」且不动地图。

## 傍晚：china_relief v1.3.0 · 图鉴（只学不考）

需求原话：「游戏内部缺乏**完整体**，也就是**不需要答题**的图鉴版本，这样学习起来更合理。」
拆开是三件事：① 整幅地形一开始就全塑好（不是残缺地图 + 一摞卡片）；② 全程不答题；
③ 定位是**先学后考**——认全了再切回去答题，所以不能破坏既有两种答题模式。

### 核心设计：图鉴是一份**退化到极点**的 `Session`，不是新状态机

```ts
export function createAtlasSession(allIds: string[]): Session {
  return createSession([], "pick", { required: [], preset: allIds.slice() });
}
```

三个参数各封死一个方向，全是**结构上做不了**而不是 `if` 挡住：

| 参数 | 取值 | 结果 |
|---|---|---|
| `preset` | 全部 38 条 | `isSettled()` 恒真 ⇒ 复用「已在图上：不给拖、但点得开」⇒ **零新交互代码** |
| `required` | 空 | `requiredCount()===0` ⇒ 结算判据 `total > 0 && placed.length === total` 不成立 ⇒ **永不上报** |
| `order` | 空 | `currentId() === NO_CURRENT` ⇒ 提交函数首闸 `studentId < 0` 挡住 ⇒ **不加分/扣分/换人** |

那个 `total > 0` 本是防"空局误判完成"写的，这次正好复用成"图鉴完不成"。

**图鉴是 `stage` 不是第三种 `PlayMode`**：`relay`/`pick` 答的是"这一题谁来答"，图鉴不答题，
塞进 `PlayMode` 会让所有 `switch (mode)` 多一个空分支。所以 `stage: "lobby" | "play" | "atlas"`，
`mode` 仍是 `LobbyPick = PlayMode | "atlas"` 只管大厅按钮取值域，**答题代码一行没动**。

### 聚焦与轮廓是两个字段（不是同一个开关的两档）

`outline` 答"相邻两块地分不分得开"，`focus` 答"现在在看哪一块"。都往同一条像素写色，语义无关：

```ts
const gridOwner = lastScene?.owner ?? null;          // 全量：判归属
const owner = lastScene?.outline ? gridOwner : null; // 受开关控制：上色
const focusTag = lastScene?.focus ?? 0;              // 不受 outline 控制
```

非聚焦 `mul *= FOCUS_DIM = 0.42`（压太狠就只剩"有一块地"，而"哪块高哪块低"本身是教学内容）；
聚焦地块保持原色 + 边缘 `FOCUS_EDGE = [214,48,36]`，且**排在归属轮廓之后**算（否则山脉紫边和朱红打架）。
影像底图单开一支：非聚焦不能压暗（压暗=看不清影像），盖暗纱 `FOCUS_VEIL = 170 / rgb(26,30,38)`。

### 两个必须记住的边界

1. **回大厅必须 `resetTerrain()`**（清 lift/liftTarget/add/addTarget/ownerGrid + focus）：
   图鉴把 38 条全塑上，直接回大厅开"空白地图"会出现**地图看着已塑好、进度却写 0/38**——
   上色判据 `lift > 0 ⇒ 已塑形` 与"本局谁该在图上"是两回事。
   **不能用 `location.reload()` 偷懒**：平台名单是一次性消息，刷新后永远等不到 ⇒ 学生卡在
   "正在等待平台下发学生名单…"。出口还要把 `mode` 切回 `"relay"`（否则按钮写「去答题」却还进图鉴）。
2. **知识卡在图鉴里是左下角浮层**（`.cr-sheet.is-atlas`），不是居中模态——居中正好压住刚聚焦的那块。
   必须写 `pointer-events: none`：`.cr-sheet` 是 `inset:0` 的全屏层（**连侧栏也盖住**），
   不放开侧栏的「下一条」就点不动。

翻页按**完整 38 条目录**而非侧栏当前筛选（图鉴用法就是"通读一遍"），首尾相接。

### 回归抓到的两个真问题（都是首跑才暴露）

1. **半灰**：「练习范围」的置灰打在 `section` 上（只有 `.cr-lobby-box.is-muted > h2` 生效 ⇒ 标题浅了），
   而 CSS 的 `pointer-events: none` 认的是 `.cr-modes.is-muted` ⇒ **按钮看起来正常且照样能点**。
   「起始地图」那处却打对了 —— 对称的两组只对了半组。
   修：两处都写成「外层 section + 内层 `.cr-modes` 双 `is-muted`」，并在探针里补
   `getComputedStyle(el).pointerEvents`（**只查 class 抓不到半灰**），另加一条自检对照
   （现场摘掉 `is-muted` → PE 变 `auto` → 加回变 `none`，证明断言真的在测那个 class）。

   **图鉴里连兜底出来的那个体验学生也没拿到任何东西**（无记分板/答题人条/进度/上报）。

## china_relief v1.4.0（横断山脉 5 条平行岭 / 浅色地形底图 / 地名标注）

用户三条反馈：① 横断山脉应该是**好几条平行的山脉**，现在只画一条；② 底图可以就是
**颜色比较浅的中国地形图**；③ 位置放正确之后应该可以**标注地形名称**，提供可关闭的按钮。

### ①「好几条」不是改数据就算做完的 —— 得在投影上真的数得出来

数据层从 `line` 扩成 `lines`（**5 条**，`lift_half_deg: 0.20` 单独收窄走廊），
`distToRange` / `buildRidge` 都改成"到**最近那一条**"的距离。
**但验收标准不是"数据里有 5 条折线"，而是画面上数得出 5 条** —— 于是连踩三个坑：

**坑一：按真实经纬度摆，5 条必然糊成一片。** 三江并流区真实间距只有 40~60 km，
而塑形走廊半宽默认 0.42°（≈38 km）⇒ 相邻走廊必然重叠、5 条融成一整块高原面。
必须把经度**摊开**到 1.10° 间距、并把走廊收到 0.20°，才留得下河谷缝隙。
代价是每条岭的经度与课本有偏差 ⇒ **所以不逐条命名**（否则"名字标错位置"更糟），
地图上只标「横断山脉」一个名字。

**坑二：走廊在经度方向被放大 1/0.809 倍。** `distToPolyline` 把经度差先乘
`lonScale = cos36° ≈ 0.809` 再算距离，南北向的岭等距线是东西向的 ⇒ 经度方向覆盖
= `(half + fade) / lonScale`，**不是** `half + fade`。第一版漏了这步，
算出的"缝隙 5.8 px"只存在于纸面，真值 3.7 px。

**坑三（最值钱）：窄河谷会被 `drawImage` 的放大插值"渗"掉 —— 是尺子错了，不是数据错了。**
渲染链路是 **480×358 的离屏画布 → `drawImage` 放大到 ~1164×1000**，且
`terrain.ts:695` 显式 `imageSmoothingEnabled = true`（关掉整幅图会变马赛克）。
放大 2.4 倍走双线性插值，两条岭之间那 3~4 格宽的河谷被两侧塑形色"渗"进来，
**逐像素差永远回不到 0**：缝1 谷底 **4**、缝2 谷底 **29**，而两侧峰高 220~340。
拿固定阈值 12 去卡 ⇒ 5 条被数成 4 条。我连着**误判两次**：先怀疑"数据还不够开"
（差点去调间距），再怀疑"轮廓线把缝描掉了"（实测开/关轮廓几乎无差别：
`{3:11,4:22,5:7}` vs `{3:9,4:24,5:6}`）。真因是**判据**。
改成**按行自适应阈值**（低于 `该行峰值 × 0.15` 算断开）后：40 行里 **38 行数出 5 段**，
5 段宽度 11/17/17/18/15 px（岭1 偏窄是因为它南段压在中缅边界上被 `clip_to_land` 裁过）。
→ **教训：断言报"画面上只有 4 条"时，先问一句"我这把尺子量的，是我以为的那件事吗"。**

### ② 浅色地形：未塑形区取**真实高程** `da[k]`，不是塑形后高度场 `hAll[k]`

这样这块地的形状、高低与塑好之后**完全重合**，差别只在浓淡 —— 学生看到的是
"这里本来就长这样，我塑形只是把它从淡变浓"。刻意**不加档界描边与明暗**：
那两样是"已经塑好了"的信号，提前给出去学生就分不清"我塑的"和"本来就这样"。

### ③ 谁该被标名字：`isSettled`（已在图上），不是 `isPlaced`（学生自己放的）

按 `isPlaced` 过滤 ⇒ **图鉴里一个名字都没有**（图鉴 38 条全是预置的），
而图鉴恰恰最需要名字。逻辑抽到 `labels.ts` 的 `pickLabels`（纯函数，7 条 node 断言钉着）。
绘制：必须画在 `drawImage` **之后**；**数组顺序即避让优先级**（贪心 + 包围盒相交跳过）；
白描边 + 深字（底图有 7 档色）；字号跟 `mapScale` 走而不是跟屏幕宽走。

### 顺带修掉的真问题（都是回归逼出来的）

1. **「名称」开关与「轮廓」开关共用 `.cr-basemap.cr-viewopts`，`top: 64px` 完全重叠**
   ⇒ 轮廓**点不动**。拆出 `.cr-labelopts { top: 108px }`，文案改「标注 / 不标」。
2. **大厅「选择底图」成了第 5 个 box ⇒ 被挤到第 2 行、总高超滚动区 ⇒
   第 4 个「遥感影像」整个看不到**（光看截图只会以为底图就三种）。
   并进「起始地图」box（语义上都是"这张地图长什么样"）+ 复用 `is-compact` 两列。
3. **大厅两行开关共用 `.cr-lobby-outline`** ⇒ 探针把 4 个按钮当成一组 ⇒ 第二行改 `.cr-lobby-names`。

## 山河三消 v1.1.0 —— 港澳轮廓细化

用户反馈「香港和澳门的轮廓非常粗，需要更加细致的数据」。查下来是**两层问题叠在一起，
而且只修任何一层都不够**。

### 第一层：数据被"用坏"了（源数据本身没问题）

港澳原先跟着全省走 `simplify(3800 m)` + `round()` 到整数。整张数据只有 1200 单位宽
（1 单位 ≈ 5.3 km），澳门真实跨度 7.1 × 11.9 km ⇒ 取整后 47 个顶点**只落在 4 个不同位置**上。
旧产物里澳门的 `d` 就是 `M727,740L727,740L727,740L727,740Z` —— **一条零长度的路径**。
所以澳门原来不是"粗"，是**压根没有形状**。

修法：新写 `shanhe-match3/scripts/prepare_data.py`（与 province-puzzle **同源同投影同尺度**，
只适配输出 schema：本游戏没有 centroid、bbox 是 viewBox 的 `[x,y,w,h]` 写法），
加 `SMALL_AREA_OVERRIDES = {"810000": (120.0, 0.00001, 2), "820000": (50.0, 0.00001, 2)}`。
修前先量过面积可信度：源数据香港 1110 km²（官方 1114.57，−0.4%）、澳门 35 km²（+5.1%）；
DataV/高德香港 +15.6%、澳门 +59% 且澳门只有 84 顶点 ⇒ **不换源，修参数**。

### 第二层：描边是 viewBox 单位，会跟着要素一起放大

牌面 svg 拿**该要素自己的 bbox** 当 viewBox 单独缩放（`preserveAspectRatio=meet`），
`stroke-width: 2` 要乘缩放倍数 ⇒ 要素越小描边越粗：

| | bbox | 牌面缩放 | 旧描边 | 形状短边 | 描边/形状 |
|---|---|---|---|---|---|
| 澳门 | 1.59 × 2.41 | 27.8 px/单位 | **55.6 px** | 44 px | **126%** |
| 香港 | 12.19 × 10.02 | 5.58 | 11.2 px | 56 px | 20% |
| 上海 | 23 × 27 | 2.48 | 5.0 px | 57 px | 8.7% |
| 北京 | 34 × 38 | 1.76 | 3.5 px | 60 px | 5.9% |

修法：`src/gameData.ts` 加 `bboxSize()` + `TINY_BBOX = 22`，`styles.css` 加
`.tile-shape.is-tiny path { stroke-width: 1.1; vector-effect: non-scaling-stroke }`。
阈值前把所有 34 个对象排了序（`tiny_budget.cjs`）：只圈中港澳（2.41 / 12.19），下一个是上海 27。

### 判据演进（本轮最值钱的部分）

- 第一版拿「轮廓卡里红像素占比 <0.35」当判据 → **失败（实测 44.5%）**。真因是**我的尺子错了**：
  香港 34 个岛的海岸线极曲折，周长/面积比很高，1.1 px 的细描边总面积本来就和填充同量级。
  改成**匹配物理尺度**的量：**描边宽 ÷ 形状短边**（22.2% → 2.2%；200% → 2.7%）。
- 真机牌面是**分层叠放、每局随机**的，目标卡取景框会被相邻牌盖住一部分 ——
  同一份**旧产物**两次跑出「红 434 / 墨 0」与「红 9 / 墨 450」，量级差两个数量级。
  ⇒ 像素量只作辅助证据，硬判据放在**计算样式 + 几何量**上；要干净的像素对照另做隔离页。

### 隔离对照页（A/B/C/D 拆开两个因素）

`.workbuddy/tmp/match3verify/host/_shapeproof.html` 四个面板，每个 svg 就是真机 68×67 px：

| 红占比 | A 旧数据+旧描边 | B 只调描边 | C 只调数据 | D 都调 |
|---|---|---|---|---|
| 香港 | 97% | 24% | 98% | **41%** |
| 澳门 | 100% | 100%（只剩 **34 px**） | 100% | **22%** |

**澳门 B 只剩 34 px** 正是"旧数据是零长度路径"的铁证 —— 光修描边只会让它消失。
这个 2×2 也证明了单一改动（C 或 B）都还是粗的。合成图 `对照-港澳轮廓四组合.png`（8× 放大）。

## 省级行政区识别（province_quiz）v1.1.0 —— 港澳轮廓细粒度化

用户原话：「省级行政区识别游戏更新：v1.1.0：这个游戏里面的香港和澳门的轮廓也非常的粗，
需要更加细致的数据来作为识别的轮廓。」

**注意区分**：这是 `province-quiz`（中文名就叫「省级行政区识别」），不是上一轮的
`province-puzzle`（「行政区拼图」）。11 款游戏的中文名查法：
`for d in */; do python -c "...manifest['name']..."`。

### 三层根因（比上一轮多一层）

| 层 | 根因 |
|---|---|
| **数据** | `provinces.json` 是 province-puzzle 的**派生副本**，而那个生成器只是一个 **29 行拷贝器**、没有自检；上游 v1.0.0 修好港澳后**这里一直没重跑** |
| **描边** | `stroke-width` 是 viewBox 单位 + 轮廓 svg 拿要素自身 bbox 取景 ⇒ 要素越小描边越粗 |
| **取景**（新发现） | 取景边距里有个**常数 `+12`**，对澳门（长边 2.41）＝ 框的 **96% 是空白**，轮廓只画成 18×27 px 的小红点 |

⇒ **「只修数据」毫无改善**：澳门 200% → 125.8%、香港 22.2% → 20.0%，画面几乎没变。

### 修法

### 新踩的坑（都很值钱）

1. **`--check` 必须校验磁盘上那份，不是刚构造的 payload**。第一版把"与源逐字节比对"跑在
   新构造的 payload 上 ⇒ 恒为 34/34，等于什么都没查。改成校验 `current` 后立刻抓到
   **32/34 + 退化环 2 个/1 个**。
2. **`non-scaling-stroke` 的描边不能再乘缩放**。度量写成 `strokeWidth × k` 把 1.5px 算成
   37.6px ⇒ 假失败。更糟的是解析 bug 让形状短边变成 `-Infinity` 时，
   `1.5 / -Infinity === -0 ≤ 0.05` 让断言**恒真（假绿）** ⇒ 断言里必须显式带
   "度量是有限正数"这一条。
3. **`d` 解析别写 `split(/[\s,]+/)`**：那会把 `740.96,730.74` 拆成两个 token，
   再 `split(",")` 拿到 y=undefined ⇒ NaN ⇒ 全跳过 ⇒ bbox 停在 ±Infinity。
   只按空白切。修完用"与数据 bbox 逐一对表（34/34 零偏差）"自证。
4. **本机 bash shim 会改写 heredoc 里的反斜杠与反引号**：`r"version:/s*[`\"']"` 被改成
   `r"version:/s*[/"']"` ⇒ 正则永不命中 ⇒ 得出一条"版本指纹不存在"的假结论。
   **凡含反斜杠/反引号的校验脚本一律写成文件再跑**，别内联 heredoc。
5. **旧产物基线：v1.0.0 的 zip 没留存**，改用 `.workbuddy/tmp/pkcheck/www-province`（v0.3.3）
   —— 先核它的 CSS 是 `stroke-width:2px`、JS 里 viewBox 公式 `×0.08+12`，与 v1.0.0 完全一致，
   并把它"含旧澳门零长度路径"作为数据层也是旧的证据。
6. **Electron 脚本三段式**：`report.steps` 漏初始化 ⇒ check() 首句 TypeError ⇒
   promise 拒绝而**进程不退**（表现成"跑了几分钟没有任何输出"）。必须
   `whenReady().then(run).then(exit, catch)` 且 catch 里也写报告 + exit。
7. **打包自检要分别验 JS 与 CSS**：渲染层修复一半在 JS（`silhouette-path is-tiny`）、
   一半在 CSS（`non-scaling-stroke`），只查一边会漏。

### 一局覆盖全部行政区的普查法（值得复用）

大厅有「本局题目数 10/20/34」，选 **34 题** 就 `shuffle(FEATURES).slice(0,34)` = 全部 34 个，
**不用调 `Math.random` 种子**、一局即可：既验港澳修好，又验其余 32 个 viewBox 与旧公式
**逐字节相同**（"没误伤"的排他性证据）。探针逐题从 DOM 读 viewBox / `getComputedStyle` /
`getScreenCTM()`，并把 34 行像素账打出来 —— "港澳从最粗两个变成最细两个"一眼可读。
