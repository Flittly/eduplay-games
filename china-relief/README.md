### v1.5.2 及以前画布是**故意不接**点击的

源码里那行注释写着理由：

```ts
/* 地图本身不接点击：介绍只能靠"放对"或"点卡片"拿到，
   否则随手点一下就把答案点出来了。 */
<canvas ref={canvasRef} />
```

这条顾虑是对的 —— 地图上把 38 块地形都画好了（图鉴）或者都画了一部分（答题），
任何一处能点开就说明那一块"能点"，学生随手一扫就能把答案点出来。

用户这次要的正是它的**安全版本**：不是"点地图就能看讲解"，而是"点**已经在图上的**能看讲解"。
`session.ts` 里现成就有这个判据：

```ts
export const isSettled = (s: Session, id: string) => s.placed.includes(id) || s.preset.includes(id);
```

- 答题模式：`placed` 是学生自己放对的，`preset` 是本局预置的 —— 合起来正好是用户说的
  「已经填好、地图上已经有对的要素和文字」；
- 图鉴模式：会话由 `createAtlasSession` 造，38 条全塞进 `preset` ⇒ **`isSettled` 全真**。

**两条需求共用同一句判据**，不需要给图鉴写第二个分支。这也是这一版唯一真正新增的"过滤"。

### 命中判定必须与视觉同源（这是本轮最容易做错的地方）

"点哪儿算点到它"不能另起一套标准，否则会出现"看着是一条带子却点不中""点着这块地弹出隔壁那条山"。
所以三条判定路径各取自己**画出来时用的那个范围**（新模块 `src/pick.ts`，纯逻辑、可 Node 回归）：

| 顺序 | 路径 | 范围取自 | 说明 |
| --- | --- | --- | --- |
| ① | 地名带（名字优先） | `ANCHOR_RADIUS_DEG = 0.375°` | 点在名字附近就先认这一条 |
| ② | 走带（山脉） | `geo.corridorHalfDeg(range)` | 与塑形用的**同一个函数**（`RIDGE_LIFT_HALF_DEG + RIDGE_LIFT_FADE_DEG`） |
| ③ | 归属格（地形区） | `regionGrid[grid] === area.gridId` | 与落点判定查的**同一张位图** |

②排③前的理由：走带是画在色块**上面**的那条凸起带（`ownerGrid` 里山脉也是后写、覆盖地形区）。
反过来的话，27 条山脉里二十多条会被压在某个地形区底下（昆仑山 / 祁连山 / 喜马拉雅全在青藏高原的格子里），
"点地图上的要素"在图鉴里就落空了。实测最大压盖比是**青藏高原 30.3%**。

⚠️ **不能拿 `RANGE_TOL_DEG`（0.55°）当点击容差**：那是**落点**容差，刻意比走带宽
（0.55 vs 0.50，横断山脉只有 0.28），是留给学生的宽容度。拿它做命中会让山脉把手伸到自己带子外面，
把周围地形区整片吃掉（点塔里木盆地弹出天山），而且只在边缘一带发生，最难归因。
回归里有一条断言专门盯这层窗口。

### 顺手救了一个实测冲突：长江中下游平原 ↔ 大别山

"名字优先"这条规则不是想出来的，是被一个实测数字逼出来的：
`长江中下游平原` 的锚点离 `大别山` 脊线只有 **0.31°**，比走带半宽（0.5°）还近。
没有这条规则就是"点着「长江中下游平原」那几个字，弹出大别山"。

半径 `0.375°` 的三个边界**全是量出来的**：

- **下界 0.31** —— 被走带盖住的锚点里，离脊线最远的那一个（就是上面这一对）；
- **上界 0.53** —— 全图最近的两个锚点（长江中下游平原 ↔ 大别山）相距 **1.06°**，超过一半就互抢；
- **越小越好** —— 半径会从山脉走带里"拿走"一小块：`0.375°` ⇒ 0.32% 的走带格；
  放到 `0.6°` 涨到 0.78% 并开始吃到巫山。

实测锚点带只占全部命中的 **3.2%**，是条支路，不是主路径。

### 顺带修掉一个真问题：锚点带对山脉要再截一刀

回归第一版报红：`【关键】山脉走带之外、落点容差内不命中山脉` ⇒「误命中 1 条：横断山脉→anchor」。

原因：横断山脉的走带只有 **0.28°**（`lift_half_deg: 0.20 + FADE 0.08`），比锚点带半径 0.375 还窄，
于是"名字附近"伸到了画出来的带子外面 —— 破坏了"点得中 = 画得出"这条不变量。

修法不是放宽断言，是改实现：

```ts
const reach = t.range ? Math.min(ANCHOR_RADIUS_DEG, corridorHalfDeg(t.range)) : ANCHOR_RADIUS_DEG;
```

地形区没有这一刀（它自己就是一大片）。修完 27/27 条山脉的探针点全部命中自己，误命中 0。

### 光标反馈是"地图可点"唯一的提示

地图点击是个**既不报错、也没有别处反馈**的交互：点在米灰上什么都没发生，
与"点在要素上但没点准"在画面上长得一模一样。所以指针移到能点开的地方时画布变手型：

```ts
<canvas
  ref={canvasRef}
  className={`cr-canvas${pickable ? " is-pickable" : ""}`}
  onClick={onMapClick}
  onPointerMove={onMapHover}
  onPointerLeave={() => setPickable(false)}
/>
```

用 `click` 而不是自己记 down/up：语义就是"同一点按下又抬起"，拖卡片松手不会走到这儿。
这个类用的**与点击同一个**命中函数，所以不会"光标是手型却点不开"。

（176 = 浮层底距 38 + 三条浮层最高 130 + 8px 气口）

### 为什么这次让卡片、上一版却是让按钮条

v1.5.1 里写过"让位的是按钮条而不是知识卡"，理由是卡片是**内容**、挪窝会改掉
「点右侧目录 → 看左下角实景照片」的动线。这次反过来让卡片挪，并不矛盾 ——
**挪的不是卡片的动线，是它的纵向位置**：卡片仍贴左侧、仍随目录点击出现，
只是整体上移 158px。左列从「卡片独占」变成「卡片在上、按钮条在下」，
卡片并没有离开左下角这一列。

反过来若继续让按钮条留在右上，用户那句"左下角的空地比较多"就没被满足。
两轮反馈要的是同一件事，第二轮只能靠让卡片来达成。

### 176 是按**最坏情况**算的

`--cr-corner-reserve: 176px` = 浮层的 `bottom: 38`（给「影像来源」小字让的）
+ 三条浮层最高形态总高 130（实测 48 / 35 / 35 + 2×6 间隙）+ 8px 气口。

"最高形态"指密钥**没配**的时候：那时「底图」条多一行「需密钥」才是 48px，
配好之后整叠矮 13px，实际间隙只会更大、不会反过来压住卡片。

⚠ 这个数只在"按钮条与卡片同底"时成立。实测 `.cr-stage` / `.cr-root` / `.cr-sheet`
三者底边都是 1000（差 0），所以一个常量就够。谁要往 `.cr-corner` 里加第四条，
必须回来重算 —— `geom.js` 把 `.cr-corner` 的真实高度量得出来，用不着猜。

### `max-height` 必须跟着一起减

卡片是**贴底生长**的（`align-items: flex-end`）。底边被 `margin-bottom` 钉死之后，
高度就是唯一的位移方向 —— 只改 margin 不改 `max-height` 的话，讲解文本一长，
卡片会顶着底边往上顶穿顶栏、长到屏幕外去。所以：

```css
max-height: calc(100% - var(--cr-corner-reserve) - var(--cr-card-top-gap));
margin: 0 0 var(--cr-corner-reserve) 18px;
```

`--cr-card-top-gap: 80px` = 图鉴顶栏底边（实测 y=72）+ 8px 气口。
当前卡片实测 503px，离这个上限（744px）还有 241px 余量，所以**没有一条讲解被截断**
（`.cr-sheet-body` 本来就是 `overflow-y: auto`，真到那天也只是内部滚动）。

### 回归判据改成「矩形两两不相交」

`atlas.js` 里 v1.5.1 那条「图鉴里必须留在右上角」已作废，换成四条从**期望行为**写的
断言，一条都不读实现里的 left/right/top/bottom：

1. 图鉴里浮层**贴左下角**（左边距 ≤ 20、下边距 ≤ 60、整体在左半区）；
2. 浮层与**知识卡**不相交；
3. 浮层与**卡片底部那行按钮**也不相交 —— 真正不能被压住的是它；
4. 卡片让位之后**没有钻进顶栏底下**。

第 3 条是这轮新加的：v1.5.1 只盯了"与整张卡片不相交"，但卡片是个大矩形，
"压住它中间"和"压住它底部那行按钮"对用户是两件事 —— 真正点不动的是按钮。

另外那条 v1.3.0 的老断言「卡片贴底 ≤ 60px」也跟着改了：它写死的是**当时**的实现，
卡片让位后 `bottomGap` 从 18 变成 176。现在判的是"仍以左下角为锚"（左边贴近 +
水平中心明显偏左）+ "底边还在舞台下半区"，用舞台高度当分母，不再写死绝对值。

### 顺带修掉一个藏得更深的挖洞漏网

`overlayRects()` 里那条 `.cr-sheet-card`（图鉴的知识卡，纸底 392×503）**从来没被挖掉**，
一直被当成"陆地"像素数进所有统计。v1.5.1 时卡片还压在左下角的海面上，混进去的多是
海色，影响小到没露馅；v1.5.2 卡片上移 176px 后压在**西北内陆**上，亮纸底把"陆地均亮"
直接抬高：

| | 聚焦前 | 聚焦后 | 差 |
| --- | --- | --- | --- |
| 不挖卡片（错的口径） | 159 | 146 | −13（断言要求 ≥ 15） |
| 挖掉卡片（对的口径） | 159 | **126** | **−33** |

判据本身是"两个状态的差"，看着天然免疫位置变化 —— 但**分母里混进了 UI**，
差就会跟着 UI 走。上一轮的 `labelopts` 与这一轮的 `sheetCard` 是同一类漏网，
每加一个浮层都要回来查一遍名单。

### 那句「空地比较多」说的是**答题模式**，图鉴里左下角不空

> 下面保留的是 v1.5.1 当时的判断与依据（数字已按本轮复量校正）。

图鉴模式的知识卡就钉在左下角（`.cr-sheet.is-atlas` 是 `align-items: flex-end` +
`justify-content: flex-start`，卡片 `margin: 0 0 18px 18px`）。真机实测卡片是

为什么当时让位的是按钮条而不是知识卡：两条性质不同 —— 知识卡是**内容**，

> 注入一段把 `.cr-corner` 打回旧摆位的样式，两帧相减。脚手架 `ab.js` 可复跑，
> 原始数字在 `.workbuddy/tmp/crverify/ab-report.json`。早先注释里记的 3px / 10px 是错的

密钥配好之后「遥感影像」那条少一行、矮 13px，各自写死 `top` 的话下面两条就都悬空了。
回归里有一条断言专门盯这个 —— **两条间隙彼此相差 ≤ 2px**（改前是 2 与 9）。

### `bottom: 38px` 那个数是量出来的

「影像来源」那行小字（天地图署名，只在遥感影像 + 瓦片取到时出现）是 `bottom: 10px`
的固定定位，真机实测占 **y 968~989、高 22px**，顶到距底 32px；底图条留 6px 气口 ⇒ `38`。

前提是那行小字**永远只占一行**，所以顺带给它加了 `white-space: nowrap` 与写死的

### ② 那层白为什么不好看 —— 不是审美问题，是它和「分层设色」相冲

关键在 `fadeToWhite(c, k) = (1-k)·c + 255k` 是一条**仿射**映射：
它把**任何**色差一律乘 `(1-k)`，陆地 k=0.62 ⇒ **一律乘 0.38**。实测七档相邻色的 ΔRGB：

| 档 → 下一档 | 原色间距 | 淡 62% 后 | 保留 |
| --- | --- | --- | --- |
| 低地绿 → 黄绿 | 58 | 22 | 38% |
| 黄绿 → 土黄 | 43 | 17 | 40% |
| 土黄 → 橙褐 | 46 | 18 | 39% |
| 橙褐 → 褐 | 84 | 33 | 39% |
| 褐 → 灰褐 | 81 | 32 | 40% |
| 灰褐 → 雪白 | 274 | 105 | 38% |
| **平均** | **97.7** | **37.8** | **39%** |

七档色淡完之后全挤进 `(206~247, 204~245, 187~242)`（原色是 R 127~233 / G 122~228 / B 77~221），
相邻档只差 17~33、摊到三通道每通道 6~11 —— **贴着"看不出区别"的边上**。

截图实测吻合：地图里占面积最大的两种陆地色是 `(238,220,194)` 与 `(206,225,198)`，色差 32，
而它们原本是"橙褐"和"低地绿"两个八竿子打不着的色相。

⇒ 结论不是"淡一点不好看"，而是**这套淡化方式与分层设色本身冲突**：
分层设色靠的就是色相差异，而向白插值做的是等比例压缩所有色差。
真要"浅"，该压的是饱和度而不是往白里兑 —— 但那已经是另一套调色了，而且
**用户要的就是原色**，所以没有理由再做一层。

#### 代价：这张底图上"塑形"的信号换了

未塑形区现在**原色**（不给档界描边、不给明暗），已塑形区是同一套色**加上**那两样。
所以塑形的反馈从「由淡转浓」变成「**浮出档界描边与明暗**」。

- 好处：档界（＝等高线）本身压得住七档的接近，是比"浓淡"更准的信号；
- 代价：**开局的辨识难度比 `relief` 低** —— 想让学生"没放之前什么也看不见"，
  用 `relief`（未塑形是米灰斜纹）。这一条是 v1.4.0 就接受的取舍，v1.5.0 只是不再糊着。

顺带一处**不能忘的连带影响**：地名标注是「白描边 + 深字」，v1.4.0 那会儿七档色被压到
R 206~247 的浅区间，深字本来就都读得出来；现在恢复成 R 127~233，**白描边的必要性回到 v1.3.0 的水平**
（雪白档会吃掉浅字、褐档会吃掉深字）。`drawLabels` 一行没改，但别把它当成多余。

### ① 「好几条」不是改数据就算做完的 —— 得在投影上真的数得出来

把 `line` 换成 `lines`（5 条折线）只完成了一半。用户抱怨的是**画面**上看着只有一条，
所以真正的验收标准是「**5 条脊之间那 4 道河谷在地图上看得见**」。这里连着踩了两个坑：

**坑一：按真实经纬度摆，5 条必然糊成一片。**
真实的三江并流区，相邻两条岭只隔 40~60 km（0.3~0.5°），而塑形走廊半宽就有 0.42°（≈38 km）——
相邻走廊**必然重叠**，5 条融成一整块高原面，"看着还是一条"的老问题原封不动。
所以经度必须摊开。最终定在**间距 1.10°**、并把横断山脉的走廊单独收窄到
`lift_half_deg = 0.20`（其余山脉仍是默认的 0.42°）。

代价是每条岭的具体经度与课本位置有偏差。既然位置本来就摊开了，
**就不该再逐条写山名** —— 否则"名字标错位置"是个更严重的教学错误。
所以地图上只有「横断山脉」一个标签。

**坑二：走廊在经度方向被放大了 1/0.809 倍。**
`distToPolyline` 把经度差先乘 `lonScale`（= cos 36° ≈ 0.809）再算距离，让距离在地理上可比。
南北向的岭，等距线是东西向的，于是走廊在**经度方向**的实际覆盖是

```
(lift_half_deg + RIDGE_LIFT_FADE_DEG) / lonScale      ← 不是 lift_half_deg + RIDGE_LIFT_FADE_DEG
```

第一版就是漏了这一步，算出"缝隙 5.8 px"自我感觉良好，真值只有 3.7 px。
这个数落到了断言里（`game.test.cjs`），换算口径写明来源，别改成拍脑袋的阈值：

| 间距 | 走廊 `half` | 单边覆盖（经度） | 缝隙 | ≈ 屏幕像素 |
| --- | --- | --- | --- | --- |
| 0.85° | 0.25 | 0.371° | 0.108° | ≈ 1.5 px（糊） |
| 1.00° | 0.22 | 0.371° | 0.258° | ≈ 3.7 px（看不清） |
| **1.10°** | **0.20** | **0.346°** | **0.408°** | **≈ 5.8 px** ✔ |

换算成像素要除以 **14.3 px/°**，这个数来自"地图区约 902 px 宽 / 取景 73~136°E"，
`shot.js` 里另有一条实测断言与它同源。**这个游戏的地图不能缩放**（`mapScale` 由画布尺寸
算出，没有 wheel/zoom），所以学生看到的就是全图比例，一切都要按它算。

⚠️ 上表的"≈屏幕像素"是**画布 CSS 口径**。回归（`shot.js` / `countBands`）是在
1500×1000 的**窗口帧**上量的，中间隔着 `frameScale` 那一层，帧里 1° 对应
**≈17.7 帧 px**（`report.json` 的 `notes["P3.bands"].win`：窗口取经度 98.2~103.4 共 5.2°，
落在帧里宽 92.2 px）。同一段 0.408° 的缝隙，CSS 上是 5.8 px、帧上是 **7.2 px** ——
两个数都对，只是别拿一个口径的数去对另一个口径的阈值。`countBands` 之所以
**逐像素扫、不隔点采样**，就是因为 7.2 px 在帧里也不算宽裕。

**坑三：窄河谷会被 `drawImage` 的放大插值"渗"掉 —— 判据不能拿固定阈值卡。**

回归数"5 段"用的是「塑形前后逐像素比，沿东西向剖面数连续变化段」。但渲染链路是
**480×358 的离屏画布 → `drawImage` 放大到 ~1164×1000**，而
`ctx.imageSmoothingEnabled = true`（`terrain.ts:695`，是显式设的，关掉整幅图会变马赛克）。
放大 2.4 倍走的是**双线性插值**，于是两条岭之间那 3~4 格宽的河谷会被两侧的塑形色
"渗"进来，**逐像素差永远回不到 0**：

| 河谷 | 谷内格心数 | 谷底 diff | 两侧峰高 |
| --- | --- | --- | --- |
| 缝1（4 格） | 4 | **4** | 220 |
| 缝2（3 格） | 3 | **29** | 339 |

拿固定阈值 12 去卡，缝2 就断不开 ⇒ **5 条被数成 4 条**。第一版跑出"中位数 4 段"时
连着误判了两次：先怀疑"数据还不够开"（差点去调间距），再怀疑"轮廓线把缝描掉了"
（去关轮廓，实测 `{3:11,4:22,5:7}` → `{3:9,4:24,5:6}` —— 几乎没变）——
两次都不对，是**尺子不对**。

判据改成**按行自适应**：低于 `该行峰值 × 0.15` 才算断开。这样量的是"看得出几条
明暗条带"，而不是"有几段逐像素严格相等" —— 谷底 29 相对峰高 339，学生一眼就
看得出那是条暗缝。改完 40 行里 **38 行数出 5 段**（另 2 行为 6 段，是边界噪声），
5 段宽度 10/16/16/16/15 px（岭1 偏窄是因为它南段压在**中缅边界**上被 `clip_to_land`
裁过，这是对的）。另配一条"5 段宽度相仿"（最大/最小 ≤ 2.5），挡住"一大块 + 4 个碎条"
也能凑出 5 段的假通过。

**这条的教训比数据本身值钱**：断言报"画面上只有 4 条"时，先问一句
"我这把尺子量的，是我以为的那件事吗"。

另外两条是为了让"5 条"真的出现在同一屏里：

- **5 条必须真正平行**（每条岭 `Δlon/Δlat` 都是 0.10）。若各条斜率不同，
  间距会随纬度变化，北边悄悄压窄，"缝隙 5.8 px"只在南端成立。
- **纬度覆盖留大片重叠**，使 5 条同时可见的区间达到 27.60~29.60°N（2.0° ≈ 29 px 高）。
  南端停在 27.60 而不是数据里的 26.40，是因为第 1 条在 98.4°E 那一段压在**中缅边界**上，
  被 `clip_to_land` 裁掉了 —— 这是对的，山岭不该画到国界外。

### 横断山脉不参与 DEM 拟合，不是偷懒

`fit_ridges.py` 里对它直接 `continue`。全国 DEM 是 11.9 km/格，相邻两岭只隔约 50 km ≈ 4 格，
断面上找"局部最高点"时最高点会在几条岭之间随机跳（今天落在沙鲁里山、明天落在大雪山），
中值滤波也救不回来 —— 结果是**把 5 条平行岭揉成 1 条歪线，比手绘还错**。
这类"网格分不开的地形"，地理知识比 DEM 可靠。

### ② （v1.5.0 已改写，保留是因为另一条结论仍然成立）未塑形区取的是**真实高程**

`soft` 底图的分支里，未塑形地块取的是 `da[k]`（真实 DEM 高程）而不是 `hAll[k]`（塑形后高度场）。
这样这块地的**形状、高低和塑好之后完全重合** —— 学生看到的是"这里本来就长这样，
我塑形只是把它（**描出来**）"，而不是"我塑形让地形变了形状"。

同样刻意**不加档界描边与明暗**：那两样是"这块已经塑好了"的信号，提前给出去，
学生就分不出"我塑的"和"本来就这样"了。

> ⚠ 这两条在 v1.5.0 **一个字没改**，但上面那句"差别只在浓淡"已经不成立 ——
> 淡化被拆了，现在的差别**全在**"有没有档界描边与明暗"。详见上面的 v1.5.0 §②。

### ③ 谁该被标名字：判据是 `isSettled`，不是 `isPlaced`

`labels.ts` 的 `pickLabels` 只标**已经在图上**的条目。这里容易写错：

- 按 `isPlaced`（学生自己放的）过滤 ⇒ **图鉴里一个名字都没有**（图鉴的 38 条全是预置的），
  而图鉴恰恰最需要名字；
- 按 `isSettled`（`placed ∪ preset`）⇒ 答题时预置的条目自带名字、学生放对的立刻浮出名字、
  图鉴里 38 条全标。

这段逻辑从 App.tsx 的 `useMemo` 里搬到了 `labels.ts`，就是为了能被 node 测试覆盖 ——
它坏掉的样子截图看不出来（少一个名字的画面"看起来也很正常"）。
`game.test.cjs` 里有 7 条断言钉着它，包括"图鉴场景 38 条一个不少"（用真实数据跑）。

### 标签的绘制与避让

- **必须画在 `drawImage` 之后**。`render()` 是逐像素写 `ImageData` + 一次 `drawImage`，
  画在前面会被整句 `drawImage` 静默盖掉。
- **数组顺序就是避让优先级**：`drawLabels` 按顺序画，与已画过的包围盒相交就跳过。
  所以 `pickLabels` 把"刚放对 / 刚点开的那一条"排第一位 —— 保证"放对了"的即时反馈
  不被邻居的名字吃掉。
- **白描边 + 深字**：底图有 7 档色（深褐→雪白），单用浅字会在雪白档消失、
  单用深字会在褐档糊掉；描一道白廓等于给每个字自带衬底。
- **字号跟 `mapScale` 走**（`min(16, max(11, mapScale * 0.72))`），不跟屏幕宽度走 ——
  否则小窗口里的字相对地图会显得巨大。

### 图鉴不是「又一套状态」，是一份**退化到极点**的 `Session`

最直觉的做法是给图鉴单开一套 `atlasState`（哪些条目看过、当前聚焦谁……）。
但图鉴要回答的问题（"这块地在图上了没有""现在在看哪一块"）和答题模式**完全是同一批问题**，
另开一套等于把同一件事回答两遍，两边还会各自演化出不一致的边界情况。

所以图鉴是把既有的 `Session` 推到极限 —— 三个参数各封死一个方向：

```ts
// src/session.ts
export function createAtlasSession(allIds: string[]): Session {
  return createSession([], "pick", { required: [], preset: allIds.slice() });
}
```

| 参数 | 取值 | 封死了什么 |
| --- | --- | --- |
| `preset` | **全部 38 条** | 每条 `isSettled()` 恒真 ⇒ 落到既有规则「已在图上：不给拖、但点得开」⇒ **图鉴零新交互代码** |
| `required` | **空** | `requiredCount()` 为 0 ⇒ 结算判据 `total > 0 && placed.length === total` **结构上不可能成立** ⇒ 永远不会上报 |
| `order` | **空** | `currentId()` 恒返回 `NO_CURRENT`（−1）⇒ 所有提交函数的第一道闸门 `studentId < 0` 挡住 ⇒ 不可能加分、扣分、换人 |

注意这三条都不是"加个 `if` 让它别做"，而是**让它做不了**。
结算判据里那个 `total > 0` 本是当初为防"空局误判完成"写的，这里正好复用成"图鉴结构上完不成"。

### 图鉴是 `stage`，不是第三种 `PlayMode`

`relay` / `pick` 回答的是「**这一题谁来答**」。图鉴根本不答题，把它塞进 `PlayMode`
会让所有 `switch (mode)` 的地方都多一个空分支。所以图鉴改的是 `stage`：

```ts
type LobbyPick = PlayMode | "atlas";                        // 大厅按钮的取值域
const [stage, setStage] = useState<"lobby" | "play" | "atlas">("lobby");
const atlas = stage === "atlas";
```

`mode` 仍然只表示两种答题方式，答题相关的代码一行都没动。

### 聚焦与轮廓是两个开关，回答两个问题

v1.2.0 的 `轮廓` 回答"**相邻两块地分不分得开**"，图鉴的聚焦回答"**现在在看哪一块**"。
两者都往同一条像素上写颜色，但语义毫不相干，所以 `SceneView` 里它们是两个字段：

```ts
interface SceneView {
  owner?: UShortArray | null;   // 归属轮廓（受 outline 开关控制）
  focus?: number;               // 聚焦条目（不受 outline 开关控制）⚠️
}
```

渲染时把归属图拆成两个变量，各取所需：

```ts
const gridOwner = lastScene?.owner ?? null;          // 全量：判"这块地属于谁"
const owner = lastScene?.outline ? gridOwner : null; // 受开关控制：拿来上色
const focusTag = lastScene?.focus ?? 0;
```

着色策略：非聚焦地块整体压暗 `FOCUS_DIM = 0.42`，聚焦地块保持原色、边缘换朱红 `FOCUS_EDGE`。
0.42 是权衡出来的 —— 压得太狠（比如 0.15）就只剩"这里有一块地"，
而"**哪块高哪块低**"本身也是图鉴要教的内容，得留着看得出来。

聚焦的着色**排在归属轮廓之后**算，于是朱红能盖住同色系描边（否则山脉的紫边会和朱红打架）。

遥感影像底图下还有一条单开的分支：影像里"非聚焦"不能照设色底图那样压暗（压暗＝看不清影像），
改成盖一层半透明暗纱 `FOCUS_VEIL = 170 / rgb(26,30,38)`。

### 从图鉴回大厅必须把沙盘清空

图鉴把 38 条全塑上（`liftTarget` 全 1）。若直接回大厅再开一局**空白地图**，
会出现"**地图看上去已经塑好、进度却写 0/38**"—— 因为上色判据是 `lift > 0 ⇒ 已塑形`，
它跟"本局谁该在图上"是两回事。

所以出口必须先 `resetTerrain()`：

```ts
const resetTerrain = useCallback(() => {
  lift.fill(0); liftTarget.fill(0); add.fill(0); addTarget.fill(0);
  ownerGrid.fill(0);
  setFocusTag(0);
  sceneRef.current.focus = 0;
  viewRef.current?.refresh(data.alt, lift, add, false, basemapRef.current, sceneRef.current);
}, [lift, liftTarget, add, addTarget, ownerGrid, data]);
```

**不能用 `location.reload()` 偷懒**：平台下发的学生名单是一次性消息，刷新后名单不会再来，
学生会永远停在"正在等待平台下发学生名单…"。

同理，出口里必须把 `mode` 切回 `"relay"` —— 否则按钮上写着「去答题」、
`mode` 却还是 `"atlas"`，点下去又进图鉴。

### 知识卡在图鉴里是"浮在地图左下角"，不是居中模态

图鉴的重点是"**一边对着地图看它在哪、一边读它是什么**"。居中模态会把刚聚焦出来的那一块
正好压住（舞台铺满整个界面，居中卡片盖的正是中原一带），学生得先关掉卡片才能看地图。

所以复用同一个 `.cr-sheet`，加 `is-atlas` 改成左下角浮层、无遮罩：

```css
.cr-sheet.is-atlas { align-items: flex-end; justify-content: flex-start; padding: 0; background: transparent; pointer-events: none; }
.cr-sheet.is-atlas .cr-sheet-card { pointer-events: auto; width: min(392px, 100%); margin: 0 0 18px 18px; }
```

`pointer-events: none` 这条是必须的：`.cr-sheet` 是 `inset: 0` 的全屏层（**连侧栏也盖住**），
不放开指针事件，卡片一出现侧栏的「下一条」就点不动了。

### 翻页按**完整 38 条目录**，不按侧栏当前筛选

「上一条 / 下一条」走全部条目的次序，而不是侧栏当前分组的结果 ——
图鉴的用法就是"从第一条翻到最后一条通读一遍"，中途因为侧栏还停在某个分组而翻不动会很别扭。
首尾相接：最后一条的「下一条」回到第一条。

### 「完整体」的判据必须逐条落到锚点像素

"整幅地形都在图上了"用一个"米灰总占比 < 2%"是撑不住的：
**不属于这 38 条的陆地**（东南丘陵、东北山地这些没进目录的地方）本来就是米灰，
再叠上"用了哪种底图""挖掉了多少浮层"的影响，占比这个数说不出到底缺了哪一条。

改成用 `scripts/_geo.cjs` 的 `lonLatToCanvas` 算出 38 个锚点，各取 5×5 邻域量"非米灰比例"，
逐条判定 `shaped.length === 38`。再配一条对照：**同一批锚点在空白地图开局时应当全部变回米灰**
（这就是"回大厅清沙盘"的证据）。两个数一起看，"图鉴 = 38 条全在图上"没有别的解释。

### 新玩法里，"不该出现的东西"比"该出现的东西"更能说明问题

图鉴的回归里专门有一组断言查**负空间**：记分板不在、答题人条不在、进度条不在、
「本局待塑」分组不在、提示/换人按钮不在 —— 汇总成一个 `answerOnlyChrome()` 探针。

"地图上有 38 条"只证明塑形做对了；"一个答题浮层都没有"才证明它真的是图鉴，
而不是"某一局所有人都答完"的画面。这两件事在学生眼里长得几乎一样，含义却完全不同。

### ① 和 ② 在实现上是同一件事

需求①和需求②表面是两条（"预置一部分"、"只留某一类"），落到代码里都是**「有一批条目不由学生完成」**。
所以只做一个 `preset` 集合，而不是写两套机制：

```ts
// src/plan.ts
export function planRound(items: PlanItem[], scope: Scope, start: StartMode,
                          rng: () => number = Math.random): RoundPlan {
  const inScope = (it: PlanItem) => scope === "all" || it.scopeKey === scope;
  const poolIds = items.filter(inScope).map(it => it.id);

  // ① 低难度：只从"范围内的池子"里抽，抽中的进 preset
  const keep = new Set<string>();
  if (start === "easy" && poolIds.length > 1) {
    const floor = Math.max(1, Math.min(MIN_REQUIRED, poolIds.length - 1));  // 至少留 2 张
    let keepCount = Math.round(poolIds.length * EASY_KEEP);
    if (poolIds.length - keepCount < floor) keepCount = poolIds.length - floor;
    for (const id of shuffled(poolIds, rng).slice(0, keepCount)) keep.add(id);
  }

  // ② 分类专练：范围之外的**整类**都预置 —— 这就是"地图上只缺山脉"的实现方式
  const presetSet = new Set<string>(keep);
  for (const it of items) if (!inScope(it)) presetSet.add(it.id);

  return {
    required: items.filter(it => inScope(it) && !presetSet.has(it.id)).map(it => it.id),
    preset:   items.filter(it => presetSet.has(it.id)).map(it => it.id),
  };
}
```

一条范围选择、一条起始地图，各自只回答一个问题，组合起来十种情况全都自然成立
（只练山脉 × 空白地图 = 27 条山全要塑；只练山脉 × 随机预置 = 地形区全给、山脉抽掉四成）。

### `preset` 与 `required` 是两个**语义不同**的集合，不能合成一个

- `required` = 本局**要学生塑的**：进度分母、结算判据、上报 `totalCount` 都用它；
- `preset` = **一进场就已在图上的**：老师划的起点，**不计分、不记归属**。

由此派生出一对刻意分开的判断：

| 函数 | 含义 | 界面用途 |
| --- | --- | --- |
| `isSettled(id)` | `placed ∪ preset` | 「这块完成了没有」—— 卡片灰掉、进度条 |
| `isPlaced(id)` | 只算学生塑的 | 「这块是谁塑的」—— 成绩与归属 |

把两者合成一个 `placed` 会立刻出两个错：预置卡被记成"学生塑的"（分给了没动手的人），
或者预置卡被当成"还没做"（学生被要求塑一块本来就在图上的地形）。
**"还在不在场上"和"算不算谁的功劳"是两件事。**

### 随机必须可注入，否则这条需求没法回归

`planRound(…, rng = Math.random)`：产品传默认值，**回归传 `mulberry32(seed)`**。
否则"每次随机"这条需求在自动化里只能测出"看起来不太一样"，而"换一局确实换了一批"
（以及"数量恒等于 23"）这类断言根本无从下手 —— 有了种子就两条都能精确断言。

`plannedCount(items, scope, start)` 也被单独抽出来：大厅文案「本局要塑 N 张」与
开局后的进度分母**必须出自同一个算法**，各算一次迟早会漂。

### 归位卡：拖不动，但点得开

预置卡在界面上是"已经在图上了"，所以**不允许再拖**（拖了等于重复塑形）。
但它仍然要能点开看讲解 —— 卡片里的介绍本来就写着"本局开局时就已经在图上 ✓"，
那个字段存在的意义就是"能点开看"。所以 `dragRef` 加了 `locked`：

```ts
const locked = isSettled(s, item.id);   // 在 pointerdown 里算，而不是在 pointerup 时
// locked ⇒ 不挂幽灵卡、不跟手；pointerup 时若没移动过就 openIntro()，若拖动过则提示
// 「「XX」已经在图上了」，并且不动地图。
```

`locked` 在 `pointerdown` 就要定下来：等到 `pointerup` 再判，中间那 16 帧幽灵卡已经跟出去了。

### 轮廓的着色：从「rgb × 0.5」改成 HSL

最初的写法是把条目色乘以 0.5 压暗。问题是**乘一个系数不控制结果亮度**——
浅色乘完还是偏亮、深色乘完直接糊成一团黑，13 种条目色的轮廓深浅完全不齐。

改成把明度**压到固定档**、饱和度反而提上去：

```ts
outlineRGB(rgb) => hsl(h, s * 0.9 + 0.2, 0.26)   // 明度固定 0.26，不再是被乘出来的
```

这样 13 种轮廓的感知深浅是一致的，只是色相不同 —— 学生看到的"分界"是一样清楚的一条线。

### 轮廓**先于**底图分支算

遥感影像底图下，已塑形区是**抠成透明**的（露出影像）。如果轮廓跟着透明，
换到影像底图就看不到任何分界了。所以轮廓描边在底图分支**之前**画，任何底图下都在。

同时要说清一件事：**轮廓 ≠ 档界**。档界（7 个 200/500/1000/… 米色档之间的描边）
表达的是**海拔**，轮廓表达的是**归属**；轮廓开关**管不着**档界。两条信息各说各的，
把开关做成"一刀切全关掉"就把海拔信息也丢了。

### 大厅：内容区滚动 + 底部固定操作栏

加上「范围」和「起始」两组选项之后大厅变高，「开始塑形」的中心被挤到 y=1006
（视口高 1000）—— `elementFromPoint` 返回 `null`，**按钮点不到了**。
本质是：`position: sticky` 的底栏在外层内边距加在滚动容器上时，滚动区会把底栏露出来。

改成外层定高的 flex 列 + 内层 `overflow-y:auto`：

```css
.cr-lobby      { display:flex; flex-direction:column; overflow:hidden; }
.cr-lobby-inner{ flex:1 1 auto; min-height:0; overflow-y:auto; }  /* 内边距挪到这里 */
.cr-lobby-foot { flex:0 0 auto; border-top:2px solid var(--line); }  /* 「开始塑形」常驻 */
```

并补两条断言守住：「开始塑形完整落在视口内」「把大厅内容滚到底，按钮位置一动不动」。

### 两条刻意定下的规则

- **答错不换人**（两种模式都是）。如果答错就换人，学生很快会发现「答错＝把难题丢给下一位」
  比自己想更划算，于是乱丢一气 —— 那是把规则设计成了反激励。放错扣 5 分已经足够让
  「想清楚再放」划算，不需要再动用换人。
- **联动的是地图、不是回合**。全班塑的是同一幅图，所以「这块是谁塑的」在卡片上标出来
  （`session.owner`），结算页说得出每个学生塑成了几张。

> **v1.0.0 的两条仍生效**：① 三维换卡通 —— 摘掉 three.js，整层换成 **Canvas 2D 俯视分层设色**。
> 原实现是 480×358 的真实高程网面（约 34 万个三角形），每帧要重算 17 万个顶点的高度与颜色、
> 动画收尾还得重算法线（20~50 ms），在教室那类没有独显的机器上就是明摆着的卡顿。而这个游戏
> 真正要教的东西 ——「这块地按它真实的海拔被塑起来了」—— 并不需要透视相机：**分层设色 + 档间描边
> + 北向明暗** 在俯视图上就读得出来，而且这正是地理教科书读地形图的方式。
> ② 点地图不弹介绍（随手点一下就把答案点出来了），介绍只从「放对」和「点卡片」两个口子进。

### 为什么影像底图必须用天地图，以及密钥为什么不能写进代码

这是要发给学校、随包离线运行的中国地图产品。境内地图产品的影像底图有明确的合规要求，
境外图源一律不能用；「国家地理信息公共服务平台（天地图）」是自然资源部主管的官方平台，
属于可以用的那一小撮。

但天地图要密钥，而**密钥不能写死在随包发布的代码里** —— 明文密钥会被抓包、会被盗用，
也没法给不同学校分别配。所以 `basemap.ts` 里只有 `{tk}` 占位符，密钥由老师在界面上填一次、
存在浏览器本地（`localStorage`），**既不分发也不上传**。

顺带一个必须说清楚的取舍：天地图是**在线服务**，校机室没网就取不到。所以另两种底图完全由本地
DEM 算出来，断网照常可用；影像取不到时也会明确说一句并自动切回分层设色，
而不是留一张空白沙盘让人猜。

### 影像怎么落到我们的画布上

天地图 `img_w` 是标准 Web Mercator 瓦片（256 px），而我们的地图是**按 cos(36°) 修正的等距圆柱**。
两者都是「经纬度 → 平面」的映射，所以每个瓦片在我们画布里仍是一个**轴对齐矩形**，按四个角算位置即可。

要留意的是**瓦片内部的畸变**：Mercator 在纬度方向不等比，把它整块拉成「纬度均匀」会在瓦片内部
产生误差，且随瓦片纬度跨度**平方**增长。z=5 时约 2~3 km（不到一个网格 11.9 km 的五分之一，
肉眼不可见），z=4 就涨到 15 km 左右 —— **所以缩放级别不能随便降**，`pickZoom` 的下限是算出来的。

配准是回归里的一条硬断言：把瓦片的画布坐标**反算回经纬度**，必须回到这个瓦片本该覆盖的范围
（实测最大偏差 0.0000°）。这类错误在画面上只会表现为「影像和等高线差了几十公里」，
看着只像「图有点糊」，很难归因。

### 接口怎么接

平台侧（`eduplay/frontend/src/pages/GamePage.tsx`）：

- `GAME_INIT` 下发 `roster`（`requiresRoster !== false` 时老师选完学生才发）；
- 游戏侧报 `GAME_COMPLETE`（**每人一条**，带 `roundId` 做幂等）；
- 全部结束后报 `GAME_SESSION_COMPLETE`（平台据此出成绩榜并切回「再选一批学生」）。

体验模式（游戏包被单独打开、没收到名单）下**一条都不发** —— 虚拟学生的学号不在平台的
选择名单里，发了只会让平台弹「游戏返回的学生不在本次选择名单中」。

## 积分规则

| 项 | 分值 |
| --- | --- |
| 地形区基础分 | 20 |
| 山脉基础分 | 12 |
| 尝试系数 | 第 1 次 1.0 / 第 2 次 0.6 / 第 3 次起 0.3 |
| 连击奖励 | 连续 3 次「一次答对」额外 +15 |
| 放错 | −5（**不**计入尝试次数，所以不会被一次手滑毁掉满分） |
| 要提示（在图上闪一下位置） | −8，并把该条目记成「多试了一轮」（随后放对只拿 6 成） |
| 分数下限 | 0 |

评级按**一次答对率**给，不是按绝对分数 —— 这样拖得慢不会吃亏。

**多人模式下这些分记在「当时那位答题人」头上**：地图共用，分数各记各的。
`session.ts` 给每个人留一整份 `GameState`（而不是只留一个总分），因为记分规则本身
带状态 —— 同一张卡第几次才放对、当前连击、一次答对率 —— 这些都要按人算。
复用 `game.ts` 那套函数，等于复用已经回归过的规则，不必为「多人版」再写一份会走样的积分代码。

### 预置在图上的是「起点」，不是「成绩」

v1.2.0 的低难度 / 分类专练会一进场就摆好一批条目。这些**一分不记、也不记归属** ——
它们代表"老师给的起点"，不是"学生做出来的"。所以上报的 `totalCount` 用的是 `required`（要塑的）
而不是 `pool`（在场的），结算页的分母、进度条、评级全都只认学生自己塑的那些。
**如果把预置也算进去，低难度模式就会变成"什么都没干就先得了 23 张的功劳"**，
那恰恰和"降难度"的初衷相反 —— 要降的是操作量，不是把分数白送出去。

同一张地图在两局里预置不同批次，也是刻意的：**每局重抽**保证学生不能把"预置了哪 23 张"
背下来（否则低难度模式会退化成"记住答案"）。

### 提示里的「+N」必须等于记分板加的分（曾经不一致）

提示文案要报「这一次加了多少分」，而记分板上的数字由 `applyCorrect` 算。
这两处各写一个常数，就会出现「提示写 +20、记分板只加 12」——
用过提示的条目要乘 0.6 系数，学生一比对就发现对不上，然后就不信提示了。

现在只有一处算法：`game.ts` 的 `gainFor(state, id, kind)`，`applyCorrect` 复用它，
提示也调它。回归里用属性测试锁死（6 个状态 × 2 类 × 3 条目 = 36 组逐一比对）。

配套的一条坑：`handleDrop` 只在 `state.placed` 变化时重建，学生用过提示之后
`placed` 没变，闭包里拿到的 `attemptOf` 还是旧的。所以另有一份 `stateRef` 镜像，
提示取的是它的当前值。

## 数据管线（`/` 全离线，运行时不需要联网）

- **DEM 来源**：[AWS Terrain Tiles](https://registry.opendata.aws/terrain-tiles/)（Terrarium 编码），
  公有领域、免 key。解码 `h = R*256 + G + B/256 − 32768`。
- **取景框**：73–136°E / 17–55°N（保证曾母暗沙以北、黑龙江主航道以南都在框内），
  **480 × 358** 格，约 11.9 km/格。
- **编码**：整数米 → `Uint16` 小端 → base64，整块 **476 KB**，内嵌进 bundle。
  不做 zlib：实测压缩率只有 0.77，却要把解码变成异步、换来一个 loading 态和一堆
  `await`，省那点体积不值这个复杂度。
- **陆地遮罩**：1 bit/格（放对但落在海里要拦住；**v1.0.0 起画布点击已整条取消**，
  这张掩膜现在只服务于「落点是否在陆上」的判定与渲染描边）。
- **区域位图**：**4 bit/格**，记「这一格属于哪个地形区」。见下面「为什么查位图」。

## 关键设计决策

### 为什么是「按 cos(36°) 修正的等距圆柱」，不是 Albers

游戏要把经纬度栅格上的 DEM **逐格**搬到像素上，并在同一套索引空间里做着色与落点判定。
等距圆柱下网格 `(i,j)` 与画布像素一一对应，全都退化成查表；换成 Albers 就得给每个
像素做反投影，精度省下的那点形变远抵不过复杂度。

x 方向乘 `cos(36°)` 之后，南北与东西的**地面米数比例**与真实一致 ——
这是「中国看起来没有被横向拉长」的关键。副产品：1° 经度 ≈ 90 km，
所以 `distanceHint` 里算距离用的就是 `dLon * 90`，和地图自己的横向缩放同源。

二维版把这条又简化了一步：`terrain.ts` 的 `layout()` 只算一次
`scale = min(宽 / SPAN_X, 高 / SPAN_Z) × 0.96`，`pick()` 与 `project()` 都是它的
线性反演 —— 没有相机、没有射线求交、也没有"按地表高度迭代收敛"。代价是失去了
旋转与缩放视角；收获是**判定坐标与学生看到的画面必然同源**，
而且回归里可以拿"画布上的陆地像素数"去对"掩膜算出的期望值"（±8%），
投影/缩放/掩膜三者只要有一个不一致就会红。

### 落点判定为什么查「区域位图」而不是「离中心点多近」

地形区是有面积的。学生把「塔里木盆地」丢到天山北边的准噶尔去，按中心距离可能
也算「近」；查位图则直接问「**这一格到底属于谁**」—— 判定口径和地图本身完全一致。

位图按「**小面积优先**」生成，于是柴达木盆地这种嵌在青藏高原内部的盆地也能各归各位
（不然一个格子只能写一个编号，柴达木会被青藏高原整个吞掉）。回归里有一条断言
专门验「各区格数之和 = 非零格数」，也就是**互斥**。

### 山脉为什么要「走廊 lift + 高斯 add」两层

全国 DEM 是 11.9 km/格，太行山、南岭这种宽 50~80 km 的山脉在这个尺度上只剩
三四个格子，**光靠 DEM 立不起来**。但**完全不用 DEM 也不行**——那样山脉就只是
一条按「叠加米数」上色的扁平色带，既不是起伏的地形，颜色也和它真实的海拔对不上
（秦岭真高 2000 m，画出来却是 0~680 m 的草绿）。

所以：

- `lift` 遮罩把**走带走廊**整条按真实 DEM 塑出来（半宽 0.42° ≈ 47 km，往外 0.08° 收干净）
  —— 太行山那道「山西高原 vs 华北平原」的断崖、台湾中央山脉，都是这么自己长出来的；
- `add` 再沿折线叠一条高斯脊（σ = 0.24°，峰 900 m），把脊线挑出来，让窄山脉在
  这个网格精度下也读得出「一条脊」。

⚠️ `add` **必须裁进走廊**（乘上 lift 遮罩）。不裁的话高斯尾巴会拖到 1.08°，而那里
`lift = 0`、着色退化成「只按叠加米数上色」——肉眼看到的就是山体外面围了一圈草绿晕。
这条是放大截图之后才发现的，缩略图上根本看不出来。

### 「海拔」与「视觉高度」是两份数组

`elevationOffset`（真值，进判定与读数）与 `verticalExaggeration`（仅渲染）必须分开。
`raw` 只读 / `alt = max(0, raw + offset)` / `visualY = alt * exag` 只在顶点处算一次。
混在一起会立刻产生「山高 9000 米」这类荒谬读数。

- 主图取景 73–136°E / 17–55°N，**南海诸岛按规范另附小图**（十段线 + 岛礁，共 157 条路径）。

  随机预置的**数量恒等于 `round(0.6 × n)`**（不是"差不多"）；

  `plannedCount()` 与 `planRound().required.length` **处处相等**（大厅分母与开局分母同源）；

- 用 `capturePage` / `paint` 取帧做像素直方图
- **点开卡片真的能看到照片**：`img.naturalWidth > 0`、src 指向 `assets/photos/qingzang.jpg`，

- **38 张卡片的照片对着产物逐一点名**。缺一张不会报错 —— `onError` 会把它藏掉、

- **陆地像素总数 vs 掩膜算出的期望值**（±8%）。v1.0.0 那次的头号 bug

- **v1.2.0 三条需求各有专属断言段**（N1 / N2 / N3，共 37 条）：

    HUD `0/27` → 「本局待塑」27 张 → **锚点取样**（见下）→ **预置卡拖不动 + 点得开**。
  - **N2 低难度**（12 条）：大厅 `已有 23 / 要塑 15` → HUD `0/15` →
    **连开两局，预置那 23 张不是同一批**（`presetNamesA ≠ presetNamesB`）→
    数量两次都恒等于 23 → 地形区与山脉**两类都抽到过**。
  - **N3 轮廓开关**（8 条）：默认开 → 关掉 → **逐像素配对比较**全是变亮 →
    深色像素同坐标比较 `onlyB = 0` → 再打开**回到原样（差 0 px）** →
    遥感底图下轮廓**仍然不透明可见**（`onlyA ≥ 800`）。

### 锚点取样：断言尺度必须匹配物理尺度

N1 最初写成「在青藏高原窗口里量米灰占比」——窗口半径 40，**一格地形在画布上只有 2.33 px**，
半径 40 横跨 34 格 ≈ 400 km，量到的是隔壁（已预置的黄土高原）。行为完全正确，断言红了。

改成**以每个条目的锚点为心、半径 10（≈9 格）的小窗口**再取全部 38 条的中位数。
尺度对了之后，N1 的判据变成一个**双峰结构**（`hiShares ≥ 11 / midShares ≤ 2`），
而不是"每条待塑山脉下面都该是米灰"——因为**13 条山脉的锚点本来就落在已预置的地形区里**
（昆仑 / 喀喇昆仑 / 唐古拉 / 喜马拉雅 / 巴颜喀拉 / 冈底斯在青藏高原内，
太行 / 六盘 / 贺兰在黄土高原内）——**"山脉往往是地形区的界"，这恰恰是正确行为**。

> 通用教训：**断言的尺度不能凭感觉给**。先问"我这个窗口在物理上覆盖了多少东西"，
> 再决定窗口多大；否则量到的不是被测对象，而是它的邻居。

### 深色集合差 > 绝对深色计数

N3 一开始判断"轮廓关掉后深色像素应变 0"，实测**还剩 590 个**。那 590 个是记分板 /
答题人条 / 说明条的文字（`--ink` = `rgb(36,31,24)`）—— 用"挖掉这些矩形"的办法删不掉
（浮层矩形挖不干净）。改用**同坐标比较两帧的深色集合**：

```js
darkDelta(a, b, …) => { onlyA, both, onlyB }
// onlyA = 只在前一帧深 ⇒ 就是被关掉的那些轮廓线
// both  = 两帧都深 ⇒ 恒定 UI，自动排除，不需要手写 skip 列表
// onlyB 必须为 0（关轮廓不该让任何像素变深）
```

实测 `onlyA 2833~3779 / both 189~224 / onlyB 0`，判据干净。
（`both` 那么小是因为每个像素都带抗锯齿过渡，真正的"纯深"很少；
这也说明**深色计数本身对阈值极敏感**，而集合差对它几乎不敏感。）

顺带把阈值 `DARK_LUM` 从 70 改成 **75**，依据是**枚举定义域**而不是单样本外推：
13 种条目色经 `outlineRGB()` 后亮度落在 **59.0~73.3**，档界描边亮度 **77.2**，
75 正好卡在两者中间。

> 通用教训：**阈值要枚举定义域**（把所有取值算一遍，看缝隙在哪），
> 不要"看到一个样本是 70 就把阈值设成 70"。定义域一变，单样本外推的阈值必然失守。

### `brighter + darker === changed` 是错的完备性假设

N3 原本断言"变化的像素清一色变亮"，写成 `brighter + darker === changed`。
实测 `brighter + darker < changed` —— 因为**像素放大插值后会有"非亮非暗"的过渡像素**
（变的一半亮一半暗，整体亮度不变）。

改成分类判据：`brighter + darker >= changed * 0.95 && brighter >= changed * 0.9`。
**分类是"排他但不必穷尽"的**——两个类别互不重叠，但不要求覆盖全集。
把"不重"当成"不重不漏"来写，就会凭空造出一条永远过不了的断言。

### 回归抓到过的九个真问题（都不是写测试时就能想到的）

**v1.2.0（227 项真机回归）抓到三个**：

7. **大厅「开始塑形」被挤出视口**（已在上文"大厅"一节详述）。加了 4 组选项后大厅变高，
   按钮中心落在 y=1006 > 视口 1000 ⇒ `elementFromPoint` 返回 `null`，真鼠标点不到。
   **加选项的改动没有让任何一条旧断言变红** —— 是"用真鼠标点掉大厅"这条流程断言钉出来的。
8. **舞台底图条缺语义修饰类**。新加的「轮廓」开关复用了 `.cr-basemap` 的外观，
   于是探针 `querySelectorAll(".cr-basemap button")` 从 3 个读出 **5 个**，
   旧断言「三种底图齐全」直接红。产品侧加 `is-base` 修饰类、探针改用
   `.cr-basemap.is-base` —— **复用样式可以，复用选择器不行**。
9. **预置卡点不开讲解**。`locked` 卡在 `pointerup` 里只判了"没移动就别拖"，忘了"没移动就该
   `openIntro()`"，于是预置卡成了"既拖不动也点不开"的死物。断言改成
   「从已归位卡片进来，给的是**已经归位那段**介绍」并显式 `closeSheetIfOpen` 收尾。

**v1.1.0（179 项真机回归）抓到三个**：

4. **渲染视图的 effect 少了一个依赖**。`useEffect(..., [data, lift, add])` 里判断
   `if (!canvasRef.current) return` —— 而 v1.1.0 起进场先落大厅，那一刻画布根本还没挂载。
   于是 effect 跑了一次就永远不再跑，进图后**地图一帧都不画**，
   `canvas.width` 停在默认的 300×150。数据、算法全对，界面上就是一片空白。
   **这是"把单屏游戏改成先过一屏"时最容易埋进去的坑**：依赖数组里的都是稳定引用，
   唯一会变的是「现在到哪个阶段了」。加上 `stage` 依赖 + `if (stage !== "play") return`。
5. **`satelliteNote` 从来没有被渲染**。取不到影像时会 `setSatelliteNote("…已切回…")`，
   但 JSX 里没有一个地方读它 —— 承诺的"取不到时说清原因并自动切回"只做了一半，
   老师只会以为底图按钮坏了。补一条常驻说明条（`.cr-note`）。
6. **虚拟学生的 id 撞上了哨兵值**。`currentId()` 用 **`-1`** 表示「没有当前答题人」，
   `commitCorrect` 第一道闸门是 `studentId < 0` ⇒ 忽略。而体验模式的虚拟学生
   `GUEST_ROSTER` 用的恰恰是 `studentId: -1` —— 整局**每一次落位都被静默丢弃**：
   提示、讲解、动画全正常，地图纹丝不动。改用 `999999001`，
   并把哨兵抽成具名常量 `NO_CURRENT` 加警告注释。
   （**哨兵值和真实 id 共用一个值域，就迟早会撞**；能用具名常量就别写字面量。）

**v1.0.0 抓到三个**：

1. **落偏方向提示整体指反**。`distanceHint` 里 `dLat = anchor[1] - lat` 是「从落点走到
   锚点要走的位移」，符号直接就是该走的方向；实现里写成了落在南边提示「往偏南找」。
   学生照着走只会离目标更远，而界面上完全看不出是 bug，只会觉得「这提示没用」。
   修的是符号，同时补了四个方位的断言（既要报对、也不能同时报出反方向）。
   顺带发现合成方位拼成了「往偏南偏偏东方向找」——`join("偏")` 把两个「偏」叠起来了，
   改为中文习惯的「东南 / 东北」（**东西在前、南北在后**）。
2. **提示里的 `+N` 与记分板不一致**（见上文积分一节）。
3. **山脉是一条扁平草绿带**，且走廊外还有一圈绿晕（见上文山脉两层隆起）。

### 回归写成**假绿**的一次（这个更危险）

上一轮真机回归里有一条断言叫「实景照片缺失时有兜底文案（不是一片破图）」——
它一直是绿的，而那一轮的 `host/web` 里**根本没有 `photos/` 目录**：
`server.log` 里明明白白记着 `GET /web/assets/photos/qingzang.jpg → 404`。

问题在于断言问的是「照片丢了会不会优雅降级」，而不是「照片在不在」。
于是**一张照片都没有的情况下，整份回归依然全绿**。
假红只浪费一次排查，**假绿会把缺陷直接放进交付物**。

改法：断言换成期望行为本身 ——「真的解码出来了（`naturalWidth > 0`，src 指向正确文件）」，
再把兜底那条单独留一条断言守着。两条各管一件事。

### 回归写成假红的两次（记录，避免再犯）

- 「可见陆地像素必须变少」——直觉是高原抬高会遮挡北侧地表，实测是 `377628 → 379142`
  （**变多**）：新增的南坡/西缘可见面积大于被遮挡的北侧面积。断言方向反了。
- 「山脉走带主色必须变」——山脉在屏幕上只有约 30 px 宽，80×80 窗口的主色**永远**是
  带子周围的米灰。改成剔掉米灰像素后求**带子自己**的均值才测得到。

### 实景照片

脚本在 `scripts/` 下。**跑这些脚本要用带 Pillow 的解释器**
（裸 `python` 里没有 PIL，会直接 `ModuleNotFoundError`）：

```bash
PY="C:/Users/Administrator/.workbuddy/binaries/python/envs/default/Scripts/python.exe"

"$PY" scripts/fetch_photos.py --sheet        # 补齐缺的，并出拼版缩略图
"$PY" scripts/fetch_photos.py --force        # 全部重取
"$PY" scripts/fetch_photos.py --only=taihang --force
"$PY" scripts/pick_photos.py --only=yinshan  # 出**检索结果**候选拼版（挑图用）
"$PY" scripts/sheet_selected.py --pinned     # 复核**已钉定**的 COMMONS_PICK 全部条目
"$PY" scripts/fetch_photos.py --avoid=<url片段> --force   # 拉黑某图源后重取
```

`pick_photos.py` 和 `sheet_selected.py` 是复核回路的两半：前者拼**检索结果**（挑的时候看），
后者拼**你钉死的文件名**（复核的时候看）。少一半的话，"钉进去之后到底下到了哪张图"
只能靠跑完整回归、再从截图里找，而截图里那张往往只有 300 px 宽。

`sheet_selected.py` 的 `--files=` 里，**文件名之间用 `|`，条目之间用 `;`** ——
不能用逗号，因为 Commons 的文件名本身经常带逗号
（`Xiangshui Creek, Wuying National Forest Park, Heilongjiang, China (6 September 2016).jpg`）。

主源是 **Wikimedia Commons 官方 API**，备源是百度图片。

为什么不是当初那套 360 图片接口：2026-09 实测 `image.so.com` 的接口**整体不通**
（`SSL: UNEXPECTED_EOF_WHILE_READING`），主源直接没了；而百度接口把返回的
**60/60 条**结果全打上 `isAigcEdit: true`（连百度自家 CDN 和知乎的真实照片也标），
这个字段已经没有区分度 —— 当初照旧拿它当一票否决，结果 38 张里 **25 张候选池被清空**、
一张都没抓到。Commons 的图是真实照片、有明确许可、标题就是山名，也没有水印图库和
「景区门票攻略」这类噪声。**教学产品要分发到学校，图源干净本身就是交付质量的一部分。**

#### 只收 JPEG

Commons 上的**地图、卫星拼接图、地形渲染图几乎都是 PNG**，实景照片几乎都是 JPEG。
这一条比任何标题关键词都管用：复核时看到「四川盆地」抓到一张英文地形图、
「台湾山脉」抓到一张分层设色高度图，两张都是 PNG。

#### 跨境山脉要查 `Category:`，别只搜关键词

小兴安岭的英文正名是 **Lesser Khingan**，而 `Category:Lesser Khingan` 只有 4 个文件、
其中 **3 个在俄罗斯**（犹太自治州、Облучье、一个采石场），仅存的中国照片是
1963 年神树镇的**生活照**（烟囱、木屋、人物），当风景照不合格。
自动检索的结果，正是一张西里尔文标题的俄方照片。

阴山也一样：`Category:Yin Mountains` 只有 2 个文件，但两个都真的在阴山
（其中「大青山一景」在包头石拐区，40.65°N/110.30°E，是真正的阴山·大青山段）。

结论：**能查到分类就先列分类成员**，比关键词检索准得多；
跨境山脉（小兴安岭 / 阿尔泰 / 帕米尔一带）尤其如此 —— 关键词会把邻国那一半捞进来。

#### 复核回路（这一步不能省）

`--sheet` 出的拼版必须**逐格目视确认**。Commons 的排序只能保证「标题里有这个地名」，
保证不了「这张图适合当教材」—— 实测「巫山」抓到巫山寺、「燕山」抓到燕山寺、
「阴山」抓到 `Yinshanosaurus`（一种恐龙，属名也来自阴山）、「祁连山脉」抓到 ISS 太空照。
**标题对、内容不对**是最常见的坑，重灾区是这几类：

| 现象 | 实例 |
| --- | --- |
| 同名寺庙 / 陵墓 | 「巫山」→ 巫山寺；「燕山」→ 燕山寺；「阴山」→ 阴山墓地 |
| 同名古生物 | 「阴山」→ `Yinshanosaurus`（恐龙，属名也来自阴山） |
| 城市全景，山只当背景 | 「阴山」→「呼和浩特北面的大青山」，画面九成是楼群 |
| 换了主体 | 「雪峰山」→ 树干树皮特写（标题是"雪松林"）；「xuefeng」→ 日本琴平神社 |
| 舷窗 / 舱内照 | 「浩良河镇航拍」→ 左上角带飞机翼尖，缩略图下还像卫星图 |

所以流程是：

1. `python scripts/pick_photos.py --only=<出问题的 id>` 出候选拼版；
2. 在拼版里挑出编号，用 `scripts/_cands.json` 查到确切文件名；
3. 把文件名写进 `fetch_photos.py` 的 `COMMONS_PICK`（**写死的文件名绝对优先，且不参与排序**——
   否则「阴山」挑的中文标题照片会被检索到的 `Yinshanosaurus` 挤下去）；
4. `--force` 重取；
5. `python scripts/sheet_selected.py --pinned` 把**钉死的那些**再拼一张复核，
   并确认没有"钉了 A 下到 B"的情况。

第 5 步别省：卡片上的照片框是 `aspect-ratio: 16/10` + `object-fit: cover`，
**竖构图的图会被居中裁掉大半**。挑图时要按裁完的样子判断（五营那张 1200×1500
裁成 1200×750 之后正好是"苔藓溪流 + 蕨类"，反而比原图更像林区）。

#### 图源规则的两代误杀（都静默）

`_is_bad_url()` 里那组"广告位"关键词误杀过两次，**两次都不报错**：

1. **拿整条 URL 做子串匹配**时，`"banner"` 命中了 `Grasslands in Heshigten Banner.jpg`。
   而 **Banner 是内蒙古县级区名的正式英译**（Heshigten Banner = 克什克腾旗），
   于是 Commons 上**所有关于内蒙古"旗"的照片都抓不下来**。
   表现只是挑定报 `pick-fail`，而 `fetch_one` 的挑定分支用 `except Exception: got = None`
   把原因吞了，看着像"网络不好"；更隐蔽的是 `rank_candidates()` 也用它，
   自动检索时这些候选是**静默跳过**的。修复靠的是把异常打出来逐层复现
   （`_download_best` 返回 None → 查池子非空 → 查 `_is_bad_url` → 命中）。
2. **改成"片段以 `/` 开头"之后仍不够**：`.../1/1a/Iconic_Mountain.jpg` 里
   第二个 `/` 后面就是 `icon`，照样中招。最终改成**完整路径段**（正则 + 边界：
   片段后必须紧跟分隔符或到结尾）。
3. 边界集合**故意不含 `_` 和 `-`**：那样 `Logo_Rock.jpg`（地名）会被误杀。
   取舍标准是 **"误杀比误放更糟"** —— 误杀是静默的，误放会在复核拼版里一眼看见。
   代价是 `logo_dark.png` 这类带下划线的 UI 资源拦不住，交给 CDN 那几条规则兜。

定稿后补了 `scripts/photo_rules.test.py`（16 项，`npm run test:photos`）双向锁住。

#### 四个必须注意的行为

- **图源记录必须合并写，不能覆盖。** `_photo_sources.json` 原来每次都是整体覆盖，
  于是任何一次 `--only=` 的局部重取都会把**其它条目**的记录抹掉（实测只剩 13 条）。
  改成"读旧文件 → `update` → 写回"。
- **收录条件不能按状态白名单。** 原来只收 `ok / ok-small / ok-relaxed / reuse`，
  而 Commons 主源返回的状态是 `commons` / `commons-pick`（来自 `_download_best` 的 tag）——
  于是**最主要的两种来源一条都没记**，38 张里只写进 14 条，而且少的正好是
  "人工挑定项"这批最需要留痕的。改成按事实判断：**图确实落盘了、且说得出它从哪来，就记**。
- **挑定失败不许静默退回检索。** 退回的后果是「本来挑好的图被一张更差的图顶掉」，
  而日志上只看得到一次成功的抓取。现在直接报 `pick-fail` 并计入「缺失」，
  让下一轮把它显出来。这条是踩过的：批量取图时三条挑定图连着撞 **HTTP 429**，
  而当时的代码正是静默退回，三张图被悄悄换成了别的。
- **429 的退避要比断连长得多**（按 `Retry-After`，默认 6 s × 次数递增）。
  条目之间也留 1 s 间隔，别把 API 打限流。
